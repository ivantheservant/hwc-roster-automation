一樣是公開文件，會進 git、會上 GitHub public repo。

內容一律用虛構例子（虛構姓名如「陳大文」「李小明」「王美美」「假甲」「假乙」；

### 需求第 3 項：REMIND 的完整演進史與現況

這條需求的字面意思是「季初前 4 週 +2 日寄提醒」，一個固定日期式的機制。
實際演進分三個階段：

1. **最初**：曾經有 `LEAD_DAYS_REMIND` 這個 Config Key，試圖直接對應這個需求
   （「季度開始後第幾日寄」）。查證後發現全專案沒有任何呼叫端真正讀取它算出來
   的日期，是一個從未接上任何邏輯的死 Key，已經移除註冊。
2. **中期**：REMIND 重新定義為「Stage 卡在 REVIEW_SENT（已寄審閱、未套用申報）
   超過 `REMIND_STUCK_DAYS` 日未前進，每日提醒幹事」，對象只有幹事，不寄給
   義工——但範圍只顧 `REVIEW_SENT` 一個 Stage，`DRAFT`（幹事還沒撳「步驟 2」）
   與 `REQUESTS_APPLIED`（幹事還沒撳「步驟 4」）停多久都完全沒有提醒，是一個
   真正的洞。
3. **現況**：REMIND 擴大成「只要 Stage 不是 `OFFICIAL_SENT`，都可能被提醒」，
   涵蓋 `DRAFT`／`REVIEW_SENT`／`REQUESTS_APPLIED` 三種停滯情境，兩個獨立的
   觸發維度，任何一個成立就提醒（同時成立也只寄一封，不重複）：
   - **停滯時間**：目前這個 Stage 已經停留超過 `REMIND_STUCK_DAYS` 日
     （三個 Stage 共用同一個門檻，理由見 A4）。
   - **死線接近**（`REMIND_DEADLINE_DAYS`，新增 Config Key，預設 7）：
     **這就是需求第 3 項「季初前 4 週 +2 日寄提醒」的現代版本**——不是
     復活 `LEAD_DAYS_REMIND`（那是「季度開始後第幾日」的概念），而是直接
     量度「距離實際的正式發出日期（`Quarters.OfficialSendOn`，缺省時退回
     `LEAD_DAYS_OFFICIAL` 從 `StartDate` 推算）還有幾日」，語意更直接、
     也不需要復活一個查證過是死值的東西。對象一律只有幹事，不寄給義工——
     義工的第一封信永遠是「步驟 4：正式發出」那一封，這一點不會因為
     REMIND 擴大範圍而改變。

實現函式：`Trigger.gs` 的 `judgeRemindAction_()`（純判斷）、
`resolveRemindReferenceDate_()`（決定「停滯多久」的參考日期，`DRAFT` 用
最新版本建立時間、其餘用 `Quarters.StageUpdatedAt`）、`readReminderLog_()`
（提醒次數，`AuditLog` 的 `TargetKey` 格式是 `季度ID|Stage`，每個「季度＋
Stage」組合各自獨立計算，Stage 前進後重新從零開始算）；`Mailer.gs` 的
`notifyAdminStageReminder_()`（實際組信、透過 `notifyAdmin_()` 寄出，
`DRY_RUN=TRUE` 時只寫 Logger）。

回歸測試：`tests/reminder_mechanism.test.js`（三種 Stage、兩個維度各自與
同時成立、次數上限與 Stage 前進後重置、只寄給幹事、`DRY_RUN` 下不真正寄出、
`OFFICIAL` 結構性防護未被繞過）。

**`TPL_REMIND_TC` 範本的特殊之處**：`EmailTemplates` 工作表裡的
`TPL_REMIND_TC`（Stage=REMIND）**不是**上面這個自動提醒機制在用的東西——
自動排程實際寄出的提醒，訊息文字是 `notifyAdminStageReminder_()` 直接在
程式碼裡組出來的，完全不讀 `EmailTemplates`。`TPL_REMIND_TC` 只有在
「測試工具 ▸ 寄送（測試模式）」手動指定 Stage=REMIND 時才會被用到（這個
測試工具沿用既有的 `sendStage()`／`listRecipients_()` 管線，對 REMIND 階段
是依 `EmailRecipients.Stage` 欄篩選收件人，不是只寄給幹事——這是既有、
沒有改動過的人手測試功能行為，跟自動化機制的「只寄給幹事」是兩回事，
使用這個測試工具時請自行注意）。這次已經更新 `EmailTemplateSeed.gs` 的
`TPL_REMIND_TC` 預設內容（只改程式碼的 seed 值，沒有寫入試算表），
新增 `{CurrentStage}`／`{NextAction}` 兩個 placeholder，建議的新版
Subject 與 BodyHtml 全文如下，**由 Ivan 自行決定要不要貼入 EmailTemplates
工作表覆蓋現有內容**：

```
TemplateID：TPL_REMIND_TC
Subject：
{QuarterID} 粵語堂職事表提醒——目前狀態：{CurrentStage}

BodyHtml：
<p>各位堂委、幹事：</p>
<p>{QuarterID}（{StartDate} 至 {EndDate}）的職事表目前狀態：{CurrentStage}，現提醒各位跟進。</p>
<p>下一步：{NextAction}</p>
<p>職事表計劃於 {OfficialSendDate} 正式發送給各服侍人員，請在此之前完成所需的步驟。</p>
<p>試算表連結：{SpreadsheetUrl}</p>
<p>如有查詢，請直接回覆本郵件。</p>

BodyPlain：
各位堂委、幹事：

{QuarterID}（{StartDate} 至 {EndDate}）的職事表目前狀態：{CurrentStage}，現提醒各位跟進。

如有查詢，請直接回覆本郵件。

{QuarterID},{StartDate},{EndDate},{OfficialSendDate},{SpreadsheetUrl},{CurrentStage},{NextAction}
```

`{CurrentStage}`／`{NextAction}` 兩個新 placeholder 由 `Mailer.gs` 的
`buildMailContext_()` 動態算出（查 `Quarters.Stage` 與 `Constants.gs` 的
`STAGE_NEXT_ACTION` 對照表）；任何範本用到這個階段呼叫沒有提供的
placeholder，`applyPlaceholders_()` 會直接清空成空字串，不會留下未代入的
花括號文字、也不會拋錯——這是這次順手加的安全網，見 A4。

## A4. 已知的設計取捨與已被推翻的假設

- **`Stage=REQUESTS_APPLIED` 時步驟 3 與步驟 4 同時可用，是刻意設計，不是
  bug**：Web UI 的五張步驟卡片邏輯（`FiveStageCore.gs` 的
  `computeFiveStepAvailability_()`）在這個 Stage 會讓步驟 3（可重複執行
  套用新申報）與步驟 4（正式發出）同時 `available`。曾經有一版測試假設
  「任何時候最多只有一個步驟按鈕 active」，寫測試時發現這個假設不成立——
  步驟 3 的設計本來就是「可重複執行」（幹事收到新一輪申報還是可以再套用
  一次），即使 Stage 已經前進，這個按鈕仍然合理地保持開著。測試已經改為
  明確驗證這個真實情況，不是繼續套用錯誤假設。
- **`OFFICIAL` 永遠不由自動排程觸發，是結構性防護，不是慣例**：
  `Trigger.gs` 的 `assertOfficialNotFromAutomationTrigger_()` 用一個執行期
  旗標（`AUTOMATION_TRIGGER_CONTEXT_ACTIVE`）在 `dailyAutomationCheck_()`
  執行期間主動攔截任何嘗試觸發 `OFFICIAL` 階段的呼叫，即使日後有人不小心
  在 `Trigger.gs` 裡加一行呼叫 `sendStage(..., MAIL_STAGES.OFFICIAL)` 也會
  被擋下來並記錄到 `AuditLog`——這不是「這裡的程式碼剛好沒寫觸發 OFFICIAL
  的邏輯」這種容易被以後修改破壞的保證，而是主動拒絕。REMIND 範圍擴大到
  涵蓋三個 Stage 之後，這道防護完全沒有被觸碰，`tests/reminder_mechanism.test.js`
  有專門的測試案例驗證。
- **`Role` 的 `ALL` 值名稱與實際行為相反**：`ALL` 直覺上容易被理解成
  「所有階段都收」，實際意思剛好相反——是「不是審閱者」，不會收到
  「步驟 2：寄給堂委審閱」那封信，只依 `Stage` 欄決定收不收其他階段。
  已決定保留這個值不改名、不移除（可能有其他用途尚未確定），但在三處
  文件（`EmailRecipientsSeed.gs` 檔頭、`Mailer.gs` 的 `listRecipients_()`
  註釋、`docs/幹事操作說明.md`）都明確指出這個落差。
- **REMIND 的三個 Stage 共用同一個 `REMIND_STUCK_DAYS` 門檻，不是各自
  獨立設定**：這是刻意的簡化——目前沒有證據顯示 `DRAFT`／`REVIEW_SENT`／
  `REQUESTS_APPLIED` 三個階段需要不同的停滯容忍度，拆成三個 Config Key
  只會增加設定複雜度而沒有對應的實際好處。如果日後發現某個 Stage 確實
  需要不同的門檻（例如 `REQUESTS_APPLIED` 階段幹事習慣拖比較久），再拆
  不遲，不需要現在預先設計。
- **`DRAFT` 停滯時間的參考日期改用「最新版本建立時間」，不是
  `StageUpdatedAt`**：`Quarters.StageUpdatedAt` 只在 `advanceQuarterStage_()`
  被呼叫時才會寫入，而 `DRAFT` 是預設狀態，在 `GENERATE` 自動生成之前，
  這個欄位很可能完全空白——如果沿用 `StageUpdatedAt` 判斷「停留了多久」，
  一個季度還沒到生成日期就會被誤判成「停滯」。改用 `RosterVersions.CreatedAt`
  （版本已經生成，代表輪到幹事按「步驟 2」了，這才是「幹事開始需要行動」
  的真正起點）解決這個問題。
- **範本 placeholder 缺值時清空而不是保留原始花括號文字**：
  `applyPlaceholders_()`（`Mailer.gs`）新增了一道清理，任何範本文字裡
  形如 `{XxxYyy}` 但不在已知 placeholder 清單內的字串，一律換成空字串。
  取捨：這犧牲了「打錯 placeholder 名稱時能一眼看到 `{Foo}` 字樣、方便
  除錯」這個好處，換取「收件人絕不會在信裡看到未代入的花括號文字」——
  對於會寄給真人的正式信件，後者更重要；除錯應該在 `DRY_RUN=TRUE` 模式
  下用「測試工具 ▸ 寄送（測試模式）」人手核對內容，不應該依賴收件人
  收到的信件本身暴露問題。

### 階段 E：個人 PDF 生成效能複查與 6 分鐘執行上限風險評估

**E1／E2：重新量度＋批次策略評估結論——現行實作已經是最佳化，只找到
一個小效能缺口並已修正，其餘沒有再改。**

重新讀 `src/PdfBatch.gs` 全文，確認：

- highlight 格式化早就是共用 render context 的整批寫入
  （`openPersonalPdfRenderContext_()`／`applyPersonHighlightToContext_()`，
  見 A5），58～60 人的批次只複製一次工作表，不是逐人複製，這部分已經
  沒有進一步可安全批次化的空間——A5 的結論在本輪依然成立，本輪沒有
  再改動這部分程式碼。
- 「跳過已存在的 PDF」判斷**本來就是一次過列資料夾內容**（呼叫端在
  `generatePersonalPdfBatch_()` 用 `listExistingFileSizes_(folder)`
  把整個資料夾內容讀成一個 `Map<檔名,大小>`，只查一次 Drive API），
  不是逐人查——這點跟本輪任務指示原本擔心的「是不是逐個檔案查」的疑慮
  相反，程式碼一開始就是對的。

但重新讀 `generateOnePersonalPdf_()` 的既有查詢分支邏輯時，發現一個
真實但小的浪費：當呼叫端要求 `forceRegenerate=TRUE`（例如手動「強制
重新產生全部 PDF」）時，呼叫端傳入的 `existingFileSizes` 其實是 `null`
（見 `generatePersonalPdfBatch_()` 的呼叫端邏輯），於是程式仍然會為
**每一個人**多執行一次 `folder.getFilesByName(fileName)`（真實 Drive
API 查詢），查完的結果卻完全用不到——因為 `forceRegenerate=TRUE` 時，
`!forceRegenerate && alreadyExists` 這個判斷式永遠是 `false`，一定會
往下重新產生。已修正為 `forceRegenerate=TRUE` 時整段查詢與判斷完全
跳過（`src/PdfBatch.gs`）。影響：強制重新產生 60 人份 PDF 時，省下
60 次多餘的 Drive API 呼叫（單次查詢耗時雖小，但累積 60 次在 Apps
Script 執行時間與 API 配額上都有實際節省，且原本這個查詢完全沒有
產生任何有用的效果，純粹是浪費）。

E4 回歸測試：[`tests/pdf_batch_perf.test.js`](../tests/pdf_batch_perf.test.js)——
驗證修正前後行為完全不變（`forceRegenerate=FALSE` 且已存在達標檔案
仍然略過；不存在或大小不足仍然重新產生；`forceRegenerate=TRUE` 不論
是否存在都一定重新產生），並且用呼叫次數計數的假查詢函式證明
`forceRegenerate=TRUE` 時查詢函式確實完全沒有被呼叫（修正前會被呼叫，
修正後不會）。

**E3：Apps Script 6 分鐘執行上限風險評估——現有機制已經足夠，不需要
再設計新的續跑方案。**

本輪任務原本預期可能需要「設計（不實作）一個可續跑的方案」，但重新讀
`PdfBatch.gs` 發現這個方案**早就存在且已經在運作**，不是缺口：

- `PDF_BATCH_TIME_BUDGET_MS`（`Constants.gs`，240000ms＝4 分鐘，刻意
  比 6 分鐘上限留有安全餘裕，讓函式有機會在真正逾時前主動停止並儲存
  進度）作為批次迴圈的時間預算上限，迴圈內每處理完一人就檢查
  `已耗時 + 平均每人耗時 > 時間預算` 是否成立，成立就主動停止。
- 進度透過 Script Properties 持久化（哪些人已經處理完），下一次呼叫
  （不論是幹事再按一次選單、或是 time-based trigger 再次觸發）會從
  上次停下的地方接著做，不會重新開始、也不會重複處理已完成的人。
- `PDF_BATCH_SIZE`（seed 預設 25）是另一個獨立的、每次執行最多處理
  人數的上限，跟時間預算是兩個各自獨立的停止條件，任一個先到就停——
  這代表即使時間預算綽綽有餘，單次選單點擊也不會一次處理超過 25 人，
  60 人份預設需要至少 3 次點擊（或 3 次 trigger 觸發）才能全部完成。

**風險評估結論**：以目前量測到的單人耗時估算（PDF 匯出約 0.8 秒／人，
加上既有的 `PDF_EXPORT_PACING_MS` 節流間隔約 0.5 秒／人，highlight
因為已經整批處理、每人幾乎不佔額外時間），60 人份全部處理大約需要
60×1.3秒≈78 秒，遠低於 240 秒的時間預算——**實際限制批次次數的是
`PDF_BATCH_SIZE=25`這個人數上限，不是 6 分鐘時間上限**，25 人上限本身
就已經是一種保守的分批機制。換句話說，現有「時間預算＋人數上限＋
Script-Properties 續跑」三者組合已經是一個運作中的可續跑方案，能夠
安全處理遠超過 60 人的規模而不會真正撞到 6 分鐘上限，不需要再另外
設計新機制。E4 測試檔案內也用模擬迴圈驗證了「60 人在預設設定下需要
3 輪完成，且即使把時間預算故意調到極短，機制依然能分批收斂完成、
不會卡死」。

如果日後教會規模顯著成長（例如超過 200 人），才需要重新評估
`PDF_BATCH_SIZE` 是否要調高、或改成完全依賴時間預算而不設人數上限——
本輪沒有證據顯示現在有這個需要，屬於「有需要再處理」的項目，記在此處
供日後參考。

### 階段 F：全系統唯讀自我檢查整合——「維護 ▸ 🩺 全面體檢（唯讀）」

**F1 盤點**：全專案累積了 17 個各自獨立的唯讀檢查／自我檢查選單項目：

自我檢查、AuditLog 摘要、檢查設定、重新載入設定、檢查 Config 行數、
檢查各版本派工紀錄、檢查個人 PDF 完整性、SOFT 規則與選人加權、欄標題
對照、個人版 highlight 定位、上線前檢查、查看自動排程狀態、檢查自動
排程條件。逐一讀完每個工具的實作後，發現它們天生分成三種不同性質，
不是同一類東西：

1. **可以完全自動跑、不需要任何輸入**的統計／自我檢查類（9 個裡有 8 個

   可以分級的健康狀態。

**F2 評估與實作結論**：把第 1 類的 9 個項目整合成新選單項目
「維護 ▸ 🩺 全面體檢（唯讀）」（`src/FullHealthCheck.gs` 的
`runFullHealthCheck_()`），一次過跑完並統一寫入 Diagnostics 的
「全面體檢」分區；第 2、3 類**維持獨立選單項目**，不勉強整合（理由已
寫在 `FullHealthCheck.gs` 檔頭註解，摘要：第 2 類塞進來會變成要對每個
季度每個版本各跑一次，失去「一次過」的意義；第 3 類沒有可分級的健康
狀態）。**全部 17 個既有選單項目原封不動保留**，這是額外多一個入口，
不是取代任何一個。

整合進「全面體檢」的 9 項：檢查設定、Config 行數、各版本派工紀錄、
電郵範本自我檢查、AuditLog 摘要、自動排程狀態、自動排程條件、全部

7 項各自依既有語意分級（例如：電郵範本有未代入的變數，若範本目前是

會取最後一行的值、不會直接壞掉）。單一檢查項目執行失敗（例如 Drive
API 逾時）不會讓其餘 8 項跟著中斷，失敗的那一項直接記為「必須處理：
執行失敗」，並附上原始錯誤訊息。

### 階段 D：真實資料規模的壓力檢視

**D1／D2 找到的真實模式**（`readSheet()` 本身用一次 `getRange().getValues()`
批次讀取，不是逐格 `getValue()`，這個底層已經是正確寫法——問題不在
這裡，而在「呼叫的次數」與「每次讀多少」）：

1. **Web UI `apiGetFlowState()` 重複讀取 `SendLog` 三次——已修正**：
   這個函式幾乎每次 Web UI 操作後都會被呼叫一次（`ui/Script.html` 的
   `closeWizardAndRefresh()`），原本步驟 2／4／5 的 `lastSentAt` 各自
   呼叫 `findLastSendTimestamp_()`，即各自完整讀一次 `SendLog`——同一次
   執行內重複讀了三次同一張、只會越來越大的表。已改成
   `findLastSendTimestampsByStage_()`，一次過讀完 `SendLog`、三個階段
   的最後寄送時間一次算齊，讀取次數從「跟查詢階段數成正比」變成「固定
   1 次」。純粹的效能重構，回傳格式與行為完全不變。
2. **`buildFineTuneContext_()`（`FineTune.gs`，步驟 3／5 每次執行都會
   呼叫）與 `readPriorWeeks_()`／`readQuarterAssignments_()`
   （`Generator.gs`，步驟 1 生成初稿時呼叫）三者都對
   `RosterAssignments` 做**完整表格讀取**，再用 JavaScript 端
   `.filter()` 篩到只要的季度／版本／日期範圍——`RosterAssignments`

   規模（每版約 195 格，一季常見到 v10 以上）估算，這張表可能已經有
   數千行，`getValues()` 單次讀取仍然快（毫秒到低個位數秒級），但

   規模風險，但不是這一輪能安全解決的**——`readSheet()` 的架構本身

   需要的那一段」，Google Sheets 的 `getValues()` 也沒有伺服器端篩選

### 階段 E：交接資料完整性

**E1／E3 稽核結論：程式碼本身完全沒有寫死任何人的身分**。全文搜尋
`Session.getActiveUser()`／`Session.getEffectiveUser()` 的全部呼叫點
（11 處），以及所有跟「誰可以做什麼」有關的判斷（`SCRIPT_ACCOUNT_EMAIL`／
`WEBAPP_ALLOWED_EMAILS`／`MAIL_ADMIN_NOTIFY`），確認：需要記住身分的
地方全部是 Config 工作表裡可以自由修改的值，不是寫死在程式碼裡的
帳號；「誰在操作」永遠透過 Google 的 `Session` API 即時讀取。**這代表
移交這件事完全不需要改動任何程式碼**，需要處理的全部是平台層級的
擁有權設定與 Config 值。

盤點出以下 8 項綁定在「開發帳戶」（Ivan 個人身分）、不會隨程式碼一起
自動轉移的項目：clasp 本機登入（開發用）、Web App 部署身分

全部操作的實際執行身分）、Trigger 擁有者（哪個帳戶執行了「安裝自動
排程」）、Google Drive 的 `RosterPDF` 資料夾擁有權、**Google 試算表

註解已經提到「試算表擁有者無法被移除編輯權，這是 Google 的限制」，
即使 `SCRIPT_ACCOUNT_EMAIL` 改成別人，原擁有者依然可以繞過 v0 保護）、
Script Properties（PDF 批次進度，屬於 Apps Script 專案本身，不綁定
個人帳戶，會隨專案擁有權自動轉移，不需要特別處理）、三個跟身分有關
的 Config 值（`SCRIPT_ACCOUNT_EMAIL`／`MAIL_ADMIN_NOTIFY`／
`WEBAPP_ALLOWED_EMAILS`）、GitHub public repo 的擁有權（如果要一併
移交）。
