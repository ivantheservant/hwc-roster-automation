# 排表規則

這份文件記錄**教會定下的排表規則**，以及每一條在系統裡是怎樣落實的。
跟 `docs/系統範圍稽核.md` 一樣是公開文件，會進 git、會上 GitHub public repo。

⚠️ **不含任何真實姓名**。名單一律由幹事在試算表維護，程式碼與文件只用
「現任堂委」「現任執事」這類身分描述，以及虛構例子（假甲、假乙）。

---

## 規則總覽

| # | 規則 | 級別 | 系統怎樣落實 |
|---|---|---|---|
| 1 | 報告（家事報告）只可以由現任堂委擔任 | 硬 | `HARD_ROLE_REQUIRED` ＋ `Posts.RequiredRoles` |
| 2 | 當值堂委只可以由現任堂委或現任執事擔任 | 硬 | 同上（一個崗位可以接受多個身分） |
| 3 | 個別人士的崗位限制 | 硬 | `HARD_PERSON_POST_EXCLUDED` ＋ `PersonPostExclusions` 工作表 |
| 4 | 現任堂委盡量集中在四個指定崗位 | 軟 | `SOFT_ROLE_POST_FOCUS`（扣分，強度可調） |
| 5 | 每年固定四次合堂 | 工具 | 「產生年度合堂建議」＋ `SpecialSundays.Confirmed` ＋ 提醒 |

**硬規則**＝系統絕不會自動違反，人手改動也會被步驟 3／5 的重跑檢查揪出來。
**軟規則**＝有其他人選時會避開，人手不足時仍然可以排（只是扣分）。

## 身分名單：`Roles` 工作表

規則 1、2、4 全部圍繞「這個人是甚麼身分」，所以系統需要一份身分名單。

| 欄位 | 意思 |
|---|---|
| `RoleAssignmentID` | 隨便一個識別碼，方便你自己對照 |
| `PersonID` | 對應 `NameMapping` 的 PersonID（**不是姓名**） |
| `RoleCode` | `COMMITTEE`＝堂委、`DEACON`＝執事 |
| `EffectiveFrom` | 生效日（yyyy-MM-dd）。留空＝一直以來都是 |
| `EffectiveTo` | 結束日。留空＝仍然在任 |
| `Active` | `TRUE` 才生效 |
| `Notes` | 備註 |

一個人可以有多行（同時是堂委又是執事、或者卸任之後再連任）。

### 為甚麼是一張新工作表，不是塞進現有的表

- **不可以寫死在程式碼**：堂委與執事每屆換人，寫死等於每次換屆都要改程式、
  重新部署；而且真實姓名不可以進入公開的 repo。
- **不應該塞進 `Eligibility`**：`Eligibility` 回答的是「這個人**做不做得到**
  這個崗位」（人 × 崗位 × 歷史次數），是一種能力／資格。身分回答的是
  「這個人在教會**擔任甚麼職份**」，跟崗位無關——一位堂委即使一個崗位都
  沒做過，他一樣是堂委。而且 `Eligibility` 沒有時間維度，做不到換屆。
- **不應該在 `NameMapping` 加一欄**：一欄只放得下「現在是甚麼身分」。
  換屆之後舊值會被覆蓋，上一屆的職事表就會被追溯判定為違規（當時他明明
  是堂委）。要保留歷史就一定要「一個人可以有多行、每行帶生效期間」。

### ⚠️ 換屆時的正確做法

**在卸任那一行填 `EffectiveTo`，然後為新人加新一行。
不要刪除舊那一行，也不要直接改 `PersonID`。**

刪掉那一行等於告訴系統「這個人從來都不是堂委」，於是他做過報告的所有
舊季度會全部變成違反規則 1。填 `EffectiveTo` 則保留了「他在某段期間
是堂委」這個事實，舊季度重新核對仍然是零違規。

系統判斷身分一律**以該主日當日的日期**為準，不是以「今天」為準——
這正是為了讓換屆不會影響已經發出的舊職事表。

## 崗位的身分要求：`Posts.RequiredRoles`

規則 1 與 2 的實際開關在 `Posts` 工作表的 `RequiredRoles` 欄：

| 崗位 | `RequiredRoles` 填甚麼 |
|---|---|
| 報告 | `COMMITTEE` |
| 當值堂委 | `COMMITTEE,DEACON`（逗號分隔＝**任何一個**符合即可） |
| 其餘所有崗位 | 留空（＝沒有身分要求，行為完全不變） |

欄位不存在或留空時，那個崗位完全不受身分規則影響，所以**還沒有填的環境，
系統行為跟加入這些規則之前一模一樣**。

欄位用「維護 ▸ 補建 Posts 欄位（崗位身分要求）」新增。這個工具**只加欄位、
一格值都不會填**——哪個崗位需要哪個身分是教會的規定，工具沒有資格猜，
而且猜錯的後果很嚴重（那個崗位會直接排不到人）。

### ⚠️ 填寫次序的陷阱

如果先填了 `RequiredRoles`、但 `Roles` 名單還是空的，**那個崗位會完全
排不到人**（沒有人持有那個身分）。「查看 ▸ 身分名單概況（唯讀）」有專門
的檢查會報告這個情況（「這個崗位會永遠排不到人」）。

建議次序：先建 `Roles` 並填好名單 → 再填 `Posts.RequiredRoles` →
最後用「身分名單概況」核對一次。

## 合資格人選怎樣決定：聯集，不是交集

這一點是設計上最需要想清楚的地方。

**問題**：一位新任堂委可能從來沒做過報告，`Eligibility` 完全沒有他的
報告那一行。如果要求「`Eligibility` 有這一行 **且** 身分符合」（交集），
就會把他排除，直接違反教會的規則。

**做法**：

1. **候選池 ＝ `Eligibility` 名單 ∪ 持有所需身分的人**
   → 解決「新任堂委沒有歷史紀錄」。
2. **減去 `Eligibility` 裡明確 `Eligible=FALSE` 的人**
   → 保留幹事的覆寫權。幹事寫下「即使他是堂委，也不要排他做報告」
   這個決定不會被身分規則靜靜推翻。
3. **再由 `HARD_ROLE_REQUIRED` 逐格逐日檢查真正的身分**
   → 解決「前任堂委有歷史紀錄但已經卸任」——他仍然在 `Eligibility` 裡，
   聯集不會踢走他，但硬規則會。

**為甚麼不能完全放棄 `Eligibility`**：

- `HistoricalCount` 住在 `Eligibility`，是配額與選人分數的來源；
- 其餘所有沒有身分要求的崗位完全靠它決定人選；
- 它仍然是幹事逐人逐崗位覆寫的地方。

三條規則檢查路徑（生成初稿／步驟 3-5 重跑檢查／核對職事表）**共用同一套
增補邏輯**，所以不會出現「生成時容許、核對時說違規」這種矛盾。

## 規則 3：個人崗位限制（`PersonPostExclusions` 工作表）

用來表達「某人暫時不做某崗位，日後另行通知」。

| 欄位 | 意思 |
|---|---|
| `ExclusionID` | 隨便一個識別碼 |
| `PersonID` | 對應 `NameMapping` |
| `PostID` | 對應 `Posts` |
| `Reason` | 原因（會出現在違規訊息裡，寫給人看的） |
| `EffectiveFrom` | 生效日。留空＝即時生效 |
| `EffectiveTo` | 解除日。留空＝暫時無限期 |
| `Active` | `TRUE` 才生效 |

**日後解除時：填 `EffectiveTo`，不要刪除整行。** 道理跟 `Roles` 一樣——
刪掉會令解除之前的舊季度被追溯判定為違規。

目前已知需要的兩條：一位新任堂委可以擔任報告與當值堂委，但暫時不擔任
主席；另一位堂委不擔任主席。兩條都是「主席」這個崗位的個人排除。

## 規則 4：堂委集中在四個崗位（軟規則）

現任堂委盡量集中在**主席、報告、當值堂委、聖餐襄禮**四個崗位，其餘崗位
盡量不排，避免負擔過重。

### 為甚麼是軟規則

教會的說法是「**盡量**集中」，不是「不得擔任」。做成硬規則的話，一個人手
緊絀的主日（例如當日只有三個人有空、其中兩個是堂委）會直接排不到人，
留下一個空格要幹事人手補——結果反而更差，而且違背規則本身「避免負擔
過重」的原意（排不到人最後還是要找人補）。

做成扣分之後：有其他人選時自然不會揀堂委，沒有其他人選時照樣排得出。

### 設定（`RuleSettings` 的 `SOFT_ROLE_POST_FOCUS` 那一列）

| 欄位 | 填甚麼 |
|---|---|
| `Enabled` | `TRUE` |
| `Level` | `SOFT` |
| `ScopePostIDs` | **集中的四個崗位**的 PostID，逗號分隔 |
| `TargetValue` | 強度倍率，見下 |
| `ParamJSON` | `{"roles":["COMMITTEE"]}`（留空時預設就是堂委） |

`ScopePostIDs` 用的是**白名單**（要集中的崗位），不是黑名單（要避開的崗位）。
理由：日後新增崗位時，白名單的預設行為是「新崗位堂委都應該少做」，正正
就是規則 4 的原意；黑名單則要記得逐個補上去。

### 強度怎樣調

扣分 ＝ `(SOFT 基礎分 10 + max(0, 100 − Priority)) × TargetValue`

| `TargetValue` | 效果 |
|---|---|
| `1`（預設） | 跟一般軟規則同級，只是一個輕微偏好 |
| `5`～`10` | 明顯偏好，通常足以令有其他人選時一定不揀堂委 |
| 很大（例如 100） | 幾乎等同硬規則（但人手緊絀時仍然排得出），會壓過其他軟規則（例如次數平衡），要小心 |

**建議由 `5` 開始試**，生成之後用「查看 ▸ 軟規則實測量度（唯讀）」的
第 6 項看實際效果再調。

### 怎樣看執行得好不好

「查看 ▸ 軟規則實測量度（唯讀）」新增了第 6 項「堂委崗位集中度（規則 4）」，
會顯示：堂委本季總共服侍幾多次、其中幾多次落在集中崗位以外、比例是多少，
再逐崗位、逐人（只顯示 PersonID，不顯示姓名）列出明細。

數字越低代表規則 4 執行得越好。偏高時可以調大 `TargetValue`。

## 規則 5：每年四次固定合堂

| 合堂 | 日期 | 系統能不能算 |
|---|---|---|
| 復活節主日（浸禮） | 每年浮動 | ✅ 用復活節演算法算出 |
| 五月合堂 | 5 月 22 日前後的主日 | ❌ **要出表時向教會確認** |
| 宣教月合堂 | 8 月最後一個主日 | ✅ 算得出 |
| 十月主日（浸禮） | 10 月第一個主日 | ✅ 算得出 |

### 工具：「準備工作 ▸ ⚠️ 產生年度合堂建議」

輸入年份，一次過算出四行 `SpecialSundays` 建議，在確認畫面列出每一項的
日期、所屬季度、是否已經有同一日的列，**確認之後才寫入**。

- 只 append，永遠不覆寫——同一日已經有列的一律略過，不會蓋走你已經填好的
  `SkipPostIDs`／`ExternalOwner`。
- `SkipPostIDs` 與 `ExternalOwner` **一律留空**，由你按每一次合堂的實際
  安排自己填。

復活節日期用 Anonymous Gregorian algorithm（Meeus/Jones/Butcher）計算，
**沒有任何寫死的日期表**，1583 年之後任何年份都準確。測試檔
`tests/annual_combined.test.js` 用 13 個獨立查證過的已知日期逐年驗證。

### 「未確認」怎樣表達：`SpecialSundays.Confirmed`

五月那次的日期每年不同，要出表時才能向教會確認，所以工具寫入時會把那一行
標成 `Confirmed=FALSE`。

⚠️ **空白＝已確認**，只有明確填 `FALSE` 才算未確認。這個方向是刻意選的：
這一欄是後加的，如果空白當「未確認」，全部既有的列一開機就會變成未確認，
提醒機制會即刻噴一堆假警報。

### 「五月那次要確認」不靠人記

兩個地方會主動提醒：

1. **生成初稿前一星期**（可在 Config 的 `REMIND_UNCONFIRMED_SPECIAL_DAYS`
   調整）——併入現有的提醒機制（`TRIGGER_REMIND`），不是另建一套，所以
   同樣有「每季每 Stage 各自計次數」「今天提醒過就不再提」「上限 3 次」
   「只寄給幹事、絕不寄給義工」全部既有保護。
2. **生成初稿的完成畫面**——「步驟 1：生成初稿」與「準備工作 ▸ 生成職事表」
   兩個畫面都會列出未確認的特殊主日。

用生成日期而不是正式發出日期做基準，因為 `SkipPostIDs` 是在生成那一刻
才套用——生成完才發現日期錯了，整張表要重新生成。

### 三種合堂類型（浸禮／堂慶／宣教月）需不需要分開處理？——**不需要**

歷史上三者的分別是：浸禮翻譯需求較高、堂慶通常由英語堂帶領詩與司琴、
宣教月講員多為宣教士。逐項核對之後，**三種分別全部落在系統本來就不會
自動排的崗位上**：

- 「翻譯需求較高」——翻譯是 `AutoGenerate=FALSE` 的崗位，系統從來不會自動
  派，一律由幹事用「填寫講員／翻譯／獻花」人手填。
- 「英語堂帶領詩司琴」——已經完全表達得到：`SkipPostIDs` 填那兩個崗位的
  PostID、`ExternalOwner` 填「英語堂」。這正是 2026-10-04 實測過的做法。
- 「講員多為宣教士」——講員同樣是 `AutoGenerate=FALSE`，人手填。

結論：`Type`（自由文字）＋ `Title` ＋ `SkipPostIDs` ＋ `ExternalOwner`
四個既有欄位已經足夠，而且是用**資料**表達，不是在程式碼寫死三種類型的
特殊邏輯（後者一旦教會改做法就要改程式）。年度合堂工具會為每一次合堂
預先填好合理的 `Type`／`Title` 建議值，讓這個分別以資料形式保留下來。

## 規則在哪三條路徑生效

| 路徑 | 甚麼時候跑 | 檔案 |
|---|---|---|
| 生成 | 步驟 1：生成初稿 | `Generator.gs` 的 `evaluateViolations_()` |
| 重跑檢查 | 步驟 3：套用修改申報、步驟 5：改動後重發 | `FineTune.gs` 的 `findStateViolations_()` |
| 核對 | 測試工具 ▸ 核對職事表 | `Verify.gs` 的 `checkHardRuleViolations_()` |

三條都涵蓋是必要的：生成器只管自己排的格，**幹事在 grid 直接打一個名字
它管不到**——那種情況只有後兩條路徑捉得到。

違反時訊息會明確指出違反哪一條，例如：

```
違反身分限制：報告 只可以由「堂委」擔任，但此人在 2027-01-10 當日並未持有這個身分
違反個人崗位限制：PersonPostExclusions 明確排除此人擔任 主席（原因：暫時不擔任主席）
```

## 規則沒有在 `RuleSettings` 登記時會怎樣

一般規則的慣例是「`RuleSettings` 沒有那一列＝停用」。但規則 1／2／3 這
兩條硬規則是**例外，沒有登記時預設啟用**：

- 它們真正的開關在資料本身（`Posts.RequiredRoles` 有沒有填、
  `PersonPostExclusions` 有沒有列），沒有資料就完全沒有影響；
- 反過來如果沿用「沒登記＝停用」，幹事補建了工作表、填好名單、填好
  `RequiredRoles` 之後規則仍然不生效，而且沒有任何地方會提示他還差一步——
  這種「看起來做齊了但其實沒生效」是最危險的失敗方式。

同樣地，這兩條規則沒有登記時**級別預設是 `HARD`**（一般規則是 `SOFT`）。
如果級別掉回 `SOFT`，生成器就不會排除違規者（它只排除 `HARD` 級別的
候選人），一個不是堂委的人照樣排得到做報告，而且畫面上完全看不出。
這一點有專門的回歸測試鎖住（`tests/role_hard_rules.test.js`）。

幹事仍然可以在 `RuleSettings` 明確填 `Enabled=FALSE` 停用它們。

規則 4（`SOFT_ROLE_POST_FOCUS`）則維持一般慣例：**沒有登記＝停用**，
因為它需要 `ScopePostIDs` 才知道哪四個崗位是「集中崗位」，沒有設定就
無從執行。
