### 階段 A：一季一條固定連結（新增 `src/PublicRoster.gs`）

（唔係主試算表本身）——每次發佈都覆寫呢個檔案嘅內容，但**保留同一個
檔案 ID**（`resolveOrCreatePublicSpreadsheet_()` 一定先試 `openById`，
搵唔到先至 `create`），所以連結永遠唔變、永遠顯示最新版本。

⚠️ **主試算表本身絕對唔可以對外分享**——公開嘅只係呢個新檔案，用
`DriveApp.setSharing(ANYONE_WITH_LINK, VIEW)`。內容白名單刻意收得好緊：
`buildPublicRosterContent_()` 只組合職事表格、圖例（沿用第十輪
`buildLegendRows_()`）、更新時間，靜態原始碼檢查鎖住呢個函式**唔會**
出現 `PERSON_ID`／`EMAIL`／`getNotes`／`ruleFlags`／`MailApp` 呢幾個字——
已排定嘅格即使有規則警告都**唔上色**（`computePublicRosterBackgrounds_()`
刻意唔重用 `applyCellMarks_()` 嘅 WARNING／FORCED 顏色，嗰兩種係診斷用途，
唔應該喺公開版出現）。

`PublicLinks` 工作表（新增）逐季記一行：檔案 ID、網址、最後發佈時間／版本、
分享設定。`查看 ▸ 公開連結狀態（唯讀）` 會即時重新查一次 Drive 嘅實際

### 階段 B：個人專屬連結（新增 `src/WebAppPersonalLink.gs`）

每位義工可以有一條專屬連結，打開見到完整職事表、自己個名 highlight
標示，一季一條、永遠最新。用現有 Web App 加一個新入口：
`<web app url>?q=<QuarterID>&p=<token>`，token 用
`Utilities.getUuid().split('-').join('')` 產生（32 字元十六進位）。

⚠️ **需要新增一個 `access=ANYONE` 嘅部署**——現有幹事介面嘅部署係
`access=MYSELF`，同一個 script project 可以有多個部署，各自 `access`
獨立，但**共用同一個 `doGet()`**。`WebApp.gs` 嘅 `doGet(e)` 而家喺最開頭
就分流：`e.parameter.p` 有值就完全唔行幹事介面嗰三層防護（義工冇 Google
身分過唔到白名單），改由 `renderPersonalRosterPage_()` 處理，呢個函式
自己有一套獨立嘅安全模型：

- 只檢查 `assertWebAppEnabled_()`（總開關），**唔會**檢查
  `assertApiCallerAuthorized_()`（電郵白名單）——義工冇 Google 身分，
  呢層本來就唔適用。
- Token 比對用 `matchPersonByToken_()`，exact match only（唔接受部分／
  大小寫混淆比對），空白 token 一律當唔存在（防止「兩行都空白」誤配）。
- Token 無效／季度不存在／資料建構失敗，一律導向同一個
  `renderPersonalRosterError_()`，回同一句中性訊息
  `PERSONAL_LINK_INVALID_MESSAGE`，**唔會**因為失敗原因唔同而露出唔同
  提示（測試入面特登有一個「反證」——用一句會洩露原因嘅訊息證明檢查
  規則本身有效）。
- 頁面本身：`ui/PersonalRoster.html` 完全冇 `google.script.run`、
  冇 `<form>`／`<input>`，唯一嘅互動係深色/淺色切換掣，改變唔到任何
  資料。

`NameMapping` 新增 `PersonalLinkToken` 欄。`維護 ▸ 補發個人專屬連結
token`（只填未有 token 嘅人，唔覆寫現有）同
`維護 ▸ ⚠️ 重新產生單一個人的 token（外洩時用）`（針對一個人強制重新
產生）兩個工具**本輪都冇執行過**——只實作咗函式，符合本輪「唔可以寫入
試算表」嘅限制。

### 階段 C：ICS 日曆檔（新增 `src/IcsExport.gs`）

步驟 4／5 寄出嘅個人信而家會多附一個 `.ics`，iPhone／Google 日曆一撳就加。

**⚠️ 架構調整（原始需求文字寫「喺 Config 逐個設定」，實作改用 Posts 欄）**：
每個崗位嘅提早到場分鐘數，實作放喺 `Posts` 工作表新增嘅
`EarlyArrivalMinutes` 欄，而唔係逐一開 Config Key（例如
`EARLY_ARRIVAL_MINUTES_音響`）。理由三點（完整說明見
`src/PostSeed.gs` 檔頭）：(1) `ConfigSeed.gs`／`SelfTest.gs` 都假設
Config 係一份固定已知嘅 Key 集合，逐一列出、逐一自我檢查完整性——崗位
數量會隨季度調整，動態 Config Key 會令呢兩份「固定清單」失效；
(2) Posts 工作表本來就係「逐崗位設定」嘅資料結構，已經有
`EmptyDisplay`／`AllowConsecutive` 呢類前例，`EarlyArrivalMinutes` 係
同一個模式嘅延伸；(3) 對 Ivan 嚟講「呢個崗位要提早幾多」同「呢個崗位
留空點顯示」係同一類決定，放喺同一份表更直覺。全域嘅預設崇拜時間
（`ICS_SERVICE_START_TIME`／`ICS_SERVICE_END_TIME`）仍然留喺
Config——嗰個係「一個」值，符合 Config 原本用途。新增
`維護 ▸ 補建 Posts 欄位（提早到場分鐘數）`，跟現有「補建 Posts 欄位」
一樣嘅 plan→confirm→execute 樣式，欄不存在先新增、只填空格唔覆寫，
填嘅預設值一律 0（唔提早），要 Ivan 自己再改成需要嘅分鐘數。

格式要求全部落實（`tests/ics_calendar.test.js` 41 項全過）：

- 每個服侍安排一個 `VEVENT`；`UID` 由「季度+人+日期+崗位+slot」組成，
  **刻意唔含版本號**，保證同一個服侍安排跨版本重發時 `UID` 相同——日曆
  App 會更新舊事件而唔係新增重複事件。
- `SEQUENCE` 直接用 `versionNo`（版本號本身單調遞增，天然符合
  「SEQUENCE 遞增代表較新版本」嘅語意，唔使另外維護計數器）。
- `METHOD:PUBLISH`，`DTSTART`/`DTEND` 用 `TZID=Pacific/Auckland` 搭配
  本地時間字串（唔轉 UTC），`VTIMEZONE` 有完整 STANDARD／DAYLIGHT 定義
  （紐西蘭 2007 年後嘅 DST 規則）。
- 換行用 CRLF，長行（`DESCRIPTION` 呢類含中文嘅內容特別容易超過）用
  UTF-8 位元組數（唔係字元數）折行，符合 RFC 5545 每行 ≤75 octets 嘅規定。
- 附件 MIME type 用 `text/calendar`、副檔名 `.ics`，只喺 `OFFICIAL`／
  `RESEND` 兩個階段、收件人本季有派工時先附上；ICS 產生失敗**唔會**
  拖累個人 PDF 一齊寄唔出（獨立 try/catch，只記警告）。

### 階段 D：Web UI 深色/淺色切換

幹事介面加咗一個切換掣，用 CSS 變數實作（`:root` 淺色基準 +
`:root[data-theme="dark"]` 手動深色 + `@media (prefers-color-scheme:
dark)` 加 `:not([data-theme="light"])` 防護，令手動選擇一定贏裝置設定），
**冇寫兩套樣式**。偏好記憶策略：優先用瀏覽器 `localStorage`（同步、免
來回伺服器），只有讀寫失敗（例如 sandbox 擋咗）先退回新增嘅
`apiGetThemePreference()`／`apiSetThemePreference()`（`WebApp.gs`，用
`PropertiesService.getUserProperties()`）——兩種都實作咗，本輪冇辦法
喺真實 HtmlService sandbox 實測邊一種真正會觸發。義工用嘅個人專屬連結頁面
（階段 B）本身喺上一節已經預設淺色、唔跟裝置設定，呢個決定沿用不變。

### ⚠️ 階段 A（本輪最重要）：公開試算表版面完全轉置

**實測發現**：公開試算表原本係「日期做列、崗位做欄」——同教會現行職事表
（崗位在左、日期在頂）方向**完全相反**；而且欄闊唔夠，姓名全部截斷成
「潘秀…」「陳庭…」，義工要橫向捲動先搵到自己。呢個係全體義工唯一會睇到
嘅畫面，做唔啱等於整個功能白做。

**修正**：新增純函式 `transposeRosterForPublicView_()`（`RosterWriter.gs`），
把 `buildGridLayout_()` 產生嘅 date-major grid（唔改動——`Roster_XXXXTX_vN`
工作表、生成器、PDF 匯出全部繼續用返舊有嘅日期做列版面，本輪絕對冇碰）
轉置做 post-major：

- **崗位喺左欄**（凍結），多 slot 嘅崗位（司事、司數各 2 個 slot、聖餐
  襄禮 4 個 slot）逐 slot 展開成獨立列，崗位名稱垂直合併（`isFirstSlot`
  旗標決定邊一列輸出名稱、`slotCount` 決定合併幾多列）；
- **日期喺頂列**（凍結），`buildMonthGroups_()` 按月分組、月份標題橫跨
  該月嘅日期欄；特別主日名稱（「浸禮」「堂慶合堂」）顯示喺日期下方
  （同一格內第二行，唔另開一行 header）；
- 欄數固定喺「幾多週 + 1」（通常 13＋1＝14 欄），唔會再因為崗位／slot
  數量增加而越嚟越闊；
- 日期欄用**固定欄闊 130px**（`PUBLIC_ROSTER_DATE_COLUMN_WIDTH`）而唔淨係
  `autoResizeColumns()`——足夠容納中文姓名最長 6 字（例如「黃余麗貞師母」），
  亦唔會因為下一版換咗個較長嘅名又被截斷；
- 試算表版本凍結首欄＋首 3 行（標題／月份／日期）；
- 個人專屬連結頁面（`ui/PersonalRoster.html`）同步轉置，用 CSS
  `position: sticky` 令崗位欄喺手機橫向捲動時保持喺左邊可見。

底色邏輯抽成單一入口 `resolveGridCellBackground_()`（`RosterWriter.gs`），
`computePublicRosterBackgrounds_()`（舊版、date-major 用）同新嘅轉置路徑

### ⚠️ 階段 A：七個實測問題逐一修正

**A1／A2 根本原因其實係同一個**：`writePublicRosterContent_()`
（`PublicRoster.gs`）原本嘅標題列（第 1 行）合併咗**全部 14 欄**，但
凍結範圍得返首欄——呢個係程式本身內部自相矛盾，第一次發佈時就應該
出事，但因為 Google Sheets 嘅合併／凍結檢查係按「執行時嘅工作表狀態」
判斷，第一次執行喺一張全新工作表上兩個操作嘅次序啱好冇撞到；第二次
發佈時，`sheet.clear()`（Google Sheets API 一個容易被誤解嘅行為，
**唔會**解除合併、唔會歸零凍結列／欄數，只會清內容同格式）令上一次
執行遺留低嘅合併同凍結狀態同今次即將寫入嘅新合併狀態互相衝突，於是
拋出兩個唔同嘅真實 Google 錯誤：

- 第二次發佈：`"You can't merge frozen and non-frozen rows."`（A1）
- 標題橫跨全部欄但只凍結一欄嗰個結構性衝突本身：
  `"Sorry, you can't freeze columns which contain only part of a merged cell."`（A2）

**修正**：新增共用 helper `resetSheetToBlankSlate_(sheet)`
（`Utils.gs`）——`setFrozenRows(0)` → `setFrozenColumns(0)` →
`breakApart()`（解除全部合併）→ `clearDataValidations()` → `clear()` →
`clearNotes()` → `clearConditionalFormatRules()` → 縮到 1×1，作為**任何
重寫已存在工作表之前必須執行嘅第一步**；並且將標題列改成完全唔合併
（單一格，靠 Sheets 對空鄰格嘅自然文字溢出顯示全文），徹底移除呢個
結構性矛盾嘅源頭，唔使再喺「合併」同「凍結」兩者之間搵妥協。

**A3（欄闊完全冇套用）**：根本原因係 A2 嘅例外中斷咗函式執行，欄闊
程式碼永遠冇機會行到。修正 A1／A2 之後自動解決，但本輪同時重整咗
操作次序，改成固定四步、每步之間唔再互相依賴執行成功與否：
**還原 → 寫內容（零合併）→ 合併 → 欄闊／列高 → 凍結（一定最後）**。
呢個次序本身寫成規範記錄喺新文件 `docs/GoogleSheetsAPI限制.md`（見
階段 C1）。

**A4（日期顯示成「3.0」）**：根本原因係 Google Sheets 對睇落似數字嘅
字串會自動轉型做數字（`setValues()` 寫入「3」呢種純數字字串，讀出嚟
會變成數字 3，格式化顯示就可能出現「3.0」）。修正：`formatShortDateLabel_()`
改用可配置嘅樣式字串（`{M}`／`{d}` token 代入），預設 `'{M}月{d}日'`
（例如「1月3日」）——**只要格式入面有非數字字元，Sheets 就唔會誤判做

`'{M}月{d}日'`）、`PUBLIC_ROSTER_BLANK_NOTE`（見 A6），兩個都已登記喺
`ConfigSeed.gs`。

**A5（殘留 24 欄舊版面）**：`resetSheetToBlankSlate_()` 縮到 1×1 之後

### 階段 A：獻花與翻譯兩列的說明文字過度重複

**問題**：上一輪為 BLANK 類崗位（獻花、翻譯）加嘅說明文字，實作成
「每一格都寫一次」——13 個日期欄 × 2 列 = 26 格全部重複同一句十幾字嘅
說明，唔單止畫面嘈吵，仲會令儲存格文字換行、拉高成行嘅列高，令表格
睇落無啦啦變闊變高。

**修正**：改為完全唔喺格內寫任何文字（留返自然嘅空白，同幹事介面一致），
說明改成**喺圖例加一行**（新增 `buildBlankRowLegendEntry_()`，
`RosterWriter.gs`）——標記用「（空白）」（同圖例既有「（姓名）」一致，
係描述性標記，唔係逐字複製格內容），意思欄用原本嗰句說明文字（沿用
`PUBLIC_ROSTER_BLANK_NOTE` Config，保持可配置），格數欄準確統計實際
留空幾多格。

**判斷理由**（「只在該列第一格寫一次」vs「完全不在格內寫，只在圖例
解釋」二選一）：選咗後者。前者（第一格寫）嘅風險係義工可能誤會「第一
個日期欄有咩特別」，因為淨係嗰一格有文字、其餘格空白，睇落唔一致；
後者完全唔喺資料區留任何文字，同幹事介面嘅顯示邏輯完全一致，說明集中
喺圖例一次過講清楚，冇任何一格會俾人誤解。

### ⚠️ 階段 B1：合資格人選用聯集定交集？——**聯集，再加硬規則收窄**

路徑都有跑。池做日期過濾反而要知道「邊一季」，三條路徑各自傳一次季度
資訊，多咗出錯機會而冇任何好處。

### ⚠️ 階段 B：兩個「靜靜失效」嘅陷阱（本輪最危險嘅兩點）

**陷阱一：規則級別跌做 SOFT。** `makeViolation_()`（Generator.gs）同
`findStateViolations_()` 嘅 `add()`（FineTune.gs）兩處本來都係
`rule[LEVEL] || RULE_LEVELS.SOFT`——即係**規則喺 `RuleSettings` 冇一列就
當 SOFT**。對舊規則冇問題（佢哋全部預期幹事已經有一列），但對兩條新硬
規則係致命嘅：生成器排除候選人嘅條件係 `violations.some(v => v.level === HARD)`，
跌做 SOFT 就變成「只扣 10 分」，一個唔係堂委嘅人照樣排得到做報告，
**而且畫面上完全睇唔出有嘢唔妥**。修正：新增 `RULE_DEFAULT_LEVELS` map，
兩處 fallback 改為先查呢個 map（其餘規則行為完全不變）。

**陷阱二：規則預設停用。** 沿用「冇登記＝停用」嘅話，幹事補建咗工作表、
填好名單、填好 `RequiredRoles` 之後規則仍然唔生效，而且冇任何地方會提示
佢仲差一步去 `RuleSettings` 加一列。修正：新增 `RULE_DEFAULT_ENABLED` map
同 `isRuleEnabledAllowingDefault_()`，兩條新硬規則預設啟用——因為佢哋真正
嘅開關喺資料本身（`Posts.RequiredRoles` 有冇填、`PersonPostExclusions`
有冇列），冇資料就完全冇影響，所以預設啟用係安全嘅。幹事仍然可以明確
填 `Enabled=FALSE` 停用。

兩個陷阱都有專門嘅回歸測試鎖住（`tests/role_hard_rules.test.js` 嘅
「安全網」一節）。

### 階段 A：身分規則影響預估（唯讀）

新增 `查看 ▸ 身分規則影響預估（唯讀）`（`src/RoleImpact.gs`）。逐個
`AutoGenerate=TRUE` 嘅崗位列出：套用規則前後嘅人數、本季需要格數、
每人平均次數、可行性判斷、被剔走同新加入嘅人（**只顯示 PersonID**）。

**設計上最重要嘅一點：唔可以另寫一份平行嘅收窄邏輯。** 呢個工具嘅全部
價值就係佢講嘅嘢同生成器實際會做嘅一致；兩份邏輯遲早分岔，而分岔嗰陣
呢個工具就會靜靜噉講大話，幹事信咗佢去做決定反而**比冇呢個工具更差**。
所以 `computePostAvailability_()`（`Roles.gs`）唔自己判斷任何規則，
只係將生成器逐格逐日用緊嘅同一批 predicate 喺成季掃一次：
`personHasAnyRoleOn_()`／`findActivePersonPostExclusion_()`／
`isPersonUnavailable_()`／`getSkipReason_()`。

**額外加咗一個指標 `usableSlotCount`**（全部人可服侍主日數嘅總和）。
起因：單睇「候選池有幾多人」會過分樂觀——一個人如果只喺其中兩三週
先合資格（例如季中先上任），佢一樣計入池，但實際幫唔到幾多格。
`usableSlotCount` 係「本季最多填得到幾多格」嘅硬上界，直接同需要嘅格數
比，捉得到「人數睇落夠但個個都只得幾週得閒」呢種情況。

### ⚠️ 階段 B：主席兼報告嘅理論上限（本輪最需要想清楚嘅一點）

**問題**：`SOFT_CHAIR_EQ_ANNOUNCE` 目標 63%。身分規則收窄咗報告候選池
之後，同時具備兩個崗位資格嘅人可能得返幾個——嗰陣「軟規則實測量度」
會年年報「偏低」，而幹事冇辦法分辨「排得唔好」同「規則造成嘅天花板」。
後者調高目標值唔會改善，只會多咗一個永遠達唔到嘅數字。

**推導**（見 `computeChairAnnounceUpperBound_()`，每步都係必要條件）：
① 每個兼任週只歸屬一個人 → 總數 ＝ Σ 各人兼任週數；
② 每週最多一個兼任週 → ≤ `W`；
③ 某人嘅兼任週必然落喺佢「兩個崗位都用得着」嘅週 → ≤ `|A_d|`；
④ 任一崗位 `AllowConsecutive=BLOCK` → 兼任週唔可以連續 →
≤ `A_d` 嘅最大非連續子集（每段連續 `L` 週最多取 `ceil(L/2)`）。
**上限 ＝ min(W, Σ cap_d)**。

**點解要出兩個數字**——呢個係本輪最容易含混過去嘅地方，所以寫清楚：

`SEMI_NO_CONSECUTIVE` 係 **SEMI_HARD 唔係 HARD**。生成器排除候選人嘅
條件係 `level === HARD`，所以第 ④ 點嘅限制**唔係絕對保證**，生成器只係
重扣分（1000）而理論上仍然可以違反。如果淨係出一個含第 ④ 點嘅數字，
就等於偷偷把一個「假設」當成「保證」講畀幹事聽。所以報告同時出：

- **理論上限**（①–④）：較緊、實務上有參考價值；
- **絕對上界**（①–③）：只用 HARD 級別限制，**任何情況下都唔會低估**。

而且明確寫低：實測值高過理論上限**唔係計錯數**，而係代表準硬規則被
放行咗，報告會直接噉樣講並指去睇連續兩週嘅明細。

**刻意唔用每季次數上限**：`SOFT_MAX_PER_QUARTER` 係 SOFT 級別，超額只
扣分唔會擋。用咗佢會令上限變成**可能低估**——即係唔再係一個安全嘅上界，
反而會製造「實測超過上限」嘅假警報。呢個取捨寫咗喺函式註釋同
`docs/排表規則.md`。

**B2 點解改成「跟上限比」而唔係「跟基準比」**：歷史基準 63% 係喺**冇身分
規則**嘅年代由 78 週歷史算出嚟嘅，佢描述嘅係一個已經唔再存在嘅世界。
規則改變咗結構之後，仍然攞佢做判斷準則，等於永遠報一個唔可行動嘅
「偏低」。跟上限比先至答到真正有用嘅問題：「喺呢一季嘅結構之下，
排得好唔好？」上限算唔到嗰陣（規則未設定等）自動退回跟基準比，
維持加入呢一項之前嘅行為。

**B4 驗證方式**：用 48 個情境（雙重合資格人數 × BLOCK 與否 × 週數 ×
seed）**真正跑 `buildRoster_()`**，逐次數返實際兼任週數同上界比。
靜態檢查證明唔到「上界唔會低估」，只有真正生成先證明得到。

寫呢個測試嗰陣撞到一個值得記低嘅陷阱：**頭 48 個情境全部 0 兼任週**，
令「實際 ≤ 上界」變成一個永遠通過嘅空殼斷言。追查後發現係 fixture 漏咗
`SOFT_CHAIR_PREFER_DUAL`——冇佢嘅話主席嗰格會揀歷史次數最高嘅人，而嗰個

「本週主席唔喺報告候選名單」就一律回傳 0，兼任永遠發生唔到。所以測試
額外加咗一個「合計兼任週數 > 0」嘅斷言，防止同類空殼再出現。

## 第十八輪批次（2026T4 v0 生成之後）：修「缺失被當成有意義值」bug class

本輪唔係加功能，係修一個 **bug class**。起因：Ivan 用「參數掃描」同
「軟規則實測量度」兩個工具核對同一個 2026T4 v0，發現兩個工具講緊唔同
嘅嘢——參數掃描話有 26 項硬規則違反，但實際生成報告係 0 項。追落去
搵到嘅唔係一個 bug，係一種**寫法**。

### 一、bug 本身（階段 A1）

`src/Tune.gs` 嘅 `countHardViolations_()` 手砌一個 `verifyContext`
交畀 `checkHardRuleViolations_()`，但冇放 `roles` 同
`personPostExclusions` 兩個欄位。

被呼叫嗰邊係噉寫：

```js
const roles = context.roles || [];          // ← 問題喺呢一行
```

`undefined || []` ⇒ `[]`。於是 `personHasAnyRoleOn_([], personId, ...)`
對**每一個人**都回傳 false ⇒ 每一格有身分要求嘅崗位都算違規。
2026T4 有 13 個 ANNOUNCE 格同 13 個 DEACON 格，13 × 2 = **26**——同
Ivan 喺參數掃描見到嗰個數字一模一樣。

修法：`countHardViolations_()` 由**同一個** `context` 直接轉發兩個欄位
（嗰個 context 本身係 `buildGeneratorContext_()` 產生，入面已經係
`buildRoleContext_()` 讀好嘅資料），唔好另外再讀一次工作表。

### 二、真正要根治嘅係個 bug class（階段 A2）

上面嗰行 `|| []` 表面上係「防呆」，實際上做緊一件好壞嘅事：
**將「呼叫者冇話畀我聽」呢個「唔知道」，靜靜咁翻譯成「我知道，答案係
冇人」呢個確定嘅值——而且係最壞嗰個方向。**

兩件事語意完全唔同：

| 值 | 語意 | 應該點處理 |
|---|---|---|
| `[]`（空陣列） | 「確實冇任何身分資料」——例如 `Roles` 工作表未建立 | **合法**，照跑，冇人有身分 |
| `undefined` | 「呼叫者根本冇傳」 | **唔合法**，應該即刻爆 |

`|| []` 將兩者壓成同一個，所以第二種情況會**靜靜咁跑出一個錯嘅答案**，
冇 log、冇警告、冇 exception——只係報告數字錯咗。

#### 揀嘅做法：喺型別層面分辨，缺欄位直接拋錯

新增 `requireRoleContextField_(context, fieldName, callerName)`
（`src/Roles.gs`）：

- 係陣列（包括空陣列）⇒ 照回傳，舊有「真係冇資料」嘅情境完全唔受影響
- `undefined`／`null`／唔係陣列 ⇒ **拋錯**，錯誤訊息講明：
  - 缺咗邊個欄位、邊個函式要用
  - 收到嘅實際值係咩
  - 空陣列同 undefined 語意點解唔同、當成空陣列會出咩事（連 26 呢個
    實際數字都寫咗落去）
  - 應該去邊度攞返（`buildRoleContext_(...).roles` / `.exclusions`），
    同埋「唔好填 `[]` 敷衍過去」

#### 點解唔揀其他做法

| 做法 | 唔揀嘅理由 |
|---|---|
| 靠 code review／註釋提醒 | 呢個 bug 本身就係 review 睇唔出嘅——加咗個 `\|\| []` 睇落好似仲穩陣咗 |
| 預設值改成 `null` 再逐處檢查 | 檢查責任又推返去每個呼叫端，漏一個又中招 |
| 靜靜咁 log warning | 報告照樣出錯數字，Ivan 唔會見到 log |
| 喺 builder 加 assertion | 攔唔到「唔經 builder、自己砌 context」呢個情況——今次就係噉 |

拋錯係唯一一個**唔可能被忽略**嘅方向。代價係：如果有呼叫端一路以嚟
靠緊 `|| []` 過骨，改完之後會即刻爆——呢個正正就係想要嘅效果，
而且下面份表證明咗真係搵到咁嘅呼叫端。

### 四、階段 B：`CHAIR_DUAL_BONUS` 冇效果係點解

現象：同一個 `WEIGHT_HISTORICAL` 之下，`CHAIR_DUAL_BONUS` 由 30 加到 75，
六項指標四位小數一模一樣。

**先攞證據，後落結論**（第十五輪嘅教訓）。加診斷之後證實：參數係**有**
接駁到評分路徑嘅（`runTuneCombo_()` 有注入、`computeChairPreferDualBonus_()`
有讀、一次 run 入面觸發咗 63 次）。所以唔係「冇生效」。

真正原因係**飽和**。評分係
`score = penalty − bonus − selectionScore × selectionWeight`，
呢個 bonus 係**固定加分**。一旦佢大過候選人之間
`selectionScore × selectionWeight` 嘅最大差距（`selectionWeight = 45`，
`selectionScore` 正規化 0–1，實際差距約 20–25），所有雙重合資格嘅人
已經穩定排喺最前，再加大改變唔到次序。**呢個係門檻型參數，唔係連續型。**

實測（13 週 × 60 人、同一 seed）：

| CHAIR_DUAL_BONUS | 用人數 | 兼任週數 | 同上一個值比較 |
|---|---|---|---|
| 0–10 | 43 | 0 | 冇分別（加分太細，壓唔過選人分數差距）|
| 15 | 43 | 6 | **有分別** |
| 20 | 45 | 7 | **有分別** |
| 25 | 45 | 5 | **有分別** |
| 30／45／60／75／150／500 | 45 | 5 | **完全冇分別**（已經飽和）|

舊 grid `[30, 45, 60, 75]` **四個值全部落喺飽和區**——所以 12 行報告
先會一模一樣。呢個唔係 bug，係 grid 揀錯咗範圍。

兩項處理：

1. `TUNE_GRID.CHAIR_DUAL_BONUS` 改成 `[0, 10, 15, 20, 25, 30]`
2. 報告會**自己偵測飽和**：`buildTuneSaturationNotes_()` 見到同一個
   `WEIGHT_HISTORICAL` 之下所有 `CHAIR_DUAL_BONUS` 嘅指標簽名一樣，
   就喺結果下面加一段「⚠️ 參數敏感度提示」，講明係邊個參數、邊個範圍、
   點解會噉（門檻型）、同埋可以點做（試更細嘅值）

### 六、階段 D：commit 前敏感資料掃描

呢個 repo 係 public，已經洩漏過兩次。之前個流程係 **push 咗之後**先由
對話端掃描——即係發現嗰陣已經公開咗，攔唔到。本輪將關卡搬去
**commit 之前**：`tools/scan-staged-secrets.js`，掃 `git diff --cached`，
`node` 直接跑得，唔使裝嘢。

四類偵測，兩種嚴重度：

| 類別 | 嚴重度 | 做法 |
|---|---|---|
| 電郵 | HIGH（擋 commit）| 排除 RFC 2606 保留網域、本專案假資料慣例網域、`git config user.email` |
| 網域 | HIGH | **反白名單**：只列「安全樣式」，其餘一律可疑 |
| PersonID | HIGH | `P9xxx` 放行（本專案假 ID 慣例）；同一行有「例如」等格式示範字眼亦放行 |
| 中文姓名 | MEDIUM（**只提示**）| 姓氏 + 1–2 個漢字嘅樣式配對 |

#### 設計取捨（逐項講清楚）

**（a）反白名單，唔係黑名單。** 掃描規則入面**唔可以寫真實網域／姓名**
——喺一個防洩漏嘅檔案入面寫低要防嘅嘢，本身就係洩漏。所以只列安全樣式
（RFC 2606 保留網域之類），其餘全部當可疑。
代價：新嘅公開技術網域要人手加入白名單。

**（b）PersonID 靠 `P9xxx` 慣例分辨。**
盲點：**一個真實 PersonID 如果啱啱好係 P9 開頭，會漏。**
緩解：分配真實 ID 嗰陣避開 P9 段。呢個係已知、已寫低嘅限制。

**（c）中文姓名只提示、唔擋。** 姓氏樣式配對一定有誤判。設計成擋嘅話，
第一次誤判之後就會有人用 `--no-verify` 繞過，個關卡即刻等於冇。
所以呢一項係「幫人肉眼掃描縮窄範圍」，唔係保證。

**（d）真正嘅保證嚟自另外兩層**：`.gitignore` 白名單制（預設擋晒，
逐項放行）＋ `tests/scan_sensitive.test.js`（外部參考檔交叉核對）。
呢個 script 係第三層，唔係唯一一層。

#### 實作途中撞到、值得記低嘅三件事

1. **網域樣式撞正 JS 屬性存取。** `word.word` 呢個形狀會中
   `sheet.getRange`、`process.argv`、`module.exports`——第一次自我掃描
   報咗 39 個「網域」，全部係 JS 語法。加咗「一定要係真實頂層網域」
   之後解決。但**唔可以用兩個字母泛指國碼**，否則 `parsed.ok` 又中招；
   改用明確國碼清單。
2. **漢字邊界 lookaround 令姓名偵測完全失效。** 中文行文入面姓名前後
   幾乎一定係中文字（「今次由陳大明負責」——`陳` 前面係 `由`），
   加咗任何一邊嘅負向邊界就一個都捉唔到，而測試表面上仍然
   「冇誤報」，睇落好似正常。係自己寫嘅**正向**測試先揭穿。
3. **中文檔名令檔名／行號報錯地方——而且係同一個 bug class。**
   git 預設 `core.quotepath=true`，非 ASCII 路徑嘅檔頭會變成
   `+++ "b/docs/\347..."`——**個引號喺 `b/` 前面**，所以
   `startsWith('+++ b/')` 唔中。原本嘅寫法會**靜靜咁沿用上一個檔名**，
   結果 `docs/系統範圍稽核.md` 入面 22 項提示全部報成喺 `.gitignore`
   嗰度、行號 3428——而 `.gitignore` 得 80 行。呢個 repo 幾乎全部文件
   都係中文檔名，中招範圍唔細；如果嗰啲係高風險項目，人手去追會撲空，
   D2「列出檔案同行號」呢個要求就等於冇做到。

   **同階段 A 係同一種錯**：一個「我認唔到／我唔知道」被當成一個有意義
   嘅值（上一個檔名）。所以修法都一樣——`-c core.quotepath=false` 治本，
   加上「認唔到嘅 `+++` 檔頭一律拋錯，唔准沿用上一個」治那個 bug class。
   解析邏輯亦抽咗做純函式 `parseStagedDiff()` 令佢測得到。

4. **掃描器擋住自己個測試檔。** 測試要有「應該被捉到」嘅假網域樣本，
   但寫成完整字串就會被自己擋住。兩個唔好嘅解法都拒絕咗：改用
   保留網域（等於冇測到偵測能力）、將測試檔加白名單（開咗個永久盲點）。
   採用**執行時拼接**——而且每一段碎片都唔可以自成一個合法網域。

姓氏表入面有一批字同時係中文高頻構詞成分（何、方、連、程、白、高、紀）。
第一版掃 15 個檔案出咗 80 項提示，其中六成係「任何」「方法」「連續型」

### 一、階段 A1：先攞證據

Ivan 嘅判斷係「偵測器由 grid 文字反推 PersonID，遇到唔係人名嘅顯示文字
就一律當成認唔出嘅人手改動」。逐項核實：

**證據一**：`GRID_PLACEHOLDER_TEXTS`（`Constants.gs`）係
`['待確認', '另行安排', '-', '—', '－', 'N/A', 'n/a']`
——**冇包含「特殊主日」**，亦冇包含任何 `ExternalOwner` 值。

**證據二**：「特殊主日」四個字嚟自 `DEFAULTS.GRID_SPECIAL_SKIP_LABEL`，
由 `resolveGridCellText_()`（`RosterWriter.gs`）寫入 grid。
而且如果 `SpecialSundays.ExternalOwner` 有填，顯示嘅係「英語堂」
呢類**幹事自由輸入**嘅字串，唔係「特殊主日」。

**證據三**：舊嘅比對邏輯係
`normalizeCellText_(gridText) === normalizeCellText_(a.personName)`。
合堂格嘅 `personName` 係空字串 ⇒ 正規化後 `''`；grid 顯示「特殊主日」
⇒ 正規化後仍然係「特殊主日」（因為唔喺 placeholder 清單）。
兩者唔等 ⇒ 當成人手改動 ⇒ `resolvePersonId('特殊主日')` 失敗
⇒ 入 `unresolved` ⇒ 整批拒絕。

**結論：Ivan 嘅判斷完全正確**，而且機制比佢講嘅更差一層——
`ExternalOwner` 係自由輸入，所以「加白名單」呢條路根本行唔通。

### 二、階段 A2：改變偵測方向

#### 點解唔用白名單

最快嘅做法係把「特殊主日」加入 `GRID_PLACEHOLDER_TEXTS`。
但噉樣**下次多一種顯示文字又會再中**——「英語堂」「華語堂」
「青年崇拜」……`ExternalOwner` 係幹事自由輸入嘅，列唔完。
呢個係補鑊，唔係修理。

#### 採用嘅做法

**由 `RosterAssignments` 算出「呢一格本來應該渲染成咩」，
再同 grid 實際內容比對。相等就唔係人手改動。**

噉樣「特殊主日」對「特殊主日」自然相等，「英語堂」對「英語堂」
自然相等，**唔需要任何白名單**——因為兩邊都係同一個渲染器出嚟。

新增 `renderExpectedGridText_()`（`RosterWriter.gs`），
內部呼叫 `classifyGridCell_()` ＋ `resolveGridCellText_()`
——即係寫 grid 嗰陣用嘅**同一段程式碼**。

⚠️ **唔可以自己複製一份渲染邏輯。** 兩份平行邏輯遲早分岔，
分岔嗰陣呢個工具就會講大話（明明冇改動都話有）。第十八輪階段 C
已經因為同類問題食過一次虧。測試有斷言鎖住呢一點：
`renderExpectedGridText_()` 入面唔准出現任何硬寫嘅顯示文字。

#### 配套改動

`context.original` 本來冇帶 `ruleFlags`，而 `classifyGridCell_()` 要靠佢
先分得出 `SPECIAL_SKIP`／`STRUCTURAL_NA`／`MANUAL_PENDING`／`GENUINE_GAP`
——所以 `buildFineTuneContext_()` 補讀咗呢一欄，另加一個
`gridRender`（顯示標籤、逐崗位 `EmptyDisplay`、逐日期 `ExternalOwner`）。

`gridRender` 冇傳會**拋錯**，唔會靜靜咁退回舊做法——同第十八輪
`requireRoleContextField_()`、第十九輪 `resolveAuthoritativeState_()`
係同一套做法。呢度特別重要：靜靜退回嘅話，個 bug 會復活，
而且**淨係喺有合堂嘅季度先出現**，最難察覺嗰種。

#### 第二道防線，同埋差啲喺度種返一個 bug

除咗渲染比對，仲加咗一句「解析到嘅人同原本一樣 ⇒ 唔算改動」。

⚠️ 呢一句嘅**第一版寫錯咗**：`resolvedId === (a.personId || '')`。
噉樣寫嘅話，一個空格入面打錯字（解析唔到 ⇒ `resolvedId = ''`，
而原本亦係 `''`）就會被當成「冇改動」，**幹事打咗嘅嘢憑空消失而且
冇任何提示**——正正就係第十八輪嗰個 bug class（缺失被當成有意義嘅值）。
改成 `resolvedId && resolvedId === a.personId`（要求非空），
另加一句「空白對空白」單獨處理。測試有專門一節鎖住呢個情境。

### 八、誠實嘅部分：點解 61 個測試全 PASS 都捉唔到

**直接原因：fixture 冇特殊主日。**

`tests/state_source_authority.test.js`（第十九輪為咗鎖住 grid 疊加而寫）
用嘅 fixture 只有兩格 CHAIR，兩格都有派人。冇合堂、冇 `ExternalOwner`、
冇結構性不適用、冇「待確認」。於是**成個「placeholder」呢類情境
喺測試入面根本唔存在**。

更深一層：測試係我根據「我以為呢個函式要處理嘅情況」而寫嘅，
而我當時嘅心智模型就係「grid 格入面係人名」。**一個由錯誤前提寫出嚟
嘅測試，唔會揭穿嗰個前提。**

呢個同第十八輪嗰次（mock helper 自己都冇放 `roles`，於是測試同生產
程式碼犯同一個錯）係同一種失敗：**測試同被測程式碼共用同一個盲點。**

#### 而家點捉得到

1. `tests/grid_placeholder_roundtrip.test.js` 嘅 fixture **特登照住
   2026T4 真實情況造**：2026-10-04 合堂、領詩／司琴由英語堂負責，
   加上結構性不適用、留待人手填、排唔出、`EmptyDisplay=BLANK`
   六種情境全部齊
2. **A4 斷言**：冇人改過 grid ⇒ 必須報 0 格
3. **round-trip 斷言** ＋ 反證（渲染同解析對唔上就一定要報）
4. `gridRender` 冇傳會拋錯——退唔返去舊做法
5. 靜態掃描規則 6，有正向樣本證明捉得到

#### 仍然存在嘅缺口

- **離線 fixture 永遠只覆蓋到「我諗得到嘅情境」。** 呢一輪加咗六種
  placeholder，但下次多一種顯示形態（例如將來加一個「暫停服侍」標籤），
  fixture 又唔會有。
- 真正嘅防線唔係「再加多幾個 fixture 情境」，而係**渲染同解析共用
  同一份實作**——噉樣就算多咗一種顯示形態，兩邊都會同時知道。
  呢個係本輪最重要嘅結構性改動，比任何一個測試都值錢。
- 本輪嘅修正**一項都未喺真實環境驗證過**。`docs/選單實測腳本.md`
  B 段（特別係 B2b 嗰句「注意是 1，不是 3」）就係為咗呢個而寫。
