## 第二十一輪批次：硬規則違反三分類、自我測試目標、日期輸入收窄

2026-08-17 嘅實測發現三個工具各自報咗一項「睇落係 bug、其實唔係」嘅違反。
本輪核心係階段 A：**唔改判斷邏輯、唔改「必須處理」嘅門檻，只喺顯示層加分類。**

### 一、問題：三個工具各自把非 bug 叫做 bug

| 工具 | 報告內容 | 真實成因 |
|---|---|---|
| 核對職事表 | 「硬規則違反：1 項 ← 這是 bug，請查看報告」 | 幹事已經用打字「確認放行」放行咗，AuditLog 有紀錄，但工具唔讀放行紀錄 |
| 上線前檢查 | 「硬規則違反：6 項」 | 版本生成之後先落實嘅崗位身分要求（`Posts.RequiredRoles`），追溯判定 |
| 自我測試（測試 7）| 未通過，報違反 `Unavailable` | 版本生成之後先套用嘅申報寫入咗一行 `Unavailable`，追溯判定。嗰個版本喺生成當日完全合規 |

三個都唔係排表演算法出錯，但三個都用同一句「這是 bug」講出嚟。
**結果係真嘅 bug 同呢啲雜訊混埋一齊，睇報告嘅人分唔出。**

### 二、已否決嘅做法：按版本 `CreatedAt` 過濾規則與申報

曾經考慮「驗舊版本時，只用嗰個版本生成當日已經存在嘅規則同申報」。
**已否決，冇實作。**

理由：**向前看嘅檢查必須用今日嘅規則。**
如果某人今日已經唔係堂委，噉一張即將寄出嘅職事表把報告派畀佢就係真問題，
同呢份表幾時生成完全無關。按生成時間過濾，會喺**最需要示警嗰一刻**
把真問題藏起嚟——呢個正正就係本專案已經踩過三次嘅同一個 bug class：
**把「過時」或者「缺失」當成「冇事」**（第十八輪嘅 `|| []`、
第十九輪嘅兩個真相來源、第二十輪嘅顯示層反推）。

呢個否決連同理由已經寫入 `src/HardViolationClass.gs` 檔頭，
唔係淨係寫喺呢度——下次有人諗到同一個「好主意」嗰陣，
佢會喺程式碼度直接見到點解唔可以噉做。

### 三、實作：三分類

| 分類 | 判斷準則 | 會唔會觸發「需要處理」 |
|---|---|---|
| **真違反** | 按今日規則確實違反，而且冇放行紀錄 | ✅ **只有呢一類會** |
| **已放行** | AuditLog 有對應嘅「硬規則放行」紀錄 | ❌ |
| **版本生成後才新增的申報** | `Unavailable` 該行嘅 `CreatedAt` 晚過該版本嘅 `CreatedAt` | ❌ |

分類抽咗做一個純函式 `classifyHardViolations_()`（`src/HardViolationClass.gs`），
四個呼叫點共用：

| 呼叫點 | 點樣共用 |
|---|---|
| `Verify.gs` | 直接呼叫，報告第 5 節逐項標示分類 |
| `SelfTest.gs`（測試 7）| 直接呼叫，**真違反 = 0 即通過** |
| `PreLaunchChecklist.gs` | 直接呼叫，`ready` 只由真違反決定 |
| `FullHealthCheck.gs` | **消費上線前檢查嘅結果**，唔會自己再判斷一次——兩處各自判斷遲早分岔 |

#### 為咗做到呢件事而做嘅前置重構

`checkHardRuleViolations_()` 原本回傳嘅 `items` 係**一句字串**
（`2026-11-08 ANNOUNCE#1 某某：某某原因`）。只有字串就只可以靠訊息文字比對，
而訊息文字係會改嘅——第十七輪就改過一次違規訊息措辭，一改就會靜靜對唔上，
然後所有已放行嘅項目會變返「真違反」。

所以先把 `items` 改成**結構化物件**（`serviceDate`／`postId`／`slotIndex`／
`personId`／`ruleId`／`reason`／`text`），`text` 保留原本嘅顯示字串，
顯示層一個字都唔使改。

放行比對用完整六欄 key：`季度｜服侍日期｜PostID｜SlotIndex｜PersonID｜RuleID`。

#### 放行紀錄嘅寫入格式亦都改咗

`logHardViolationRelease_()` 原本只寫一句人類可讀嘅句子，入面**冇 PersonID**、
崗位可能係中文名。而家額外寫一段機器可讀嘅 key 清單（前綴 `RELEASED_KEYS:`）。

⚠️ 順帶修咗一個潛在 bug：舊版用 `slice(0, 10)` 只寫頭 10 項，
即係第 11 項之後嘅放行紀錄**永遠對唔返**——放行咗但認唔到，等於冇放行。
人類可讀嗰段仍然只列頭 10 項（`Notes` 欄要畀人睇），但 key 清單一項都唔少。

#### 舊格式相容層，同埋佢嘅代價

2026-08-17 嗰筆放行紀錄係舊格式寫嘅。三個選擇：

| 做法 | 問題 |
|---|---|
| 完全唔理舊紀錄 | 幹事之前做過嘅放行等於白做，要再放行一次 |
| 靠訊息文字模糊比對 | 正正就係要避免嘅嘢 |
| **解析已知格式，用縮減 key 比對**（採用）| 精確度較低，但係**確定性**解析，唔係模糊比對 |

縮減 key 係「服侍日期 ＋ RuleID」——呢兩個喺舊格式入面一定準確
（日期係系統寫、RuleID 係常數）。崗位同人名唔入 key，因為崗位可能係中文名、
人名可能有別名。

⚠️ **已知代價**：同一日、同一條規則、唔同崗位嘅兩項違反，
舊紀錄只放行咗其中一項嘅話，另一項都會被當成已放行。
呢個係舊資料本身資訊不足造成嘅，唔係做法揀錯。新格式冇呢個問題。

### 四、第 3 類嘅誠實界線（最重要嗰段）

**只有喺來源資料本身帶時間戳嘅情況下先可以歸入第 3 類。**

| 來源 | 有冇時間戳 | 可唔可以判斷 |
|---|---|---|
| `Unavailable.CreatedAt` | ✅ 有 | **可以** |
| `Roles.EffectiveFrom` / `EffectiveTo` | ✅ 有 | 現行按服侍日判斷嘅邏輯已經啱，**冇改** |
| `Posts.RequiredRoles` | ❌ 冇 | **唔可以** |
| `RuleSettings` | ❌ 冇 | **唔可以** |

⚠️ **冇為「規則定義幾時改」發明任何啟發式判斷。**

所以上線前檢查嗰 6 項按今日規則就係**真違反**，維持第 1 類、維持「需要處理」。
佢哋會喺重新生成嗰陣自然消失，嗰個先係正確嘅解法。

測試有專門一節鎖住呢條界線：即使畀一個「晚過版本」嘅時間戳，
規則類違反一樣要維持真違反。

另外三條界線亦都測咗：申報早過版本 ⇒ 真違反；讀唔到版本時間 ⇒ 真違反；
讀唔到申報時間 ⇒ 真違反。**判斷唔到嗰陣一律當真違反，唔可以靠估。**

（`Posts` 同 `RuleSettings` 加時間戳欄位嘅建議已寫入 `HANDOFF.md`，
本輪唔實作——會改動試算表 schema，超出範圍。）

### 五、摘要句：拿走「← 這是 bug」

原本：`硬規則違反：1 項 ← 這是 bug，請查看報告`

而家：
```
硬規則違反：3 項（真違反 1、已放行 1、版本生成後才新增的申報 1）
　其中 1 項需要在正式發出前處理，或明確放行。
```

真違反 = 0 嗰陣：
```
硬規則違反：1 項（真違反 0、已放行 1）
　沒有真違反——其餘各項是已知情況，不需要處理。
```

原本嗰句對三類項目一視同仁，而其中兩類根本唔係 bug。
**一句講錯嘅結論，比冇結論更差。**
測試有靜態斷言：`src/` 嘅輸出字串入面唔可以再有「這是 bug」。

### 六、階段 B：自我測試目標唔再寫死

`SELF_TEST_TARGET = { QUARTER_ID: '2026T4', VERSION_NO: 0 }` **已移除**。

兩個問題：

1. **寫死年份會過期。** 每過一季，自我測試就係喺驗一個舊季度。
2. **寫死 `VERSION_NO: 0`** 令佢永遠只驗初稿。初稿之後嘅版本
   （套用申報、人手改動）先係真正會寄出去嘅嘢，反而冇驗。

而家由 `resolveSelfTestTarget_()` 決定：季度讀 Config 嘅
`SELF_TEST_QUARTER_ID`（留空 = 最近一個有生成過版本嘅季度，所以唔會過期），
版本一律用**該季最新版本**。

設計取捨：Config 有設定但嗰季搵唔到版本嗰陣，**唔會靜靜跌返去另一季**
——噉樣會令人以為自己設定嗰季通過咗測試。直接當搵唔到，訊息叫人先生成。

### 七、階段 C：日期輸入收窄

`toDateString()` 接受 `dd/MM/yyyy`，即係 `05/06/2027` 一律當 **6 月 5 日**
——**無聲噉猜**，猜錯就係把人排錯主日。

而且原本嘅錯誤訊息寫「斜線、句點、日月倒轉、全形數字都認不出來」，
但實際上斜線同日月倒轉係收嘅——**訊息同行為唔一致**。
幹事照住訊息改，反而改到一個系統會靜靜猜錯嘅寫法。

#### 做法：分成兩個函式

| 函式 | 服務邊一邊 | 收咩 |
|---|---|---|
| `toDateString()` | **讀系統自己寫入嘅資料**（ServiceDates／RosterAssignments／Unavailable……）| 維持原狀，**唔可以收緊**——收緊會令既有資料讀唔到 |
| `parseOfficerDateInput_()`（新）| **幹事輸入**（Requests 日期欄）| 只收兩種：儲存格本身係 Date 物件、或者文字 `yyyy-MM-dd` |

兩個函式各自嘅 docstring 都寫明服務邊一邊，同埋點解唔可以混用。

#### 訊息同行為一致

新訊息只講兩種接受嘅寫法，並且解釋**點解**唔收斜線：
「不是認不到，是『05/06』這種寫法沒有辦法確定是 5 月 6 日還是 6 月 5 日，
猜錯就會把人排錯主日。」

測試有一節專門斷言：**訊息列為「不接受」嘅寫法，實際上真係唔收。**

而且「係咪格式問題」直接由文字判斷，**唔靠呼叫端傳參數**——
兩個地方各自講「乜嘢先算格式啱」就會分岔，而分岔嘅結果就係
「訊息同行為唔一致」，正正就係本階段要修嘅嘢。

#### 既有資料唔受影響

`Requests` 有一行歷史紀錄係 `2027/05/09`（2027T2，已 APPLIED）。
`readPendingRequests_()` 只讀 **RequestID 空白**嘅列，
已 APPLIED 嘅行有 RequestID ⇒ 根本唔會經過新嘅嚴格解析。
**冇改動試算表任何資料。**

#### 認唔到嘅日期唔會被靜靜略過

⚠️ 收窄之後有一個新風險：認唔到嘅日期如果當成空白 `return` 走，
就變成靜靜吞咗一筆申報。所以認唔到嘅照樣傳落去，由 `validateRequest_()`
報 `NEEDS_INPUT` 並寫明原因，令幹事喺驗證結果視窗見得到。測試有斷言鎖住。

### 八、階段 D：清走輸出字串裡的 literal `**`

Apps Script 嘅 `ui.alert()` **唔會渲染 markdown**。寫 `**這一步不能繼續**`
出嚟就係一堆星號。全專案有 **26 處**，分佈 17 個檔案，全部改咗。

改法唔係淨係刪走星號——噉樣句子會失去重點。改用「」或者全形括號，
或者把重點改寫成獨立一句（例如 `**這一步不能繼續**` → `⚠️ 這一步不能繼續`）。

⚠️ 註解同 `docs/` 入面嘅 markdown `**` **冇動**——嗰啲係畀人喺編輯器
／GitHub 睇嘅，會正常渲染。

新增 `tests/output_string_hygiene.test.js` 防回歸，而且有**正向樣本**
證明個規則真係捉得到（一條掃出 0 項嘅規則，可以係「真係冇問題」，
亦可以係「規則寫壞咗」，淨係睇個 0 分唔出——第十八、二十輪都食過呢個虧）。

順帶把 `ConfigSeed.gs` 同 `EmailTemplateSeed.gs` 都納入掃描範圍：
Config 說明會寫入試算表畀幹事睇、電郵範本會寄出去畀義工睇，兩者都係輸出。

### 九、階段 E：「清 Status 重新提交」係錯嘅

步驟 3／5 嘅確認視窗寫「之後可把該行 Status 清空重新提交」，
但 `readPendingRequests_()` 實際上係睇 **RequestID 係咪空白**
——清 Status 完全冇作用，照住做只會白做一次然後以為系統壞咗。

兩處都改成「刪除該行的 RequestID」，而且**主動講破**呢個誤解
（「清 Status 沒有作用，系統判斷的是 RequestID 是否空白」）——
單純刪走錯嘅講法唔夠，幹事可能已經記住咗舊做法。

全專案搜過同類講法：「清理 Requests 手改痕跡」工具嘅報告都提到清空 Status，
但嗰個係**描述系統做咗乜**（嗰個工具真係會清），準確，冇改。
測試嘅掃描規則亦都相應收窄，只掃「叫幹事去做」嗰種講法。

### 十一、誠實嘅部分

**呢三個問題全部係「工具講錯嘢」，唔係系統做錯嘢。**
2026T4 v1 嗰項違反本來就已經被幹事知情放行；2027T1 嗰 6 項按今日規則
確實係真違反（重新生成就會消失）；自我測試嗰項係版本生成之後先出現嘅申報。
排表演算法由頭到尾都冇做錯。

但**工具講錯嘢嘅代價唔細**：幹事見到「這是 bug」，唯一合理反應就係
去追一個唔存在嘅 bug。呢一輪嘅價值就係令佢唔使再追。

**仍然存在嘅缺口**：

- 第 3 類只覆蓋到 `Unavailable`。`Posts.RequiredRoles` 同 `RuleSettings`
  冇時間戳，所以「規則幾時改」永遠判斷唔到——本輪**刻意冇為呢個發明
  啟發式判斷**，寧可維持真違反（誤報）都唔要漏報。
- 舊格式放行紀錄嘅相容層精確度較低（同日同規則唔同崗位會一齊當成已放行）。
  新格式冇呢個問題，但舊紀錄會一直存在。
- 本輪嘅修正**一項都未喺真實環境驗證過**。`docs/選單實測腳本.md` 嘅
  E1／E1b 就係為咗呢個而寫。

### 十三、附記：一個測試套件結構上嘅盲點

### 一、階段 A：一個新嘅 bug class——Google 試算表自動正規化污染 Config 文字值

#### 症狀

「正式發出」寄出嘅**每一份**個人 ICS 月曆附件，`DTSTART` 都係
`NaNNaNNaNTNaNNaN00`——即係義工加入日曆嘅事件時間全部係壞嘅。

#### 成因鏈

Config 嘅 `ICS_SERVICE_START_TIME` 打咗 `10:45` 落去，**Google 試算表
自動判斷佢係時間值**，儲存格實際存嘅係一個 Date 物件
（`Sat Dec 30 1899 10:45:00 GMT+1130 (…)`），唔係文字 `10:45`。

| 步 | 發生咩事 |
|---|---|
| `convertConfigValue_()` 嘅 `default` 分支 | `String(rawValue).trim()` ⇒ 成串英文長格式 |
| `shiftIcsLocalDateTime_()` 嘅 `split(':')` | 拆成三段亂嘢 |
| `.map(Number)` | `[NaN, 45, NaN]` |
| `Date.UTC(y, m, d, NaN, 45)` | `NaN` |
| `new Date(NaN)` → 輸出 | `NaNNaNNaNTNaNNaN00` |

**壞值由頭到尾冇任何一步擋過，一路流到寄出嘅附件入面。**

#### 點解 62 個離線測試一個都捉唔到

**佢哋全部餵乾淨字串 `10:45`。試算表真正俾嘅係 Date 物件。**

呢個係本輪最值得記住嘅一句：

> **有測試 ≠ 能用。寫測試時要問：這個測試餵的資料，跟試算表真正會給的一樣嗎？**

#### 修法

| # | 改動 |
|---|---|
| A1 | 新增 `normalizeTimeOfDay_(value, fallback, timezone)`（`Utils.gs`）。Date ⇒ `HH:mm`；文字 ⇒ 補零；空白 ⇒ fallback；**認唔出 ⇒ 拋錯** |
| A2 | `IcsExport.gs` 嘅 `defaultStart`／`defaultEnd` 改用佢，唔再 `String()` |
| A3 | `shiftIcsLocalDateTime_()` 加 `isNaN` 防線，寧可拋錯中止寄送，都好過寄一份時間係 NaN 嘅月曆 |

⚠️ **A1 認唔出一定要拋錯，唔可以靜靜回 fallback 或者 `00:00`。**
靜靜回一個「睇落合理」嘅值，正正就係本專案已經燒過幾次嘅同一個 bug class：
**把「認唔到」當成「冇事」**（第十八輪 `context.roles` 漏傳、第二十輪
grid placeholder、第二十二輪 `displayCellValue_`）。時間錯咗，義工會喺錯嘅

### 一、階段 A1：`readSheet()` 快取加防線——點解揀複本唔揀 freeze

第二十三輪加咗 opt-in 嘅 `readSheet()` 快取。快取存嘅係陣列 reference，
如果有人 mutate 咗攞返嚟嘅陣列或者 row，同一次呼叫之後再讀就會攞到
**被改過嘅資料**，而且完全冇聲。

**先掃描再決定**（呢個次序好重要——唔掃就決定，等於靠估）：

| 掃描項目 | 結果 |
|---|---|
| `record[C.X] = …` 之類嘅 property 賦值 | 13 處，**全部喺新建嘅 `{}` 上面**，唔係 readSheet 出嚟嘅 row |
| 直接喺 readSheet 回傳值上面 `.sort()`／`.push()` | **0 處**——四處 `.sort()` 全部喺 `.filter()`／`.map()` 之後（嗰啲已經係新陣列）|

**所以目前冇任何一處會 mutate。呢個係將來風險，唔係現有 bug。**

**揀咗淺複本，唔揀 `Object.freeze()`：**

| 做法 | 有人 mutate 時 |
|---|---|
| `Object.freeze()` | 非嚴格模式下**靜靜失敗**——改動消失，程式繼續行 |
| 淺複本（採用）| 改動只影響呼叫者自己嗰份，快取保持乾淨 |

靜靜失敗本身已經係本專案燒過幾次嘅 bug class。但**更決定性嘅理由係
語意一致**：冇快取嗰陣，每次 `readSheet()` 都回全新物件。淺複本令
「有快取」同「冇快取」行為**完全一樣**；freeze 就會令兩者唔同——
而且個分別只會喺「有開快取」嗰條路徑先浮現，即係
**測試全綠、偏偏就係實際會行嗰條路出事**。

成本：每次快取命中複製 N 個物件。相對一次 `getValues()` 來回，可忽略。

## 第二十五輪批次：修 HtmlService 樣板引擎唔理 HTML 註解嘅 bug

**症狀：** 幹事介面開唔到，`SyntaxError: Unexpected token ';'`（`WebApp.gs` 第 123 行，即 `.evaluate()` 嗰行）。

**根因：** 呢個係「離線假設同真實環境唔同」bug class 嘅新變種。
`src/ui/Index.html` 有段 HTML 註解，入面用字面上嘅 `<?= ?>` 同
`<?= JSON.stringify(x) ?>` 做警告文字，解釋「呢個檔案唔可以點做」。

**離線寫嗰陣嘅假設係：** HTML 註解入面嘅文字係死嘅，唔會被執行。
呢個假設喺瀏覽器 JS/CSS 係啱嘅，但 **HtmlService 嘅樣板引擎唔係
喺瀏覽器行——佢喺 Google 嘅伺服器編譯成個檔案嗰陣，係逐個字元搵
`<? … ?>` 嚟編譯，完全唔識、亦唔理會 HTML 註解嘅語法。**
於是 `<?= ?>`（空運算式）被當成真嘅 scriptlet 編譯，變成語法錯誤，
令**成個樣板**（唔只果段註解）都編譯唔到。

**點解一直冇測試捉到：** 第二十四輪新增嘅紅線測試（`tests/gs_syntax.test.js`）
特登**先剝走註解先掃**——因為前提係「註解入面提到嗰個壞寫法只係
做反面教材嘅文字，唔係真程式碼」。呢個前提本身就係離線環境嘅假設，
喺 HtmlService 唔成立，所以測試同真實環境嘅判斷剛好相反。

**修法：**
1. `Index.html` 嗰段警告改用文字描述，唔再寫出字面上嘅標籤符號
2. `tests/gs_syntax.test.js` 嗰條紅線由「剝註解再掃關鍵字」改成
   **白名單制**：唔理係咪註解，掃全個檔案入面任何一個 `<?` scriptlet，
   逐個同已知安全嘅形狀（`includeHtml()`／固定嘅 `quarterId` 注入）比對，
   唔喺白名單入面就算違反——呢個做法唔依賴「邊度嘅文字係死嘅」呢個假設

### 一、階段 A：系統不再自己動任何東西

#### 為什麼改

原本設計是季初前 5 週由 trigger 自動生成初稿、再 email 通知幹事。
Ivan 決定改成幹事自己撳掣。

理由不是技術上的，是**教學上的**：真正操作系統的人不懂電腦，
「系統靜靜幫你做了一件事」比「你撳個掣才會發生」難教很多。
幹事開頁見到已經有一份初稿，他沒辦法分辨「是我上次撳的」還是
「是系統自己做的」，也不知道應該相信哪一個。

改完之後，**系統不會自己動任何東西**，全部行動由幹事發起。

#### 實作：加開關，不刪程式碼

新增 Config `TRIGGER_AUTO_GENERATE`（`BOOL`，預設 `FALSE`）。
自動生成那條程式碼路徑**一行都沒有刪**，只在 `judgeGenerateAction_()`
入口加了一道開關檢查。

理由有兩個：那條路徑已經測試過，將來想開回就改一個值即刻有；
而且符合本專案「一切須可配置，不可寫死」的原則——
**「不要自動生成」是一個決定，不應該用「刪走程式碼」去表達**，
否則改主意就要重新寫一次。

#### 開關檢查放在最前面（不是放在日期檢查之後）

這個位置是有意選的。放後面的話，「開關關了」會變成一個罕見的 outcome
——只有在剛好到期那一天才看得到；平時檢查報告顯示「尚未到期」，
**幹事會以為「到了期就會自己生成」，直到那一天才發現不會。**

放最前面，`SKIPPED_MANUAL_MODE` 就是**每一天**的答案，
唯讀檢查報告任何時候看都講同一件事。

同樣理由，`buildAutomationCheckReport_()` 那句「自動排程會做什麼」
也改成按開關講兩套不同的話——這份報告的**唯一用途**就是
「告訴幹事系統會自己做什麼」，講錯了等於整份報告失去價值。

#### 失去的安全網：提醒維度四

新增 `NOT_GENERATED`：`GenerateOn` 到期而這一季仍然**完全沒有版本**。

> **⚠️ 這一個維度不受 `REMIND_STUCK_MAX_COUNT` 上限限制**，跟其餘三個不同。
>
> 其餘三個維度說的是「你慢了」——提三次之後幹事已經知道，再提下去只是嘈。
> 這一個說的是「**完全沒有人做過這件事**」，而現在連自動生成都關了，
> 沒有這個提醒就真的沒有任何東西會發生。
>
> 一封不停的提醒信很煩，但「整季沒有職事表而沒有人知」是災難。
>
> 停止條件是「生成了」，不是「提夠次數」。幹事撳一次掣就永遠不會再收。
> 用不到的舊季度（例如培訓用的）就清空它的 `GenerateOn`。

沒有上限這件事在信裡要講清楚，而且**不可以寫「第 N / M 次」**
——寫了就是在講一個不存在的上限，幹事會以為再等幾天就不會再嘈。

#### 提醒信不附幹事介面連結

這個專案有兩個部署（義工個人連結、幹事介面），
`ScriptApp.getService().getUrl()` 只會回其中一個，而且在 trigger
執行環境回的可能是 head 部署而不是幹事日常用那個。

所以**不憑估砌一條連結**——一條打不開的連結對一個不懂電腦的人來說，
比沒有連結更差：他會以為系統壞了，而不會想到「應該用回自己收藏那條」。
試算表網址是拿得到的可靠值，就只給試算表。

#### 階段 A7：執行時間量度

**結論：不需要改細 seed 數。現有機制已經足夠，本輪做的是把它呈現出來。**

`generateBest()` 本身已經有時間預算 `MULTIRUN_TIME_BUDGET_MS = 180000`：
每跑完一次就量度平均耗時，如果再跑多一次會超出預算就停低，
並且在結果回傳 `stoppedByTime: true`。

即是說「靜靜跑少幾次令品質下降」**不會靜靜發生**。所以本輪沒有動 seed 數
（改細 seed 數是一個「靜靜降低品質」的改動，本專案不接受），
只是把 `stoppedByTime` 呈現到成功畫面的黃色警告框——以前這個欄位
**沒有任何畫面用到**。

| 項目 | 數字 | 來源 |
|---|---|---|
| Apps Script 單次執行上限 | 6 分鐘 | Google 官方限制，`google.script.run` 同一個配額 |
| 多次生成的預算 | 3 分鐘 | `MULTIRUN_TIME_BUDGET_MS` |
| 剩給寫入的時間 | 3 分鐘 | 建 grid 工作表＋寫長表＋登記版本 |

**⚠️ 以上是讀程式碼算出來的，不是實際計時。** 真實的 2027T1
（13 個主日 × 20 個崗位 × 20 次）要跑多久，要撳一次才知道。

### 二、階段 B：四項顯示層修正（Ivan 實測撞到）

#### B1　內部代號漏到畫面

狀態卡顯示 `目前第 1 版　2026-08-17　REQUESTS_APPLIED`。
`REQUESTS_APPLIED` 是 `RosterVersions.Basis` 的內部代號，違反規格 1.3。

更差的是：v0 的 `Notes` 存著
`seed=20260813　第 3 / 20 次　總偏差 0.6033　主席兼報告 46.2%`，
而舊的 `buildVersionBasisText_()` 會把 Basis 同 Notes 駁埋——
所以揀著 v0 時，狀態卡會變成一大段技術統計數字。

修法：
- 建對照表（掃過全專案，`registerVersion()` 的 basis 一共五個來源）
- **對照表沒有的值不照印**，顯示「（沒有說明）」——照印就是這個 bug 本身
- 但「已經是中文」的例外（回退版本寫的「回到第 N 版」）照用
- **`Notes` 不再入狀態卡**，函式簽名收窄成只收一個參數（結構上就拿不到）

測試那條斷言是**從 `VERSION_VALUES` 自動取清單**的，
將來有人加 `BASIS_XXX` 而不加對照，測試會立刻失敗。

#### B2　未格式化的 Date 物件（**同一個 bug class 的第三次**）

掣 2／掣 3 顯示
`上次在 Mon Aug 17 2026 04:35:09 GMT+1200 (New Zealand Standard Time) 寄過`。

| 輪次 | 位置 |
|---|---|
| 第二十二輪 | `QuarterReset.gs` 的「加入於」 |
| 第二十三輪 | `ICS_SERVICE_START_TIME` |
| 第二十五輪 | `SendLog.SentAt` |

**修的過程中發現第二個、更難察覺的 bug：** 舊寫法用
`String(a) > String(b)` 揀最新一筆。Date 物件 `String()` 出來是
`Mon Aug 17 ...` 這種格式，字串比大小是**逐個字母比**——
`'M' < 'S'` 所以九月被當成大過八月純屬巧合，換成 `Fri`／`Wed` 就會揀錯。

修法：`normalizeSentAt_()` 同時回 `sortKey`（真時間值，用來排序）
同 `text`（已格式化，用來顯示）。認不出的格式照原文顯示但
`sortKey` 設 0——不可以靜靜丟掉（會令「上次幾時寄」變空白，
看起來像沒寄過），也不可以當成最新（一個爛值會蓋過真正最新那筆）。

#### B3　「會寄給表上 0 個人」

沒有版本時掣 3 顯示 `會寄給表上 0 個人`。

那個 0 不是「數過，是零」，而是「根本還沒有表可以數」。
這是本專案一路在燒的同一個 bug class：**把「查不到」講成一個具體數字**。
零同未知是兩件事，「0 個人」會令幹事去找一個不存在的名單錯誤。

改成 `還未生成初稿，未知會寄給哪幾位。`

#### B4　口語殘留

- `要等系統生成咗初稿` → `要先生成初稿`（順帶：「等」本身也錯了，
  自動生成關了，沒有東西可以等）
- 掃了全部畫面文案，另外找到兩處真的殘留：
  - `ScriptZone1.html` 一句寫著字面上的 `**沒有**`（Markdown 粗體語法
    在畫面上只會顯示成兩粒星，第二十一輪已經在選單版清過一次同類問題）
  - `WebAppPersonalLink.gs` 一句 `（或者呢個人 Active 唔係 TRUE）`

（程式碼註解不用改，只改會出現在畫面的字。）

#### B5　禁用掣視覺太弱

原本只有 `opacity: .45`。藍底掣半透明之後仍然是藍色，
在非技術使用者眼中「淺藍」同「藍」都是「可以撳」——分不到就會一直撳，
撳完沒反應就以為壞了。

改成**換色相**：灰底、灰字、灰邊框，同啟用態是兩種顏色，
不是同一種顏色的兩個濃度。

### 一、階段 A：換季度時，區的內容不更新（bug class 新變種）

#### 現象

Ivan 由 2027年7-9月 換去 2026年10-12月，區二的標題正確變成
「還有 2 項未做」，但下面五項清單**仍然顯示上一季的數字**。

#### 根因：同一個狀態有兩個旗標，只重設了其中一個

- `Script.html` 的 `wireZoneToggle()` 內部有一個 closure 變數 `loaded`
- `ScriptZone2.html` 另外有一個 `zone2Loaded`

換季度只重設了後者，所以區二一旦開過，之後換幾多次季度都不會再叫
`onFirstOpen`。

> **這是本專案最危險的一類 bug：畫面顯示上一個季度的數字，
> 但看起來完全正常**——沒有錯誤、沒有空白、沒有任何訊號。
>
> 更值得記住的是：同一段程式碼上面的註解特地解釋了
> 「換季度一定要即刻關彈窗，否則幹事會對錯季度做事」——
> **想到了彈窗，漏了區的 body。** 同一個危險，只堵了一半。

#### 修法：不是補一句，是收成一個真相來源

修法**不是**加多一句重設 `zone2Loaded`。兩個旗標本身就是問題。

- `Script.html` 有一個全域 `zoneLoadState`，用 `bodyId` 做 key
- `wireZoneToggle()` 不再有自己的 closure 旗標
- `setZoneOpen()` 那條路走 `markZoneLoaded()`，寫的是同一個 state
- 換季度叫 `resetAllZoneLoadState()`——**整個物件掉走**

> ⚠️ 關鍵是最後那一點。逐個區列名重設的話，
> 下一輪加了區三內容而漏改那一行，bug 就會原封不動再中一次，
> **而且一樣沒有訊號**。整個掉走，加新區時那一行不用改。

`tests/zone_reload_on_quarter_change.test.js` 鎖的是**寫法本身**：
重設函式裡不可以出現任何 `zone2`／`zone3`／`zone4` 字樣，
而且任何區檔案都不可以自己再開一個「載入了未」旗標。

### 二、階段 B：填講員／翻譯／獻花

#### 拆走歷史建議下拉

理由**不是實作有問題，是這個功能本身沒用**：講員多數外請或客席、
翻譯視乎該週講員的語言需要臨時決定、獻花由會友認獻幾乎每次不同人。
而且實際上根本沒有資料——這三個崗位在 `RosterAssignments` 從來沒填過，
所以那條建議名單一直都是空的。

連同 `suggestHistoricalNames_()`、側邊欄的渲染程式碼、
以及上一輪才加的 `suggestionsByPostId` 一併拆走
（上一輪那個修法本身是對的，只是整個功能不要了）。

#### Chrome 自動填充

姓名格沒設 `autocomplete`，Chrome 當它是聯絡人欄位，
**彈出使用者自己的通訊錄**。幹事會以為那是系統給的建議名單，
撳下去就填了一個完全不相干的人。三個輸入格都加了
`autocomplete="off"` ＋ 一個 Chrome 認不出的 `name`。

#### 取而代之：儲存之後講「有沒有對上名單」

| 情況 | 文字 |
|---|---|
| 對上了 | `已對上名單上的「XXX」，正式發出時他會收到通知。` |
| 對不上 | `名單上沒有這個名字，正式發出時不會寄給他。外請講員屬正常。` |

**為什麼這一句比建議下拉重要得多**：翻譯打錯一個字，
那位弟兄姊妹就**永遠收不到通知**——正式發出時他不在收件名單裡。
而畫面上完全看不出：職事表照樣印住那個名，PDF 照樣有他，一切正常。

⚠️ 對不上**不一定是錯**（外請講員本來就不在名單），所以文案講明
「外請講員屬正常」，不寫成錯誤——寫成錯誤幹事會去「修正」一件沒問題的事。

#### `linkedToNameMapping` 的判斷準則（核實結果）

`resolvePersonId()` 的實際行為：

| 情況 | 對得上？ |
|---|---|
| 與 `NameMapping.NameTC` 完全一樣 | ✅ |
| 在 `NameAlias` 有登記 | ✅ |
| 差一個字 | ❌ **不會猜最接近的** |
| 前後有空格 | ❌（呼叫端已 `trim`，函式本身不會） |
| 全形字 | ❌ **沒有做全形正規化** |
| 異體字（恒／恆這類） | ❌ **除非在 `NameAlias` 明確登記** |

**結論：異體字與輸入法差異一定要靠 `NameAlias` 明確登記，不會自動對上。**
這是刻意的——自動對上就是在猜，而猜錯的後果是寄錯人。

### 三、階段 C：兩個數字用了兩套定義

生成完成畫面寫「另有 39 格是要你人手填的」＝ 13×3。
但區二寫「翻譯未填：0 項（做好了）」，因為那一季**沒有一日需要翻譯**。

修法不是「在生成那邊也寫多次 `TranslationRequired` 判斷」——
兩邊各寫一次就一定會有一日再分岔。而是
`sumManualFillItems_()` 直接加總 `planPreQuarterChecklist_()` 的結果，
**同一個函式的同一次結果**。

算不到時回 `-1`，前端用 `> 0` 判斷，所以不會顯示「另有 -1 格」，
也不會把「查不到」講成 0。

### 四、階段 D：`WEBAPP_STEWARD_URL`

上一輪決定提醒信不附幹事介面連結，理由是
`getService().getUrl()` 在兩個部署之下只會回其中一個。

**理由成立，但結論對不懂電腦的幹事是倒退**——他不會自己記得網址，
「請用你自己收藏那條」等於沒講。

正確做法不是在「猜」與「不講」之間二選一，而是**不要靠猜**：

### 五、階段 E：區三名單維護（三個畫面）

按幹事實際使用頻率排：不能服侍日期 > 人員與電郵 > 崗位資格。

#### 共通寫入層（`WebAppRoster3Common.gs`）

| 規矩 | 實作 |
|---|---|
| 不刪行 | 全部檔案掃過，沒有任何 `deleteRow` |
| **只改該行該欄** | `writeRowFields_()`，永遠不整行覆寫 |
| 每次寫入寫 `AuditLog` | `writeZone3Audit_()`，強制 old／new 兩邊都有 |
| 儲存前確認 | 前端每個寫入前都有「會改動 N 行」 |

> ⚠️ 「只改該欄」那一條特別重要。反面做法是「讀整行 → 改幾個值 →
> 整行寫回」——那會把畫面上沒顯示的欄（`Phone`、`Congregation`、
> `LastAttendance`、`SyncedAt`…）一併寫回去，而如果讀的時候有任何一欄
> 讀成了空白，就會**靜靜清空真實資料**。

另外：改現有行時用 `findRowById_()` **重新找列號**，不信前端傳回來那個
——幹事可能在試算表插了一行，那個列號就會指去另一行，寫下去就是改錯人。

#### E2 最危險的一件事

名單裡真的有兩位姓名只差最尾一個同音字的弟兄姊妹，**他們是兩個不同的人**。

系統**永遠不會**自動合併相似的名——合併錯了就會寄錯人：
甲收到乙的職事表，乙永遠收不到自己那份，兩邊都不知道發生了什麼。
撞名一律只警告、交幹事判斷。

同一個人因為異體字寫成兩個名，是在 `NameAlias` 處理——那是
**幹事明確說「這兩個是同一個人」**，不是程式猜。

#### 其他鎖死的點

- **`MemberNo` 前導零**：`01234` 直接寫入會被試算表當成數字變成 `1234`。
  一律加單引號前綴強制當文字。不夠 5 位就擋住，**不會靜靜補零**
  （補錯就是另一個人）。
- **`PersonID` 不可改**：它是全系統的外鍵。畫面上是灰字標籤，不是輸入格；
  後端更新時完全不寫那一欄。
- **`EmailSource` 只在電郵真的改了才動**：沒改就把一個由出席系統同步回來的
  來源標記改成「手動」，會令下次同步邏輯判斷錯。
- **`Eligibility` 取消勾寫 `Active=FALSE`**，不刪行——`HistoricalCount`
  要保留。刪了的話重新勾回就由零開始計，而那個人其實做過很多次。
- **`AddedAt` 已格式化**才寫入（第二十二輪在 `QuarterReset.gs` 撞過同一件事）。

#### E3 的渲染策略（約 90 人 × 16 崗位 = 1440 格）

**後端一次回完整資料，分頁與過濾是前端的事。**

前端預設按崗位分頁：一次看一個崗位的全部人，再加姓名搜尋。
一次畫 1440 個 checkbox 太笨重，而且幹事要橫向捲十幾欄才找到一個崗位。

> ⚠️ **但統計數字一律用後端在完整資料上算的那個。**
> 如果統計跟著分頁走，「合資格 N 人」就會變成「當前頁的 N 人」，
> 是一個錯的數字，而幹事完全看不出。
>
> 同理，「人數少於 3 人的崗位」一覽**不論選了哪個崗位都顯示**
> ——那是「整盤數有沒有問題」的訊號，不應該要逐個崗位撳才看得到。

### 一、階段 A：公開連結漏洞（bug class 新變種）

#### 現象

幹事最自然那個次序——**生成初稿 → 寄給堂委審閱**——會寄出一封
**連結是空白**的信，而且畫面上沒有任何訊號。

#### 根因鏈：每一層都以為沒事

| 層 | 做了什麼 |
|---|---|
| 生成初稿 | 不發佈 |
| 掣 1 | 零改動時也不發佈 |
| 掣 2 | 不發佈，也不檢查 |
| placeholder 解析 | 查不到就回**空字串**，註解還寫明「不會令寄信流程失敗」 |

> **bug class 新變種：一個「查不到」被包裝成一個「正常結果」，
> 而且發生在最深那一層（placeholder 解析）。**
>
> 上面每一層都沒有理由懷疑——沒有拋錯、沒有 log、畫面上零訊號。
> 空字串同 `null` 在 JS 都是 falsy，所以「回空字串」這個決定
> **令呼叫方沒有可能分辨「未發佈」與「發佈了但網址是空」**。

#### 更根本的教訓

這個洞是**四粒掣改造之後才出現的**。舊選單流程有一步
「準備工作 ▸ 發佈公開職事表」，由幹事自己撳。改成四粒掣之後，
**那一步沒有人接手**。

> **每次拆走一個人手步驟，都要問一句：
> 那一步本來在做什麼？現在誰做？**

#### 三層修補

1. **生成初稿成功之後順手發佈。** 發佈失敗不當成生成失敗——
   版本真的建立了，所以是黃色警告不是紅色錯誤，而且明講
   「寄給堂委之前請先去『進階功能 ▸ 重新發佈公開連結』」。
2. **掣 2 前置檢查。** 沒有連結就拒絕，而且畫面直接給一粒「立即發佈」
   ——只說「去進階功能發佈」的話，幹事要走五步才做到他本來想做的事。
3. **`resolvePublicRosterUrlForPlaceholder_()` 查不到回 `null`。**
   加一道 `assertPublicRosterUrlAvailableForStage_()`，在**寄第一封之前**擋。

#### ⚠️ 哪些階段要擋，由「範本實際文字」決定

**不是一個寫死的階段清單。**

逐個階段查證過（種子檔案 `EmailTemplateSeed.gs`）：

| 範本 | 階段 | 用 `{PublicRosterUrl}`？ |
|---|---|---|
| `TPL_REVIEW_TC` | REVIEW | ❌（用 `{SpreadsheetUrl}`） |
| `TPL_REMIND_TC` | REMIND | ❌ |
| `TPL_OFFICIAL_TC` | OFFICIAL | ✅ |
| `TPL_OFFICIAL_LIST_TC` | OFFICIAL | ✅ |
| `TPL_RESEND_TC` | RESEND | ✅ |
| `TPL_RESEND_LIST_TC` | RESEND | ✅ |

> **但這份表不可以寫死進程式碼。** 範本住在 `EmailTemplates` 工作表，
> 幹事改得——第十一輪就人手貼過新內容。寫死「REVIEW 不用檢查」的話，
> 會在幹事把連結加入審閱信之後**靜靜失效**，而且沒有人會發現，
> 因為缺的只是一條連結。
>
> 所以關卡是讀**這次真正會用到那個範本**的 subject／bodyHtml／bodyPlain，
> 看裡面有沒有那個 placeholder。唯一可靠的答案在範本本身。

### 二、階段 B：PDF 分季分版

#### ⚠️ 任務書的前提不成立：`RosterPDF` 工作表不存在

任務書假設有一張 `RosterPDF` 工作表存住 file ID，並要求清理工具
「改成以那份表為準」。

**全專案沒有 `SHEETS.ROSTER_PDF`。** PDF 一直都是靠掃 Drive 資料夾
＋ 解析檔名（`{QuarterID}_v{N}_...`）認出來的。

改成：**一個共用入口 `listRosterPdfFilesForQuarter_()`**，同時掃根資料夾
（舊平舖檔）與 `{quarterId}/v*` 子資料夾。效果跟任務書想要的一樣
（單一權威存取點、沒有工具會漏掃），只是背後是 Drive 而不是一張不存在的表。

#### 結構與三個關鍵決定

```
RosterPDF（根，不變）
└── 2027T1
    └── v0
        ├── 2027T1_v0_..._完整版.pdf
        └── （每人一份）
```

| 決定 | 為什麼 |
|---|---|
| **用 `LockService` 包住「查有沒有 → 沒有就建」** | Drive **容許同名資料夾**。兩個人同時生成，兩邊都「查到沒有」然後各建一個，之後就有兩個 `2027T1`，一半檔案在其中一個——而且**兩個都看起來正常** |
| **一批只解析一次** | 那個函式要拿鎖，逐個檔叫一次就是 58 次拿鎖 |
| **舊檔一個都不搬、不刪** | 搬東西本身就是一個會出錯的動作，而收益只是「看起來整齊」。附件查找**新舊兩處都找**——只找新子資料夾的話，重發舊季度會全部變成「缺件」 |

#### 為什麼一定要一個共用入口

加了子資料夾之後，任何一個「自己列根資料夾」的工具都會
**只看到一半檔案**——而且不會報錯，只會少報。

- 「清理舊 PDF」少報 ＝ 清不乾淨（可接受）
- **「檢查個人 PDF 完整性」少報 ＝ 報告說缺件，但檔案其實在**（很差）

後者是「報告說缺、實際不缺」，比漏報更難查。

清理後只刪**真正空的**版本資料夾；裡面還有東西一律不碰
（寧可留一個不該留的空殼，都好過刪走一個裡面有東西的資料夾）。
季度資料夾就算空了也不刪——它的存在本身就是「這一季做過事」的痕跡。

### 三、階段 C：排表偏好（本輪最重要的新功能）

#### 一個機制搞掂堂委三條意見

堂委收到 2026T4 系統初稿之後改了 23 格，**全部集中在四個崗位**
（主席、報告、當值堂委、聖餐襄禮），其餘十二個崗位一格都沒改。

三條意見**形狀完全一樣**：某人 × 某崗位 → 比平均多／少 N 次。
所以不需要三套邏輯，一張 `PersonPostWeight` 表搞掂。

#### 揀了哪種做法，為什麼

| 做法 | 判斷 |
|---|---|
| 每人每崗位目標值 ＋ 偏離扣分 | ❌ 現有 `computePersonQuotas_()` 只算**跨全部崗位的總配額**。要加一整層「每人每崗位目標」，而那個目標值本身要靠估，估錯會影響**全部人** |
| 直接改 `Eligibility` 權重 | ❌ 會令「有沒有資格」與「做多少次」混在一起，而它們要分開改 |
| **選人時加權（採用）** | ✅ 只在**已經合規**的候選人之間調整優先次序。沒有資料 ⇒ 加 0 ⇒ 零改變 |

#### ⚠️ 最重要的安全性質：份表空的時候，結果逐個位元一樣

`computePersonPostWeightBonus_()` 查不到就 `return 0`，而 0 加到 `bonus`
是恆等元——分數完全一樣，**連 tie-break 的隨機序列都不會偏移**
（因為沒有多抽任何一個亂數）。

**證據**：全部既有生成器測試（`generator_hard_rules`、`generator_semi_soft_rules`、
`generator_tie_epsilon`、`chair_dual_bonus_sensitivity`、四個 `role_*`）
**期望值一個都沒有改**，全部照樣通過。

#### 為什麼結構上不可能壓過硬規則

`pickPerson_()` 是先 `clean = scored.filter(!hasHard)` **隔走**違反硬規則的人，
之後才在剩下的人之間比分數。這個偏好只影響分數。

所以就算把 `PERSON_POST_WEIGHT_STEP` 調到一萬，一個違反硬規則的人
**都不會**被揀中。**這是結構保證，不是「數字剛好調到不會壓過」。**
測試用 `adjust: 999` ＋ 一個全季不能服侍的人驗證過：排 0 次，硬規則零違反。

#### 正負兩邊不對稱（有意）

| 方向 | 做法 | 為什麼 |
|---|---|---|
| **正數（多做）** | 遞減加分——只在「這一季在這個崗位已排少於 `Adjust` 次」時加分 | 常數加分會令他由 1 次跳到 4-5 次（每一格都佔優）。而 `+1` 對幹事的意思是「多**大約一次**」，不是「霸晒」 |
| **負數（少做）** | 常數扣分 | 這邊不需要遞減：`SOFT_QUARTER_DISTRIBUTION` 會隨著其他人越派越多而對**他們**扣分，最終蓋過這個固定扣分。即是「排後一些，但不會排到零」——正是想要的效果 |

#### C3 驗收結果（實際數字）

用 mock 資料（13 個主日、89 人、`randomSeed=11`），加四行偏好：

| 偏好 | 基準 | 加了偏好之後 |
|---|---|---|
| 主席 **-2** | 2 次 | **0 次** ✅ 下降 |
| 主席 **+1** | 0 次 | **1 次** ✅ 上升，而且剛好一次 |
| 報告 **+1** | 3 次 | 3 次 ⚠️ 沒有變 |
| 當值堂委 **+1** | 6 次 | 6 次 ⚠️ 沒有變 |

**「沒有變」的兩項是機制正確運作，不是失效**：那兩位已經接近或到達
`MaxPerQuarter` 上限（當值堂委已經 6 次），而偏好是 soft 的，
**不會為了滿足偏好而突破上限**。這正是「軟」的定義。

**堂委一格都沒改過的十二個崗位**：讀經、領詩、司琴、司事、音響、
PPT、錄影、交通、司數——**沒有任何一個出現 ≥2 次的用人變化**。
差 1 次是可接受的連鎖反應（主席換了人，他那一週就騰了手做別的）。

#### 量度：不可以只改行為而不顯示結果

「軟規則實測量度」報告加了一節，逐行列出：
偏好、這個崗位平均幾多次、目標約幾多次、實際幾多次、差幾多。

> 一個「軟」機制沒有量度的話，幹事同堂委都沒辦法知道「究竟有沒有用」
> ——下次開會就會憑感覺再調，而不是看著數字調。

超出 ±3 的行**完全不生效，而且列出來**——不會靜靜夾到範圍內，
那等於系統擅自改了堂委的決定。

#### C5：`CHAIR × COMMUNION` 互斥組

`HARD_MUTEX_GROUP` 早就實作好（`Generator.gs`），**只是一直沒有任何一組資料**
（`RuleSettings` 那行的說明還寫著「現時無任何組」）。所以只需要種子資料。

⚠️ 本輪只做**唯讀報告**（`planPostMutexGroupSeed_()`），一格都不寫。
理由：`MutexGroup` 一填下去，排表就會立刻多一條硬規則。
**一條硬規則應該由人明確開啟，不應該在一次「補建欄位」的維護動作裡順手生效**
——那種「順手」正正是本專案一直提防的「系統靜靜幫你做了一件事」。

### 四、階段 D：三項實測修正

#### D1　「合資格人數少於 3 人」警告是錯的

畫面頂顯示紅框：`有 2 個崗位的合資格人數少於 3 人：講員 0／翻譯 0`。

講員、翻譯、獻花由 `HARD_NO_AUTO_PREACHER` 規定**一律留空、永不自動排**，
所以合資格 0 人是**正常而且正確**。這個警告每次開畫面都出，
令幹事以為有東西沒做好，而實際上沒有東西要做。

**同上一輪的「39 格」是同一個 bug class：
一個數字在計的時候沒有理會「這個崗位到底需不需要排」。**

判斷一律由資料讀出——`Posts.AutoGenerate` ＋ 規則的 `ScopePostIDs`，
**不寫死崗位代碼**（代碼在不同試算表可能不同，寫死就會靜靜失效，
而失效的表現是「警告又出返」，一個看起來沒壞的退步）。

#### D3　電郵格式檢查太鬆

名單上有一位的電郵**結尾多了一個句號**，舊那條 regex 放行了。

這種錯會令那位弟兄姊妹**永遠收不到通知**，而畫面看起來完全正常。
⚠️ 這跟「沒有電郵」是兩件不同的事：沒有電郵的人，系統知道他收不到；
**格式錯的人，系統以為他收到**。

收緊五樣：結尾句號、連續兩點、缺 `.`、有空白、`@` 前後為空。
但**仍然不阻擋儲存**（世上有奇怪但合法的地址，擋錯了幹事就完全入不到），
改為要幹事再撳一次確認。同時「名單檢查」加一條提示並**逐個列出是哪幾位**。

### 階段 A：狀態快取單一寫入點（同一 bug class 第三次）

**Ivan 實測（2027T3）**：撳「寄給堂委審閱」→ 正確彈出「還沒有公開連結」→
撳「立即發佈」→ 掣暗一陣 → **彈返同一個畫面**。
用 connector 核實：`PublicLinks` 真的加了 2027T3 那一行（2026-08-18 19:04:59），
後端成功了，只是畫面不肯走下去。

**成因**：「立即發佈」成功之後即刻叫 `openReview()`，
而 `openReview()` 讀的是**發佈之前抓下來的狀態快取**，裡面仍然寫著「沒有連結」。

#### 這個 bug class 的第三次

| 次數 | 位置 | 症狀 |
|---|---|---|
| 1 | `wireZoneToggle` 兩個載入旗標 | 換季度時區二顯示上一季數字 |
| 2 | 掣 1 預覽過期 | 已加偵測 |
| 3 | 狀態快取 vs 伺服器真實狀態 | 本次 |

#### 訂下的結構性規則（不是補丁）

1. **`dashboardState_` 只可以在 `loadDashboard()` 裡面賦值。**
   其餘五個前端檔案完全不出現這個變數名（測試會掃）。
2. **讀的唯一入口是 `getDashboard()`**，它是 `async`，看到過期會自己先刷新。
3. **`callServer()` 是預設拒絕**：不在 `READ_ONLY_APIS` 白名單的一律當成會寫入，
   要用 `callServerMutating()`。

**第 3 條是關鍵，而且方向是刻意的。** 白名單放的是「唯讀」而不是「會寫入」，
所以將來有人加一個新的寫入 api，他**不需要記得做任何事**——
沒有加進白名單就一定會走 `callServerMutating()`，而那裡會自動標記快取過期。
估錯的代價不對稱：把一個唯讀 api 當成會寫入，代價只是多刷新一次；
反過來就是這次這個 bug。

#### 為什麼是「標記過期」而不是「即場刷新」

有些流程會連續呼叫幾十次（分批產生個人 PDF 最多 40 次）。
每次都即場刷新就是幾十次多餘的來回。改成標記過期之後：

- `getDashboard()` 一讀就先刷新 ⇒ **判斷**永遠用新資料
- `runAction()` 做完看到過期就刷新一次 ⇒ **畫面**永遠跟著變

兩邊都是自動的，呼叫端不需要記得任何事。
`runAction()` 那一次放在 `finally` 而不是成功路徑，因為拋錯不代表沒有寫入
——很多動作是「寫了一半才失敗」，那種情況畫面更加需要是最新的。

#### 測試：`tests/dashboard_refresh_after_mutation.test.js`

分兩半，兩半都要有：

- **上半（行為）**：真的把 `Script.html` 的 script 內容載入 Node 沙箱跑一次，
  用假伺服器重演 Ivan 那個情境。純靜態掃描只證明得到「字面上寫了刷新」，
  證明不到「刷新之後真的拿到新值」。
  可以這樣做的前提：`Script.html` 頂層只有宣告，而 `loadDashboard()` 用到的
  四個 render 函式全部住在別的檔案，所以在沙箱裡先定義成空函式就行。
- **下半（結構）**：靜態掃描，確保將來新增一個寫入動作不會再中同一個陷阱。
  掃描範圍**由 `Index.html` 的 `includeHtml` 反推**，不是手寫清單
  ——手寫的話，加了新檔而忘記更新就會靜靜漏掃。

寫這個測試時撞到一個陷阱值得記下來：`let`／`const` 在 vm script 頂層
**不會**變成 context 物件上的屬性（只有 `function` 宣告會）。
直接 `sandbox.currentQuarterId = …` 只會多開一個被遮蔽的全域屬性，
測試會靜靜跑錯——正正是本專案最怕的那種失敗方式。
解法是在同一份 script 尾巴掛一個小 setter 上去。

### 階段 B：排表偏好收尾

#### B1　建表工具

`PersonPostWeight` 工作表在本輪之前**從來沒有建立過**（connector 核實）。
新增「維護 ▸ 補建排表偏好工作表」，沿用 `ensureSimpleSheet_()`
（跟 `Roles`／`PersonPostExclusions` 同一個做法：冪等、只新建、絕不覆寫）。

三個地方同步認得它：

| 地方 | 怎樣處理 |
|---|---|
| 全新環境自我檢查 | 列為**可選**表，並寫明「缺少時不會出錯，但堂委決定的多做／少做不會生效」 |
| 匯出關鍵狀態 → Diagnostics | 新增一節；**分得出「工作表尚未建立」與「已建立但空白」** |
| 選單「維護」 | 新增補建項目，建表時寫 `AuditLog` |

「尚未建立」與「已建立但空白」在數字上都是「零項生效」，
但下一步要做的事完全相反（一個要去建表，一個要去開會決定）。
只印一個 0 就是把兩件事混成一件。

#### B2　偏好未生效時要解釋

上一輪的離線驗收：四行偏好之中兩行「冇變」。機制是對的
——那兩位已經撞到 `MaxPerQuarter`，而偏好是軟的，不會為了滿足偏好而突破上限。

**但幹事揀了「多一次」而什麼都沒有發生，畫面不會解釋為什麼。**
他只會得出一個結論：「這個功能壞了」，然後去做一些更危險的事
（例如去改人家的崗位資格——那是完全不同、而且很難復原的一件事）。

兩處補上：

1. **「排表偏好」畫面每一行**：如果那位已經接近或到達每季上限，即時顯示。
   已排滿的講法更肯定（「不會生效」），接近的講「可能不會生效」。
2. **生成之後的品質統計**：逐行列出偏好、目標次數、實際次數，
   未達標時**講得出是哪一條規則擋住**。

可以判斷的五種原因（全部只靠生成結果推，不重跑排表）：

| 原因 | 怎樣判斷 |
|---|---|
| 撞到每季上限 | 那個人這一季的總派工數 ≥ 他的上限 |
| 該崗位格數不足 | 該崗位這一季要排的主日數 < 目標次數 |
| 當天已在其他崗位服侍 | 該主日他有其他派工 |
| 同一崗位連續兩週（準硬規則） | 前一週或後一週他做了同一個崗位 |
| 一般的平均分配 | 以上皆非 |

#### 兩個刻意的判斷

**「未達標」的門檻用 0.5 而不是 0。** 目標值本身是小數（平均 ＋ 偏好），
差 0.3 次不算「沒有生效」，只是四捨五入。用 0 做門檻會令幾乎每一行
都報一堆原因，而真正有問題那一行就淹沒了。

**每季上限只可以有一個算法。** 寫這一段時本來加了一個
「個人值 ?? Config 預設值」的簡化版，寫完才發現 `RoleImpact.gs`
已經有 `resolvePersonQuarterLimit_()`，而且它會查 `RuleSettings` 的
`TargetValue`（排表本身用的就是這一層）。兩個版本並存 ＝ 排表用一個上限、
報告用另一個 ＝ 又一次「同一個問題兩個答案」。
已經改成重用既有那個，只在外面包一層把「查不到」與「查到」分開。
`grep` 全域重名那一步就是在這裡抓到的。

**「查不到」與「查到，沒有人接近上限」一定要分開。**
兩者在畫面上長得一樣（都是沒有黃字），但意思完全相反。
`readQuarterLoadForWeights_()` 回傳 `{available, reason, byPerson}`，
未選季度／未有版本／讀取失敗三種情況都是 `available: false` 加一句人話原因，
前端會把那句原因印出來，不會假裝已經檢查過。

### 階段 C：區三第七個畫面「身分（堂委／執事）」

規格 4.3。新增 `src/WebAppRoles.gs`（六個 API）＋ 區三畫面。

#### 這個畫面的重心是「換屆」，不是逐行編輯

身分名單一年動一次。真正會用到它的時刻只有一個：換屆。
而換屆最容易做錯的事是**把舊的行刪走**——後果是**追溯性**的：

> `Roles` 是按日期判斷「那一日他是不是堂委」的。刪了舊行，
> 系統就會當他**由頭到尾都不是堂委**——上一季、上上季的職事表
> 全部會被追溯判成違反「報告限堂委」那條硬規則。
> 而那些季度早就寄了信、印了 PDF、做了事。

所以把「做對」做成一粒掣：輸入卸任日期 → 預覽（列出**全部**會被填
`EffectiveTo` 的行）→ 打字「確認」→ 逐行寫入 ＋ 逐行寫 `AuditLog`。

#### 幾個刻意的判斷

- **執行時後端自己重新算一次計畫**，不信前端傳回來那份。
  前端那份是幾秒前算的，期間可能有人在試算表改過。
- **已經有 `EffectiveTo` 的行不會再碰**——他們已經卸任過，
  不應該被改成另一個日期。生效日還沒到的也不碰（可能已經預先加了下一屆）。
- **生效日比卸任日還遲 ⇒ 擋住，不執行。** 寫下去就會出現
  「生效日比生效至遲」的行，而那種行在日期判斷裡永遠不成立，
  等於那個人靜靜地沒有了身分。
- **找不到的行會報出來（`failed`）**，不會靜靜略過。
  靜靜略過就是「做了一半但報告說全部成功」。
- **認不出的身分代號會標出來**（`unknownRoleCode`）。
  打錯字的話那條規則會靜靜失效，而畫面看起來完全正常。
- **生效日可以留空**（＝一直以來都是），跟 `Roles.gs` 的讀取邏輯一致。
  強制要填會逼幹事亂填一個日期，而那個日期會變成真相。
- 畫面**永遠不顯示英文身分碼**：下拉的 `value` 是代號，`textContent` 是中文；
  後端一律連 `roleLabel` 一起回，前端不維護第二份對照表。

「檢查名單」那個唯讀提示直接重用既有的 `buildRoleOverviewRows_()`，
不另寫一份會走樣的。讀不到時只回一句人話，上面的名單照樣可以用。

### 階段 D：區三第八個畫面「暫時不做某崗位」

規格 4.5。新增 `src/WebAppExclusions.gs`（四個 API）＋ 區三畫面。

#### 兩件必須分得開的事

畫面上逐字寫著（清單頁與新增頁各一次）：

```
崗位資格 = 這個人從來沒做過這個崗位。
暫時不做 = 這個人做得到，但這一段時間不排他。
```

混淆的後果：幹事想「這半年不要排他做主席」，就去取消他主席的資格
——而那是「以後永遠不會排他」，而且日後想恢復時，
「他做過多少次」這個歷史已經斷了。

#### 解除 ＝ 填 `EffectiveTo`，不是刪行、不是 `Active=FALSE`

`Active=FALSE` 的意思是「這一行**由頭到尾**都不算數」。
這樣舊季度的職事表就會變成「當時本來可以排他」——而事實上當時是真的
不應該排他。填 `EffectiveTo` 才是「那一段時間確實生效過，由今日起不再生效」。
跟 `Roles` 換屆完全一樣的道理。

`apiLiftExclusion()` 做成**獨立 API** 而不是叫呼叫端用 `apiSaveExclusion()`：
獨立入口才**結構上**保證它只寫 `EffectiveTo` 一欄，不會順手改到
`Active` 或原因，而不是靠呼叫端記得。它也在 `AuditLog` 記成
`EXCLUSION_LIFT`，日後一句 filter 就查得完。

解除日早過生效日會被擋——寫下去就會出現一段負長度的生效期，
等於那條限制從來沒有存在過。錯誤訊息會指出「如果真的想當它沒存在過」
應該改用哪一個做法。

#### 其他

- **原因必填**（後端擋，不靠前端）。三個月之後，一條沒有原因的限制
  沒有人記得為什麼，於是沒有人夠膽解除它——那個人就永遠不會再被排到那個崗位。
- **打錯 `PostID` 會標出來**（`unknownPost`）。崗位表沒有那個代號的話，
  這一條限制根本不會生效，而畫面看起來完全正常。
  新增／修改的崗位下拉只列真實存在的崗位，所以正常路徑打不到錯。
- 過期的摺入「已解除」一節，**不刪**；已解除那些不再顯示「解除限制」按鈕。
- 修改畫面的「啟用」勾選框寫明它不等於解除，取消時再警告一次。

**區三頁尾那句「這兩個畫面下一輪會搬上來」已經拆走**（測試會盯住）。
留著它會令幹事去選單找一個已經在這裡的功能。

### 階段 E：從出席系統（HWCAS）補電郵搬上 Web

規格 4.2。新增 `src/WebAppHwcas.gs`（`apiHwcasPreview`／`apiHwcasApplySelected`）。

#### 這個功能最危險的地方

HWCAS 是一個唯讀外部來源，配對靠姓名。配對錯了的後果是
**把甲的電郵寫進乙的資料**——之後乙收到甲的職事表，甲永遠收不到。
而畫面上完全看不出：兩個人都有電郵，職事表照樣印著兩個名。

名單裡真的有幾位姓名只差最後一個同音字的弟兄姊妹。
他們是**不同的人**，絕對不可以自動合併。

所以：選單版的兩步（產生初稿 → 整批套用）在 Web 版改成三步
**預覽差異 → 逐行勾選 → 套用**，而且：

- **預設全部不勾**，而且**沒有「全選」捷徑**
  ——有了那粒按鈕，「逐個看過」就會變成「撳一下」。
- 同名多人（`AMBIGUOUS`）、認不出（`NONE`）**連勾都不能勾**。
- 會蓋掉一個不同的現有電郵 ⇒ 紅色警告
  （蓋掉之後，本來收到信的那位就會停止收到，而沒有任何訊號）。
- **風險分級在後端做**，前端只負責畫紅色。判斷邏輯留在一處。

#### 其他刻意的判斷

- **預覽不寫 `NameMapping_Draft`。** 選單版會把初稿寫進一張工作表；
  Web 版不寫——「我只是想看一下」不應該靜靜改了試算表，
  而且會跟選單版那份表互相覆蓋。
- **後端不信前端傳來的任何值。** 前端只傳 `personId` 清單，
  電郵、會眾編號一律由後端重新讀一次 HWCAS，並**逐行再驗一次** `canApply`
  ——前端那份預覽可能是幾分鐘前拿的。
- **讀取與配對完全重用 `HwcasSync.gs`** 的 `readHwcasMembers_()`
  與 `buildHwcasDraft_()`，不另寫一份。自己再寫一次讀取可能讀到不該讀的欄；
  自己再寫一次配對就會有一天一邊認得、一邊認不得。
- 會眾編號**只在 HWCAS 真的有值時才寫**——空白覆蓋下去就是用一個
  「沒有資料」洗走一個真實資料。
- 略過的行一定報出來。「勾了 10 個，寫了 7 個，沒有人知」是最差的結果。
- `HWCAS_SPREADSHEET_ID` 未設定時回一個獨立旗標 `notConfigured`，
  前端不靠字串比對——靠字串比對就會在改文案那天靜靜壞掉。

**對 HWCAS 一律唯讀**：這個檔案完全沒有任何對 HWCAS 試算表的寫入呼叫。

### 階段 F：區四——只搬七個工具

規格第五節。新增 `src/WebAppZone4.gs` ＋ `src/ui/ScriptZone4.html`
（區四由共通層搬出來，成為自己的檔案）。

#### 為什麼只搬七個，不是全部八十幾個選單項目

| 判斷 | 理由 |
|---|---|
| 搬七個 | 幹事日常真的會用到 |
| 其餘留在選單 | 那批是診斷／維護工具（體檢、參數掃描、上線前檢查、補建欄位…），使用者是 Ivan 或 IT，不是幹事 |

搬上來只會令幹事在一堆他一世都不會撳的東西裡面找他真正要撳那一粒
——「找不到」和「撳錯」兩樣都會出事。

留在選單還有另一個好處：**選單版是安全網**。
Web 介面爆掉的時候（例如上一輪那個 HtmlService 樣板 bug 令整個介面開不到），
選單仍然行得。所以本輪**一行都不改選單版的行為**，測試會盯住七個
`run*_()` 入口仍然存在。

搬上來的七個：重新生成初稿（覆蓋式）、匯出職事表 PDF、產生個人 PDF、
補寄未收到的人、核對職事表、列出待補格子、草稿覆核報告（給堂委看）。

#### 「算」與「顯示」拆開

選單版的 `run*_()` 全部會叫 `ui.alert()`，在 Web App 環境沒有 Sheets UI，
一叫就爆。所以 `WebAppZone4.gs` **完全不呼叫任何 `run*_()`**，
只叫它們裡面的純運算函式（`exportRosterPdf()`／`generatePersonalPdfBatch_()`／
`listPendingBackfillCells_()`／`planMakeupSend_()`／`measureSoftRuleMetrics_()`…）。

**這一輪不需要動那些純運算函式**——它們早就為了寫離線測試而拆好了，
只是多一個呼叫端。這是幾輪之前那個決定現在收到的利息。

#### 幾個刻意的判斷

- **版本下拉一律寫人話**：`第 2 版　2026-12-04 11:20　套用修改申報後`。
  原因文字用共用的 `buildVersionBasisText_()`（跟狀態卡同一份翻譯表），
  時間用共用的 `normalizeSentAt_()`，不會兩邊各有一套。
- **「列出待補格子」不收版本號**：它問的是「現在還有哪幾格未填」，
  而「現在」永遠是最新版本。叫幹事揀只會令他對著一份跟現況無關的清單去填格。
- **「重新生成初稿（覆蓋式）」要打字確認**，而且明確指出
  「如果只是想套用剛才改的幾格，請用區一的『儲存並確認』」
  ——不講的話，幹事會用一個核彈去做一件小事。
- **匯出 PDF 的檔案大小由 Drive 拿**。寫這一段時本來寫成
  `result.fileSize || 0`——而 `exportRosterPdf()` 根本沒有回 `fileSize`，
  那種寫法永遠印「0 B」，而「0 B」看起來是一個真實而且嚇人的數字。
  改成從 `DriveApp` 拿，拿不到就誠實寫「（查不到檔案大小）」。
- **「補寄未收到的人」只列真的寄過的階段**。列一個從來沒寄過的階段出來，
  幹事揀完只會看到「所有人都收到了」，而那個講法是錯的（根本一封都沒寄過）。
  執行時後端自己重新算一次計畫，不信前端傳回來那份。
- 錯誤一律三段式，而且**指回選單**——那邊是安全網。

#### 順帶記下的一個測試寫法

`tests/zone4_tools.test.js` 有好幾條斷言是「不可以出現某個寫法」，
而**解釋那個寫法為什麼不對的註解，本身就含著那個寫法**。
所以測試加了一個 `stripComments()`，先剝註解再檢查。
不這樣做的話，寫得越清楚就越容易被自己的測試抓住，
而唯一的「修法」就是把註解寫得含糊——本專案已經撞過四次。

### 階段 G：年度工具搬入區二 ＋ 規則「人話版」審閱表

#### G1　年度工具

`產生下一年度四個季度`、`產生年度合堂建議` 搬入區二「確認特別主日」底部。
兩個都是寫入動作，所以：先預覽（列出**全部**會新增的行）→ 打字確認
→ 執行 → 寫 `AuditLog`。執行時後端自己重新算一次計畫，不信前端。

合堂建議有一個容易漏的情況：**找不到 `QuarterID` 的行寫下去等於垃圾行**
（全系統都讀不到）。那一點要在**預覽**就標明會略過，不能寫完才發現。

選單版的兩個 wizard 一行都沒改（測試盯住）。

#### G2　規則審閱表

`RuleSettings` 上面寫著一個 0 到 1 之間的小數。堂委看著那個數字是
**沒有辦法決定任何事**的——他們不知道單位、不知道調大調小是想怎樣、
更不知道調完之後實際會有什麼分別。

所以審閱表把每一條寫成一句人話，而且**小數一律換算成
「N 個主日之中大約 M 個」**——那是堂委腦裡本來就有的單位。

##### ⚠️ 分母不可以寫死 13

有些季度是 12 或 14 個主日，而整句話的意思完全靠那個分母。
分母錯了，堂委就會照著一個錯的比例做決定，而那份表看起來一切正常。
`resolveRuleReviewWeeks_()` 從最新季度的 `ServiceDates` 數出來；
**查不到就不換算**，改成寫百分比並且明講「查不到一季有幾多個主日」。
硬用 13 換算出來的數字看起來很確定，但可能是錯的。

##### 三條不可以妥協的界線

1. **匯入只讀「堂委決定」與「備註」兩欄，其餘一律忽略。**
   那份表會在幾個人手上傳來傳去，任何一格都可能被順手改過，
   而「改了一個顯示欄就靜靜改了系統」是最難查的一種事故。
   測試特意把「現時設定」「可以改成」兩欄填成亂七八糟的東西，
   證明結果不受影響。
2. **硬規則一律不可以由匯入改動。** 就算堂委揀了「要討論」，
   系統只把意見記入 `AuditLog`（`RULE_REVIEW_NOTE_ONLY`），不改 `Enabled`。
   硬規則是「一定不可以違反」的東西，不應該由一份試算表的一格下拉去關掉。
3. **匯入之後還要幹事逐條接受或拒絕**，預設全部不接受。
   三欄對照：現時 ／ 堂委決定 ／ 換算成系統的值——跟掣 1 同一個模式。

##### 寫的過程抓到自己一個真 bug

比較「有沒有改動」本來寫成「比原始小數」。
現時值 0.63 顯示成「13 個主日之中約 8 個」，而 8 ÷ 13 反推回去是 0.62
——**揀「維持現狀」反而會靜靜把 0.63 改成 0.62**。
每次匯入都漂移一點點，幾輪之後就跟堂委當初決定的差很遠，
而每一次看起來都「跟顯示的一樣」。已改成**比次數**。

反推不到（堂委自己打了一句話、次數超出範圍、分母查不到）一律回 `null`
＝那一條不會被改動，**不會估**。估錯一個規則值的後果是整季排表偏一邊，
而沒有人會知道是哪裡出事。

##### 順帶改了靜態掃描器一條規則

`apiExportRuleReviewSheet()` 在一個 `SpreadsheetApp.create()` 出來的
**全新試算表**上面做結構，被「first-run 不對稱」規則報了一項。
在全新試算表上「已經存在」這件事**結構上不可能發生**，所以加了這個豁免。

這不是把掃描器改鬆：原本那條規則講的是「同一份表可能已經存在」。
加一個會令規則失效的例外（例如「有 try/catch 就當處理了」）才是改鬆。
而且豁免只看該函式本身，不看整個檔案——看整個檔案的話，
一個檔案裡只要有任何一處 `create()`，其餘真正有風險的函式就會一起被豁免。

# 第二十九輪批次階段 A4：規則審閱表逐條稽核

> **這份表是給堂委開會用的。一句講反了，就會換來一個錯的決定，
> 而系統會忠實執行那個錯決定。對外的文字同程式碼一樣是系統的一部分。**

逐條核對三件事：（一）顯示的單位同 `TargetValue` 的實際單位一致；
（二）「這一條在做什麼」有沒有同排表引擎講反；（三）有沒有一條在講
「避免」但實際是「容許」（或者相反）。

`RULE_IDS` 現時共 **18 條**（9 硬、1 準硬、8 軟），不是 15 條。

## 一、講反了的（🔴 會導致錯誤決定）

| 規則 | 舊文字 | 實際行為 | 本輪處理 |
|---|---|---|---|
| `SOFT_ANNOUNCE_RELIEF` | 「報告盡量**不要**連續兩週」「連兩週會比較辛苦」 | `computeAnnounceReliefBonus_()` 在連續比例落後於進度時**給上週那位加分**——系統是主動讓報告連續，這是排不出人時的洩壓閥 | 改成「報告**可以**連續兩週由同一個人擔任」＋「這是系統的洩壓閥……收得太緊會令某些週排不出來」 |

只有這一條是真正講反。其餘 17 條的方向都對。

## 二、單位／分母（🔴 同一條規則在不同地方用了不同分母）

比例型規則有兩種單位，本輪加了 `RULE_REVIEW_UNITS` 標明，
換算同顯示兩邊讀**同一個**欄位（`ruleReviewPlainEntry_()` 的 `unit`）。

| 規則 | 單位 | 母體（講給堂委聽的總數） | 換算分母（引擎真正乘的數） |
|---|---|---|---|
| `SOFT_CHAIR_EQ_ANNOUNCE` | 逐個主日 | `weeks` | `weeks`（`ratioState.weeksCounted`） |
| `SOFT_CHAIR_PREFER_DUAL` | 逐個主日 | `weeks` | 引擎其實是 `dualAssigned + 1`；每個主日排一次主席，數字上約等於 `weeks` |
| `SOFT_ANNOUNCE_RELIEF` | 相鄰兩個主日 | **`weeks - 1`** | **`weeks`** ← 見下 |

### ⚠️ 一個要 Ivan 拍板的分歧

Prompt 要求相鄰對用 `weeks - 1` 做分母（`0.27 × 12 ≈ 3 對`）。
但排表引擎的 `isBehindTargetPace_(count, weeksCounted, target)` 是
`count < target × weeksCounted`，而 `weeksCounted` 數的是**全部主日**
（連第一週都數，雖然第一週不可能有「連續」）。

用引擎自己那條式模擬（13 個主日、目標 0.27）：

| | 對數 |
|---|---|
| 引擎實際排到 | **4 對** |
| `round(0.27 × 13)` | 4 對 |
| `round(0.27 × 12)` | 3 對 |

所以本輪的做法是：**量詞同母體跟單位，換算分母跟引擎。**
匯出會寫「**12 對相鄰的主日之中約 4 對**」——
量詞同母體修好了（不再是「13 個主日之中約 4 個」），
而個數字仍然是系統真正會做的那件事。

如果改成 `weeks - 1`，表會寫「約 3 對」而系統排到約 4 對，
那就是**第 6 類 bug 的新一次**（同一條規則在不同地方用了不同分母），
只是這次錯的一邊是給堂委看的那一份。

**兩條可以走的路，要 Ivan 決定：**
1. 接受現狀——表寫「12 對之中約 4 對」，不動排表行為。（本輪採用）
2. 改引擎——`ANNOUNCE_RELIEF` 的分母改成 `weeksCounted - 1`。
   這會改動每一季的排表結果，屬於行為改動，本輪沒有做。

## 三、講得不夠，堂委會據以做錯決定的（🟠 本輪一併修好）

| 規則 | 問題 | 修法 |
|---|---|---|
| `SEMI_NO_CONSECUTIVE` | 「同一個崗位盡量不要連續兩週」——但引擎只在 `post.allowConsecutive !== ALLOW` 時檢查，而報告正是 `ALLOW`。同一份表上這一條同洩壓閥那一條直接打架，沒有一句講清楚 | `what` 加「個別崗位可以豁免——報告就是豁免的」 |
| `SOFT_QUARTER_DISTRIBUTION` | 引擎是 `if (PERSONAL_QUOTA) {...} else if (QUARTER_DISTRIBUTION) {...}`——**二選一**。個人配額開着時，這一條完全沒有跑過，堂委卻會花時間調一個不會有任何效果的數字 | 加 `note`：「那一條開着的時候，這裏改什麼都不會有分別」 |
| `SOFT_CHAIR_PREFER_DUAL` | 那個數字量的是「排主席時有多少次揀了雙資格的人」，不是「有多少個主日真的兼任了」（那是上一條規則）。兩個數字很接近，混淆之後會令堂委調錯規則 | `what` 明講數字的意思 |
| `SOFT_ROLE_POST_FOCUS` | `ScopePostIDs` 一個崗位都沒填時，`evaluateRolePostFocus_()` **直接當規則未生效**；但表上仍然寫「有生效（其他崗位扣分，強度 2）」——一句大話 | 讀實際的 `ScopePostIDs`，一個都沒有時寫「開着，但沒有設定指定崗位，所以實際上沒有作用」；有的時候逐個列出中文崗位名 |
| `HARD_MUTEX_GROUP` | 只列了組裡第一個崗位（`現時有 1 組：主席。`）——一句講不出對手是誰的衝突規則等於沒講 | 逐組列出全部成員；一個成員的組明講「實際上不會擋住任何安排，請檢查是不是漏了設定另一個崗位」 |

## 四、核對後沒有問題的

`HARD_ELIGIBILITY`、`HARD_DISTINCT_SLOT`、`HARD_UNAVAILABLE`、
`HARD_COMMUNION_FIRST_SUNDAY`、`HARD_NO_AUTO_PREACHER`、
`HARD_SPECIAL_SUNDAY_SKIP`、`HARD_ROLE_REQUIRED`、
`HARD_PERSON_POST_EXCLUDED`、`SOFT_MAX_PER_QUARTER`、
`SOFT_LOAD_BALANCE`、`SOFT_PERSONAL_QUOTA`、`SOFT_CHAIR_EQ_ANNOUNCE`
——共 12 條，方向同單位都對。

## 五、順帶抓到的兩個換算漏洞（測試寫出來才發現）

`rule_review_roundtrip` 掃全部單位 × 主日數 10–16 × 目標值 0.01–0.99，
抓到兩個會令「值 → 顯示 → 值」對不上的洞：

1. **「約 0 個」這個選項**存進 `TargetValue` 之後是 `0`，
   而 `0` 已經不是一個 0–1 之間的比例，下一次匯出會原樣印「0」。
   而且「一次都不要」根本不是一個目標值，是「關掉這條規則」，
   應該走 `Enabled` 那一欄。對第 9 條來說，「0 對」正正就是封死逃生口
   ——更加不應該做成一個一撳就揀到的下拉選項。
2. **`count === 分母`那個選項**換算出來是 `1.0`，同樣不再是比例。
   而且「每一個主日都要」是一條硬規則，不是一個目標值。

兩個都改成不生成該選項（`1 ≤ count ≤ min(母體, 分母 − 1)`）。
兩個都是同一個 bug class：**一個換算不回去的值被當成一個正常選項**。

# 第三十輪批次階段 B：兩類新靜態檢查

今次兩個 bug（`written is not defined`、參數次序調轉）**語法完全合法**，
`gs_syntax.test.js` 只 parse 不執行，所以一個都捉不到。
116 個測試全綠，真人一撳就爆。

## 為什麼是自己寫，不是 eslint

這個 repo **沒有 `package.json`、沒有 `node_modules`**。
為了兩條 lint 規則引入一整套 npm 依賴（而且 Apps Script 不是 eslint
開箱就認得的環境）代價不成比例。兩個掃描器都是零依賴的純 Node。

## B1　`tools/lint-undeclared.js`（未宣告變數）

### 做法

1. 把字串／樣板／正則／註解的內容換成**同長度的空白**——
   保留長度和換行，令括號配對和行號都仍然對。
2. **全部 `src/*.gs` 當成同一個全域範圍**（Apps Script 就是這樣，
   跨檔案共用全域）。逐個檔案獨立掃的話會滿屏假警報：
   `Constants.gs` 定義的 `SHEETS`／`COLUMNS` 在其餘 80 幾個檔案都用得到。
3. 逐個頂層函式收集「宣告了的名」（`const`／`let`／`var`／參數／
   內層函式名／`catch` 參數／箭頭函式參數），再逐個被讀取的識別字比對。

### 刻意的取捨

函式裡面**不分 block scope**：一個函式的全部宣告一律當成同一個平面範圍。

- 換來：捉不到「在 block 外面用一個 block 裡面宣告的 `let`」。
- 換到：**零假警報**。

一個會吵假警報的 lint，三日之後就會有人加一堆豁免令它閉嘴，
然後它就永遠捉不到東西——那個結果比沒有好不了多少。這裡揀「少報但準」。

### 跑一次的結果：15 項 → 2 個真 bug ＋ 13 個假警報

假警報全部修好了掃描器本身（不是加豁免）：

| 假警報 | 成因 | 修法 |
|---|---|---|
| `g`／`gi`（7 處） | 正則的**旗標**沒有一併清走，`/x/g` 的 `g` 變成裸識別字 | 清走正則之後連旗標一起清 |
| `qb`／`shouldCount`／`specialSkip`／`manualPending`（4 處） | `let a = 0, b = 0;` 先取第一個 `=` 之前那段再拆逗號 ⇒ 第二個名整個丟失 | **先按最外層逗號拆，再各自取 `=` 之前** |

### 剩下的 2 項都是真 bug

1. **`SeasonRehearsal.gs` 的 `written`**——上一輪為了過
   `diagnostics_written_count` 這條不變式（禁止 `const written = tryWriteDiagnostics_(...)`）
   把整個賦值拆走，**但漏了清走下面那個引用**。
   結果就是 Ivan 實測看到的：對話框寫「已寫入 Diagnostics…共 170 行」，
   而 `Diagnostics` 裡面根本沒有那份報告。
   ⚠️ **一條太嚴的不變式造出了一個新 bug。**
   那條不變式本輪收窄成「變數名不可以令人誤會成行數」
   （`written`／`writtenCount`／`rowsWritten` 不准，`wroteOk` 可以），
   並加一條「接住了的 boolean 不可以直接串成『共 X 行』」。

2. **`Mailer.gs:690` 的 `folder`**（Ivan 沒有報過，掃描器自己找到的）——
   `lookupExistingPersonalPdf_()` 裡 `folderName: folder.getName()`，
   但那個 `folder` 在第二十六輪改用 `findRosterPdfFile_()` 之後就沒有再宣告。
   即是**每次寄個人 PDF 附件都會 `ReferenceError: folder is not defined`**
   ——步驟 4／5 的整條寄送路徑。
   修法：新增 `describePdfFileFolderName_(file)`（`PdfFolders.gs`），
   由檔案自己問回它在哪（新子資料夾／舊平鋪兩種都對）。

## B2　`tools/lint-arg-order.js`（內部呼叫的參數次序）

### 規則

> 呼叫一個內部函式（名以 `_` 結尾）時，如果傳入的**變數名**
> 同該函式**另一個位置**的參數名相同，就報警。

`findStateViolations_(context, resolved.state)`：第 1 個位傳了一個叫
`context` 的變數，但第 1 個參數叫 `state`、第 2 個才叫 `context` → 報警。

### 刻意的收窄

1. 只掃 `src/*.gs` 裡面**自己定義**的函式（Apps Script API 沒有參數名可比對）。
2. 只比對**簡單識別字**。`a.b.c` 這類運算式一律略過——
   分析它們要一個真 parser，而且假警報會多很多。
3. 傳入名跟該位置參數名一樣 ⇒ 不報；傳入名根本不在簽名裡 ⇒ 不判斷。
4. 少過兩個參數的函式不掃（沒有「次序」可言）。

### 跑一次的結果

**內部函式 801 個、呼叫點 1476 處，0 項。**
（本輪階段 A 已經把那兩處修好；沒有其他未爆的。）

⚠️ 一個「現時 0 項」的掃描器證明不到它識捉東西。所以
`tests/lint_static_checks.test.js` 會**真的把 `WebAppSaveConfirm.gs` 那一行
改回錯的版本、跑一次掃描、再還原**，確認它捉得到、而且講得出
「第 1 個應該是 `state`」。

### 豁免

同一行加 `// arg-order-ok：<理由>` 就豁免，而且**理由要逐個寫明**。
**現時 `src/` 一個豁免都沒有**（有測試鎖住）。每加一個都要在這裡寫低理由。

## C1　演練工具的步驟次序排錯了

舊次序把「儲存並確認」排在「寄給堂委審閱」之前。

## D1　互斥組只列到一個成員

實測：`Posts` 裡 `CHAIR` 和 `COMMUNION` 兩行都有 `CHAIR_COMMUNION`，
資料是對的，但匯出只列到「主席」。

**成因：`buildRuleReviewContext_()` 用 `readPostsNormalized()` 讀組員，

⚠️ 一個 `Active=FALSE` 的組員靜靜消失之後，畫面上剩一個成員的組
**看起來跟「配置漏了」一模一樣**，而正確的下一步完全不同：

（`postNameById` 和身分要求仍然用已過濾那個——那兩樣講的是「現在生效的崗位」。）

⚠️ **這只是最可能的成因，沒有在真實試算表上驗證過**（本輪禁止讀試算表）。
如果 `COMMUNION` 其實是 `Active=TRUE`，新寫法一樣會把它列出來
（因為現在讀的是原始行），所以無論哪一種，下一次匯出都會顯示真相。

> 順帶一提：那句「請檢查是不是漏了設定另一個崗位」是上一輪自己加的，
> 不在需求裡——而**正正是靠它才發現這個 bug**。保留。

## D2　相鄰對的分母：審閱表要跟 `Verify.gs`，不是跟排表引擎

上一輪把 `ADJACENT_PAIR.ratioDenominator` 設成 `weeks`（13），
理由是「跟排表引擎」。**那個決定是錯的。**

系統自己的品質統計用的是 `weeks - 1`：

```
Verify.gs 的 measureAnnounceRelief_()：
  for (let i = 1; i < dates.length; i++) pairs++;   ⇒ 12 對
報告輸出：報告（ANNOUNCE）洩壓閥　25.0%　3/12 對
```

堂委在審閱表看到的數字，跟幹事事後在品質統計看到的數字，
**一定要同一個分母**。所以改回 `weeks - 1`：
`0.27 × 12 = 3.24` ⇒ 「12 對相鄰的主日之中約 3 對」。

### ⚠️ 仍然未解決的分歧（要 Ivan 拍板）

排表引擎的**進度控制** `isBehindTargetPace_(count, weeksCounted, target)`
用的 `weeksCounted` 數的是**全部主日**（連第一週都數，
雖然第一週不可能有「連續」）。用它自己那條式模擬，
13 個主日、目標 0.27 ⇒ 實際會排到約 **4** 對，而不是 3 對。

所以現在的狀態是：**審閱表和品質統計一致（分母 12），
但引擎自己的進度控制多算一格。**

改引擎（`weeksCounted - 1`）會改動每一季的排表結果，屬行為改動，
本輪沒有做。三個地方之中兩個已經對齊，剩下那一個要你決定。
