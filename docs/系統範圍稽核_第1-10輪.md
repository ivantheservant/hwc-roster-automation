## 第五輪批次（本輪，2026-08-14）：Config 顯示、Requests 殘留偵測、PDF 管理、步驟4離線測試、效能複查

### 階段 A：Config 缺值顯示「undefined」的系統性修正

起因：Diagnostics 報告 `WEBAPP_ENABLED` 顯示成 `undefined`——原因是這個
Config Key 從未在 `ConfigSeed.gs` 註冊，程式碼退回用內建預設值，但顯示
那一行是直接 `String(config[KEY])`，沒有處理「Config 完全沒有這個 Key」
的情況。

修正做法：新增共用函式 `describeConfigValue_(config, key, fallback)`
（`src/Config.gs`），回傳 `{value, usedFallback, display}`，`display`
在使用預設值時會附註「（Config 未設定，用預設值）」。**關鍵細節**：
判斷「是否缺值」用嚴格的 `raw === undefined || raw === null || raw === ''`，
不是簡單的 `!raw`——否則 `DRY_RUN=false`／`WEBAPP_ENABLED=false` 這種
「明確設定為 false」的情況會被誤判成「沒設定」。

已找出並統一修正同一類問題的**全部**出現處，不是只修 `WEBAPP_ENABLED`
一個：`src/Diagnostics.gs` 的 `SEND_HOUR_LOCAL`／`SYS_TIMEZONE`／
`DRY_RUN`／`MAIL_SUBJECT_PREFIX`／`WEBAPP_ENABLED`／`WEBAPP_ALLOWED_EMAILS`／
`REMIND_STUCK_DAYS`／`REMIND_STUCK_MAX_COUNT`／`REMIND_DEADLINE_DAYS`，
以及 `src/Menu.gs` 的 `runReloadConfig_()`（原本 DRY_RUN 那一行也是同樣
的直接 `String()` 寫法）。

`ConfigSeed.gs` 已確認補上 `WEBAPP_ENABLED`（預設 `FALSE`）、
`WEBAPP_ALLOWED_EMAILS`（預設空白）兩個 Key 的正式註冊（只改程式碼/seed，
沒有寫入試算表，`getConfigKeySeeds_()` 已包含這兩個 Key）。**Ivan 需要
自行執行「維護 ▸ 補建 Config 參數」這個既有選單項目**（`runSeedConfigKeys_()`），
才會把這兩個新 Key 真正寫進線上 `Config` 工作表——這個選單項目本身早就
存在，這次沒有新增，只會 append 缺少的 Key 到最底，不會改動任何既有
Key 的值，執行前會先列出將新增的內容要求確認。（提醒：「設定 ▸ 重新
載入設定（唯讀）」`runReloadConfig_()` 純粹是清快取＋重讀顯示，**不會**
新增任何 Key，不要跟「補建 Config 參數」搞混。）

回歸測試：[`tests/config_display_fallback.test.js`](../tests/config_display_fallback.test.js)——
涵蓋多個 Key 的缺值 fallback、明確設值不被覆蓋、空字串視為缺值、
`false` 不被誤判成缺值、模擬 Diagnostics／Menu 訊息字串確認不含
`undefined`／`null` 字樣。

### 階段 D：步驟 4「正式發出」離線回歸測試

這是五步驟流程裡唯一一個還沒在 2027T1 上實際跑過的步驟（最重、影響面
最大：寄給約 60 人、產生約 60 份個人 PDF），本輪只做離線邏輯測試，
**沒有實際執行**（禁止真的寄電郵、禁止 deploy）。測試涵蓋七項既定行為，
全部通過：

1. **收件人組成** = 依 `EmailRecipients.Stage` 篩選的名單 + 本季度有
   被排班的個人，去重（不會漏、也不會重複）。
2. **有排班但沒有 email → `SKIPPED_NO_EMAIL`**，不是 `FAILED`（區分
   「刻意略過」與「真正失敗」）。
3. **`OFFICIAL` 不包含零排班的人**——這類人只會出現在「步驟 5：改動後
   重發」（`RESEND`）的收件範圍，`OFFICIAL` 階段本身就不考慮他們。
4. **個人 PDF 缺件 → `ERROR_PDF_MISSING`**，不會讓整批中斷，其餘收件人
   照常處理。
5. **Stage 前置條件**：只有 `REQUESTS_APPLIED` 允許執行步驟 4，其餘一律
   拒絕（`requireQuarterStage_()`）。
6. **執行後 Stage → `OFFICIAL_SENT`**，且流程設計上不能倒退回前面的
   Stage。
7. **`DRY_RUN=TRUE` 時全部記錄為 DRY_RUN，零真實寄出**——這次全程在
   `DRY_RUN=TRUE` 下測試，沒有真實寄送的風險。

額外重新確認 `assertOfficialNotFromAutomationTrigger_()` 這道結構性
防護在本輪新增的收件人組成邏輯下依然沒有被繞過（見 A4「`OFFICIAL`
永遠不由自動排程觸發」）。

回歸測試：[`tests/step4_official_send.test.js`](../tests/step4_official_send.test.js)。

### 階段 E：個人 PDF 生成效能複查與 6 分鐘執行上限風險評估

**E1／E2：重新量度＋批次策略評估結論——現行實作已經是最佳化，只找到
一個小效能缺口並已修正，其餘沒有再改。**

重新讀 `src/PdfBatch.gs` 全文，確認：

- highlight 格式化早就是共用 render context 的整批寫入
  （`openPersonalPdfRenderContext_()`／`applyPersonHighlightToContext_()`，
  見 A5），58～60 人的批次只複製一次工作表，不是逐人複製，這部分已經
  沒有進一步可安全批次化的空間——A5 的結論在本輪依然成立，本輪沒有
  再改動這部分程式碼。
- 「跳過已存在的 PDF」判斷**本來就是一次過列資料夾內容**（呼叫端在
  `generatePersonalPdfBatch_()` 用 `listExistingFileSizes_(folder)`
  把整個資料夾內容讀成一個 `Map<檔名,大小>`，只查一次 Drive API），
  不是逐人查——這點跟本輪任務指示原本擔心的「是不是逐個檔案查」的疑慮
  相反，程式碼一開始就是對的。

但重新讀 `generateOnePersonalPdf_()` 的既有查詢分支邏輯時，發現一個
真實但小的浪費：當呼叫端要求 `forceRegenerate=TRUE`（例如手動「強制
重新產生全部 PDF」）時，呼叫端傳入的 `existingFileSizes` 其實是 `null`
（見 `generatePersonalPdfBatch_()` 的呼叫端邏輯），於是程式仍然會為
**每一個人**多執行一次 `folder.getFilesByName(fileName)`（真實 Drive
API 查詢），查完的結果卻完全用不到——因為 `forceRegenerate=TRUE` 時，
`!forceRegenerate && alreadyExists` 這個判斷式永遠是 `false`，一定會
往下重新產生。已修正為 `forceRegenerate=TRUE` 時整段查詢與判斷完全
跳過（`src/PdfBatch.gs`）。影響：強制重新產生 60 人份 PDF 時，省下
60 次多餘的 Drive API 呼叫（單次查詢耗時雖小，但累積 60 次在 Apps
Script 執行時間與 API 配額上都有實際節省，且原本這個查詢完全沒有
產生任何有用的效果，純粹是浪費）。

E4 回歸測試：[`tests/pdf_batch_perf.test.js`](../tests/pdf_batch_perf.test.js)——
驗證修正前後行為完全不變（`forceRegenerate=FALSE` 且已存在達標檔案
仍然略過；不存在或大小不足仍然重新產生；`forceRegenerate=TRUE` 不論
是否存在都一定重新產生），並且用呼叫次數計數的假查詢函式證明
`forceRegenerate=TRUE` 時查詢函式確實完全沒有被呼叫（修正前會被呼叫，
修正後不會）。

**E3：Apps Script 6 分鐘執行上限風險評估——現有機制已經足夠，不需要
再設計新的續跑方案。**

本輪任務原本預期可能需要「設計（不實作）一個可續跑的方案」，但重新讀
`PdfBatch.gs` 發現這個方案**早就存在且已經在運作**，不是缺口：

- `PDF_BATCH_TIME_BUDGET_MS`（`Constants.gs`，240000ms＝4 分鐘，刻意
  比 6 分鐘上限留有安全餘裕，讓函式有機會在真正逾時前主動停止並儲存
  進度）作為批次迴圈的時間預算上限，迴圈內每處理完一人就檢查
  `已耗時 + 平均每人耗時 > 時間預算` 是否成立，成立就主動停止。
- 進度透過 Script Properties 持久化（哪些人已經處理完），下一次呼叫
  （不論是幹事再按一次選單、或是 time-based trigger 再次觸發）會從
  上次停下的地方接著做，不會重新開始、也不會重複處理已完成的人。
- `PDF_BATCH_SIZE`（seed 預設 25）是另一個獨立的、每次執行最多處理
  人數的上限，跟時間預算是兩個各自獨立的停止條件，任一個先到就停——
  這代表即使時間預算綽綽有餘，單次選單點擊也不會一次處理超過 25 人，
  60 人份預設需要至少 3 次點擊（或 3 次 trigger 觸發）才能全部完成。

> ⚠️ **2026-08-17 更正（第十九輪批次階段 E）**：下面這一段的單人耗時
> 估算**偏低而且比例寫反了**。當時寫「PDF 匯出約 0.8 秒／人、highlight
> 幾乎不佔時間」，2026-08-17 的 57 份實測是**倒過來**的量級：
> **每份 highlight 0.98 秒、匯出 3.33 秒、重試前等待 5.00 秒，
> 合計約 9.3 秒／份**（總計 530.3 秒，重試 47 次）。
>
> 對「會不會撞 6 分鐘上限」這個結論的影響：60 人 × 9.3 秒 ≈ 558 秒，
> **已經遠超 240 秒的時間預算**——換句話說，真正先到的停止條件是
> 時間預算，不是 `PDF_BATCH_SIZE=25` 這個人數上限。續跑機制本身
> 仍然有效（實測就是分 3 批完成的），所以「不需要另外設計新機制」
> 這個結論不變，但底下那句「實際限制批次次數的是人數上限」是錯的。
> 詳見本文件第十九輪批次階段 E。

**風險評估結論**（⚠️ 數字已被上面的實測推翻，保留原文以便對照）：
以當時量測到的單人耗時估算（PDF 匯出約 0.8 秒／人，
加上既有的 `PDF_EXPORT_PACING_MS` 節流間隔約 0.5 秒／人，highlight
因為已經整批處理、每人幾乎不佔額外時間），60 人份全部處理大約需要
60×1.3秒≈78 秒，遠低於 240 秒的時間預算——**實際限制批次次數的是
`PDF_BATCH_SIZE=25`這個人數上限，不是 6 分鐘時間上限**，25 人上限本身
就已經是一種保守的分批機制。換句話說，現有「時間預算＋人數上限＋
Script-Properties 續跑」三者組合已經是一個運作中的可續跑方案，能夠
安全處理遠超過 60 人的規模而不會真正撞到 6 分鐘上限，不需要再另外
設計新機制。E4 測試檔案內也用模擬迴圈驗證了「60 人在預設設定下需要
3 輪完成，且即使把時間預算故意調到極短，機制依然能分批收斂完成、
不會卡死」。

如果日後教會規模顯著成長（例如超過 200 人），才需要重新評估
`PDF_BATCH_SIZE` 是否要調高、或改成完全依賴時間預算而不設人數上限——
本輪沒有證據顯示現在有這個需要，屬於「有需要再處理」的項目，記在此處
供日後參考。

### 階段 F：全系統唯讀自我檢查整合——「維護 ▸ 🩺 全面體檢（唯讀）」

**F1 盤點**：全專案累積了 17 個各自獨立的唯讀檢查／自我檢查選單項目：
匯出關鍵狀態、預覽電郵範本、列出待補格子、PDF 內容自我檢查、電郵範本
自我檢查、AuditLog 摘要、檢查設定、重新載入設定、檢查 Config 行數、
檢查各版本派工紀錄、檢查個人 PDF 完整性、SOFT 規則與選人加權、欄標題
對照、個人版 highlight 定位、上線前檢查、查看自動排程狀態、檢查自動
排程條件。逐一讀完每個工具的實作後，發現它們天生分成三種不同性質，
不是同一類東西：

1. **可以完全自動跑、不需要任何輸入**的統計／自我檢查類（9 個裡有 8 個
   屬於此類，加上需要一次性輸入季度的上線前檢查湊成 9 個可整合項目）。
2. **需要幹事明確指定「季度＋版本」才有意義**的除錯／內容比對類（PDF
   內容自我檢查、檢查個人 PDF 完整性、列出待補格子）——本質是「我已經
   知道要查哪一版，幫我核對細節」，不是「幫我巡查全系統」。
3. **純開發除錯工具**（SOFT 規則與選人加權、欄標題對照、個人版
   highlight 定位）——輸出的是原始參數與座標，沒有「正常／異常」這種
   可以分級的健康狀態。

**F2 評估與實作結論**：把第 1 類的 9 個項目整合成新選單項目
「維護 ▸ 🩺 全面體檢（唯讀）」（`src/FullHealthCheck.gs` 的
`runFullHealthCheck_()`），一次過跑完並統一寫入 Diagnostics 的
「全面體檢」分區；第 2、3 類**維持獨立選單項目**，不勉強整合（理由已
寫在 `FullHealthCheck.gs` 檔頭註解，摘要：第 2 類塞進來會變成要對每個
季度每個版本各跑一次，失去「一次過」的意義；第 3 類沒有可分級的健康
狀態）。**全部 17 個既有選單項目原封不動保留**，這是額外多一個入口，
不是取代任何一個。

整合進「全面體檢」的 9 項：檢查設定、Config 行數、各版本派工紀錄、
電郵範本自我檢查、AuditLog 摘要、自動排程狀態、自動排程條件、全部
季度的 Requests 殘留＋矛盾組合（重用階段 B 的 `scanPendingRequestsAllQuarters_()`）、
上線前檢查（唯一需要輸入的一項——執行時會先問一次「要一併檢查哪個
季度？」，可留空跳過，其餘 8 項照常執行）。**刻意沒有整合「匯出關鍵
狀態」**：那個工具本身是「原始統計資料的完整匯出」而不是「health
check」，大部分欄位沒有天然的「有沒有問題」語意，而且會掃 RosterPDF
整個 Drive 資料夾（真實 API 呼叫，有實際耗時），如果每次全面體檢都
連帶跑一次，會跟階段 E 剛修正的「不做不需要的查詢」精神衝突——維持
獨立選單項目，全面體檢報告結尾會提示「如需完整原始狀態明細，另外
執行『匯出關鍵狀態』」。

Web UI 從未真正 deploy 過，全部只在 Node.js 離線環境測試過純邏輯部分

錯誤回呼有無漏接、前端拿到 undefined 會唔會白畫面、長時間操作有無
loading 狀態、重複快速點擊會唔會觸發兩次），逐一稽核結果：

**B1／B2 發現的真實問題（全部已修正）**：

1. **`closeWizardAndRefresh()`（全部五步驟共用，`ui/Script.html`）
   原本完全沒有錯誤處理**——這是「取消」「完成」「關閉」按鈕背後共用
   的同一個函式，原本直接 `await loadFlowState()`，`loadFlowState()`
   本身也沒有 try/catch。如果這時 `apiGetFlowState()` 失敗（Stage 被
   其他分頁改動、暫時性網路錯誤、`WEBAPP_ENABLED` 這時被關閉），會
   變成一個完全沒有處理的 rejected promise——精靈視窗關閉了，畫面卻
   完全沒有刷新、也沒有任何錯誤提示，使用者會誤以為操作完成，其實
   看到的是舊資料。**這是全部五個步驟的共用路徑，影響面最大的一個
   發現。** 修正：改為 `await runAction('重新整理狀態', loadFlowState)`，
   失敗時會用 `setStatus()` 顯示紅色錯誤文字，跟其他操作一致。
2. **步驟 4 兩個「繼續」按鈕（`step4CheckMissingPdf`／
   `step4SendPreview`）原本直接綁定沒有自己包 `runAction()` 的函式**
   ——這兩個函式是在精靈視窗**已經**渲染出來之後，使用者按鈕點擊觸發
   的，不在任何外層 `runAction()` 的範圍內，同樣是「失敗時完全靜默」
   的問題。修正：兩個按鈕的 `onClick` 改為
   `() => runAction('讀取確認資料', () => step4CheckMissingPdf(...))`
   這種寫法，直接包一層。
3. **`Quarters` 完全沒有資料時，首頁顯示空白畫面**——`loadQuarters()`
   原本 `quarters.length === 0` 時什麼都不做，頁面只剩標題與一個空的
   下拉選單，使用者無法判斷是「系統壞了」還是「本來就沒資料」。修正：
   新增 `else` 分支，明確用 `setStatus()` 顯示「目前 Quarters 工作表
   沒有任何季度資料，請先……」的說明文字。
4. **講員與翻譯側邊欄（`ui/PreacherFillSidebar.html`）的「儲存」
   按鈕沒有防止重複送出**——手快連撳兩下會送出兩次
   `apiSavePreacherTranslationEntry` 請求（寫入本身是冪等的，不會
   造成資料錯誤，但兩個請求的狀態訊息可能互相蓋過，畫面顯示會亂）。
   修正：送出請求前停用按鈕與輸入框，失敗時（`withFailureHandler`）
   重新啟用讓使用者可以修正重試。

**確認過沒有問題、不需要改動的部分**：

- `doGet(e)` 的 `e` 參數完全沒有被引用，不會因為缺少查詢參數而出錯。
- `callServer()`（`google.script.run` 的 Promise 包裝）本身的錯誤處理
  是完整的，問題出在上面 4 項「呼叫 `callServer()` 的地方」沒有正確
  被 `runAction()` 包住，不是 `callServer()` 本身有缺陷。
- 前端沒有任何地方使用 `innerHTML` 顯示未跳脫的動態資料（`make()`

## 第七輪批次（Opus 深度輪）：排表演算法保證、歸檔機制、補寄工具

本輪定位是「離線開發的最後一批實質工作」，三個階段都涉及演算法正確性
與資料結構判斷。**本輪找到並修正了一個真實的排表演算法 bug**，詳見下方
階段 A。

### ⚠️ 階段 A 最重要的發現：生成器會在資源緊絀時自動違反硬規則（已修正）

**這是本輪最重要的一項，也是「系統絕不自動違反硬規則」這句話第一次被
真正驗證。**

**問題**：`pickPerson_()`（`Generator.gs`）原本的邏輯是——先把「違反任何
HARD 規則」的候選人濾走，如果**濾完之後一個都不剩**，就退回「在全部候選人
之中挑違規最輕的一個硬派下去」，並標記 `assignSource=FORCED`。

這代表：只要某個崗位的合資格人選在某一週**全部**違反硬規則，系統就會
**即場製造一項硬規則違反**。最典型、而且真實會發生的觸發情境是：
**某個崗位（例如音響、司琴這類 pool 只有約 6 人的技術崗位）的合資格人選，
剛好全部在同一週申報了不能服侍。**

**實證**（用假資料，修正前後跑同一個情境）：

| | 該格結果 | 硬規則違反 |
|---|---|---|
| 修正前 | 派了一位當日已申報不能服侍的人，`assignSource=FORCED` | **1 項 HARD_UNAVAILABLE** |
| 修正後 | 留空 `assignSource=SKIPPED` ＋ 產生警告 | 0 項 |

**為什麼之前沒有被發現**：步驟 3／5 之後有「確認放行」關卡，會要求幹事
逐字輸入「確認放行」才能繼續——所以違反**最終**會被幹事看到。但違反在
**生成當下已經發生**，跟系統宣稱的「寧可留空，也絕不自動違反硬規則」
並不一致；而且 2027T1 那一次測試的資料沒有觸發到這個情境，統計數字看落
一切正常。**這正是「只靠一次輸出的統計數字看落合理」與「有自動化證據」
之間的分別。**

**修正**：`pickPerson_()` 現在在「候選人池非空、但全部違反 HARD 規則」時
一律**留空並發出警告**，跟「完全沒有合資格人選」走同一條路徑，交由
`summariseBlankAssignments_()` 歸入「系統應該排但排不出」的真正缺口統計，
幹事在步驟 1 完成畫面就直接看到。`FORCED` 這個 `assignSource` 值**刻意
保留不移除**——修正之前生成的版本可能已經有 `FORCED` 的列寫進
`RosterAssignments`，顯示層要繼續認得它（見 `Constants.gs` 的說明）。

### 階段 A 的第二個發現：`RANDOM_SEED` 對生成結果完全沒有影響（已緩解）

實測 30 個不同的 seed，30 份職事表**逐格完全一樣**。原因：seed 唯一的
用途是 `pickPerson_()` 的 `tieBreak`，而它只在兩位候選人的 `score` 與
`selectionScore` **完全相等**時才會被比較（見 `compareCandidates_()`）——
`selectionScore` 是連續浮點數，實務上幾乎不會完全相等。

**影響**：`generateBest()`（`MultiRun.gs`）的設計是「用多個不同 seed 各生成
一份，再揀最貼近歷史基準的一份」，預設跑 20 次。在這種資料下，等於**把
同一份表算 20 次**——而這是步驟 1 最耗時的部分（時間預算 3 分鐘）。

**處理方式（刻意保守）**：**沒有**改動選人邏輯去「製造」隨機性。理由：
任何令 seed 真正生效的改動（例如把相近分數視為同分再隨機決勝）都會改變
**每一份**生成的職事表，而本輪無法用真實資料驗證改動後的品質（指示禁止
讀試算表）。目前的行為是**正確**的（零硬規則違反），只是**不夠多樣**——
正確性優先於最佳化。

改為在 `generateBest()` 加一個**輸出完全不變**的偵測：頭
`MULTIRUN_SEED_PROBE_ATTEMPTS`（3）次如果產生逐格相同的職事表，就判定這份
資料下 seed 無效、提早停止。之所以保證輸出不變：`isBetterCandidate_()` 用
嚴格小於（`deviation < best.deviation`）比較，一份與已有候選完全相同的表
`deviation` 必然相等、不可能勝出。效果：省下 17／20 的重複計算，選出來的
仍然是同一份。真實資料如果真的有同分候選人，換 seed 會產生不同結果，
偵測不成立、會照樣跑足設定次數。

**日後如果想真正修好**（令 20 次生成有意義），建議做法是在
`compareCandidates_()` 加一個「分數差距小於某個 epsilon 即視為同分」的容差，
令 `tieBreak` 真正參與決勝——但這一定要配合真實資料驗證品質，不適合在
無法讀試算表的離線輪次做。

### 階段 A 的測試架構：直接測正式碼，不是測副本

`tests/helpers/gas_loader.js` 把 `src/` 下真正的 `.gs` 原始碼載入 Node.js
沙箱直接呼叫。可以這樣做的前提（已逐一查證）：**`Generator.gs` 全檔完全
沒有呼叫任何 Google Apps Script 專有 API**，它只吃一個由呼叫端準備好的
`context` 物件；真正碰試算表的是 `buildGeneratorContext_()`（讀資料）與
`performRosterGeneration_()`（寫回），測試都不呼叫。

這跟其他測試檔「移植逐字對應的邏輯」不同，是刻意的：排表生成器連同它
依賴的規則判斷超過一千行，而「絕不違反硬規則」這個保證的價值完全建立在
「測的是真正會跑的那份程式碼」之上——測副本只會證明副本沒問題。

斷言分兩層，兩層都必須零違反：
1. **重用正式碼的規則引擎**——直接呼叫 `findStateViolations_()`（`FineTune.gs`），
   即步驟 3／5「重跑規則檢查」用的同一個函式。
2. **不看 RuleSettings 的獨立結構檢查**——逐條照 `roster_patterns_rules.md`
   的文字檢查結果。存在理由：第一層只會回報「RuleSettings 裡 Enabled=TRUE
   且 Level=HARD」的規則，如果哪天有人把 `HARD_ELIGIBILITY` 的 Level 改成

### ⚠️ 階段 A 最重要的發現：底色語意撞車（步驟 4 前置檢查誤判規則警告格為待補格）

**問題現象**：步驟 4 執行前的「有未完成事項」視窗報告「仍有 2 格待補
（黃底，建議先人手處理）」，列出 2027-01-10 SCRIPTURE#1 與 2027-03-07
SOUND#1。但這兩格根本不是待補格——它們有人，而且正正是兩筆「指定服侍」
申報套用後的目標格，同時因為指定服侍而觸發了 `SEMI_NO_CONSECUTIVE`
準硬規則警告。步驟 3 與步驟 5 的完成畫面都正確報告「待補格子（黃底）：
0 格」，只有步驟 4 的前置檢查誤報。

**A1 根本原因（已逐行讀碼確認）**：`GRID_COLORS.WARNING`（`Constants.gs`）
與 `DEFAULTS.GRID_PENDING_FILL_COLOR`（同檔）兩個常數修正前**完全同色**
（都是 `#FFF2CC`）：

- `applyCellMarks_()`（`RosterWriter.gs`）在**每一次**建立新版本工作表時
  （包括步驟 3／5 的「套用修改申報」流程），只要一格「有人但觸發規則
  警告」（`cellWarnings.length > 0` 且不是 `SKIPPED`），就把底色塗成
  `GRID_COLORS.WARNING`。
- `listPendingBackfillCells_()`（`RequestsApply.gs`）修正前**純靠底色**
  判斷「是不是待補格」——掃描整張 grid 的 `getBackgrounds()`，凡是底色
  等於 `GRID_PENDING_FILL_COLOR` 的一律當成待補格，**完全沒有核對格子
  的 `PersonID`、`AssignSource`、`RuleFlags`**。

兩者同色的結果：指定服侍申報套用後，目標格「有人 + 觸發
`SEMI_NO_CONSECUTIVE` 警告」，被 `applyCellMarks_()` 塗成 `#FFF2CC`；
`listPendingBackfillCells_()` 掃描時只看底色，凡是 `#FFF2CC` 一律當成
待補格，於是把這兩格誤判進待補清單。Ivan 的推測完全正確。

**A2 修正**：把 `listPendingBackfillCells_()` 改為完全依賴資料層判斷，
不再讀取任何底色。判斷條件（與 `Generator.gs` 的 `buildRoster_()`／
`pickPerson_()` 留空格路徑、`RequestsApply.gs` 的 `applyCannotServe_()`
找不到替補路徑**共用同一組訊號**，本來就已經一致）：

```
PersonID 是空 AND AssignSource === ASSIGN_SOURCE.SKIPPED
  AND RuleFlags 含 RULE_IDS.ELIGIBILITY（HARD_ELIGIBILITY）
```

格子的 Note 文字仍然從 grid 讀出，但只用於組成回傳結果的顯示內容
（給幹事看原因），不再參與「是不是待補格」的判斷。詳見
[`src/RequestsApply.gs`](../src/RequestsApply.gs) 的 `listPendingBackfillCells_()`
函式註釋。

**A3 排查了整個 `src/` 有沒有其他地方也是靠讀底色判斷語意**（全專案只有
3 個 `getBackgrounds()`／`getBackground()` 呼叫點）：

| 檔案 | 函式 | 判斷方式 | 結論 |

### 個人 PDF 匯出重試效能分析（58 人／3 批／552.6 秒／重試 81 次）

**數字拆解**：81 次重試佔用了約 257.0 秒（`totalExportMs` 累計，含重試等待
時間），佔總耗時 552.6 秒的 46.5%——接近一半。平均每人重試 1.4 次
（81 ÷ 58）。

**是 Google 端速率限制，還是程式碼重試策略過於激進？逐項判斷如下**：

1. **重試只在遇到 429／5xx／內容過小三種情況才觸發**（`fetchWithRetry_()`，
   `PdfExport.gs`）——401/403/404 這類設定問題一律不重試，直接失敗。
   這三種都是**外部服務的暫時性狀況**，不是程式邏輯誤判觸發了不必要的
   重試。
2. **產生迴圈完全沒有主動間隔**（`runPersonalPdfBatchLoopInner_()`，
   `PdfBatch.gs`）——一個人匯出成功之後**立即**呼叫下一個人的匯出，
   中間零延遲，只有失敗之後的重試才會 `Utilities.sleep()`。這種「連續
   緊湊呼叫同一個匯出端點」的模式，正正是最容易觸發速率限制的用法。
3. **最終結果 `ERROR_PDF=0`**——全部 81 次重試最後都成功，代表現有的
   重試預算（4 次、指數退避 1s/2s/4s/8s）**足夠應付**目前規模的速率限制，
   不是重試次數不夠導致失敗，純粹是等待時間累積起來很可觀。

**結論：主要是 Google 端速率限制，不是程式碼重試策略本身激進。** 現有
重試機制的角色是「正確地承受」這個限制，不是「錯誤地造成」它。真正
可能有效的改善方向是**主動在兩次匯出之間加一個小間隔**（例如
200–300 毫秒），減少一開始就觸發速率限制的機率，而不是調整重試次數
或退避間隔本身——調小重試預算或縮短退避時間，風險是把現在會自己
成功的暫時性 429 變成真正的 `ERROR_PDF` 失敗，得不償失。

**本輪決定：先記錄為已知的營運成本，不在本輪動這個機制**，原因：

- 本輪明確禁止開瀏覽器／讀取試算表，無法拿到 2027T1 那次執行的實際
  逐次 HTTP 狀態碼記錄（`Logger.log`），無法確認 81 次重試裡 429／5xx／
  內容過小三者的比例，也就無法驗證「加間隔」這個假設在真實環境下
  是否真的減少重試次數——沒有實測依據就動一個目前運作正常
  （`ERROR_PDF=0`）的機制，風險大於收穫。
- 主動加間隔會讓每批次的「已耗用時間」提早接近 `PDF_BATCH_TIME_BUDGET_MS`
  上限，可能令 3 批變成 4 批——這本身不是問題（分批機制本來就是為咗
  應付這種情況設計的），但改動前應該先有實測數據支持，而不是憑推測
  調整一個目前已知運作正確的參數。
- **下一輪如果 Ivan 能在真實環境重跑一次，並且這次容許讀 Logger 記錄**，
  應該先確認 81 次重試中有幾多真正是 429（而不是 5xx 或內容過小），
  再決定加間隔的間隔長度是否有實測效果，而不是憑空猜一個數字。

**552.6 秒本身是否構成風險**：不構成——分批機制（`PDF_BATCH_TIME_BUDGET_MS`
安全網）已經確保單次 Apps Script 執行不會超過 6 分鐘上限，58 人分 3 批
完成、每批之間幹事重新按一次選單即可接續，這是設計內、預期的行為，
不是意外中斷。

### ⚠️ 階段 B：RANDOM_SEED 失效的根治（附完整 epsilon 對照表）

**第七輪批次的發現**：30 個不同 seed 產生逐格完全相同的職事表，令
`generateBest()` 跑 20 次等於同一份表算 20 次。當時刻意冇根治，因為
無法用真實資料驗證改動後的品質。

**根本原因**：`compareCandidates_()` 只在 `score` 與 `selectionScore`
**完全相等**時才輪到 `tieBreak`（唯一用到 seed 的地方），而
`score = penalty - bonus - selectionScore × selectionWeight` 含連續浮點數，
兩個人實務上不可能剛好相等。

**修正**：加入可配置的分數容差 `SCORE_TIE_EPSILON`（**預設 0＝完全不啟用，
排表行為與加入之前逐格一致**）。

**過程中發現第一版修正不足**——這一點值得記下來：只對 `score` 加容差是
**不夠**的。`selectionScore` 本身也是連續浮點數，同分群組內的決勝權只是
由「score」轉移到「selectionScore」，`tieBreak` 一樣永遠輪不到，換 seed
照樣產生逐格相同的表。離線測試量度到「容差確實改變了排表結果，但 30 個
seed 仍然只產生 1 份表」才發現。最終修正是：**容差生效時直接跳過
`selectionScore` 那一層**——它已經算進 `score` 裡面，既然兩人 score 差距
在容差內、視為「一樣好」，就不應該再拿同一個訊號決勝一次。

**另一個關鍵設計：`pickEpsilonWinner_()`**。加了容差之後
`compareCandidates_()` 不再**可傳遞**（a≈b、b≈c 不代表 a≈c）。把不可傳遞的
比較函式交給 `Array.prototype.sort()`，結果雖然可重現，但可能經由「近似鏈」
讓一個分數遠差於最佳者的候選人排到第一，epsilon 越大越易發生。所以優勝者
改為明確定義：**只有「跟最佳分數相差不超過 epsilon」的候選人才算同分**，
群組內再用 tieBreak 決勝。優勝者的分數因此有明確上界，不會被鏈式放大。

1. 主席兼報告的目標是 63%。epsilon=0 最佳只去到 **30.8%**（距離目標 32.2

2. epsilon=5 的用人數 55–61、平均次數 3.03–3.36，全部貼近歷史基準

3. **再大就開始變差**：epsilon=10／20 的最佳可達冇再提升（同樣 53.8%），

   右偏形狀**（歷史上有一小群核心義工做到 7–8 次）。原因是容差過大會蓋過
   計分裡的獎勵分量級（`SCORE_PREFERENCE_BONUS` 預設 50、
   `SCORE_CHAIR_DUAL_BONUS` 預設 30），令軟規則偏好失效。
   **經驗法則：epsilon 應該明顯細於獎勵分量級。**
4. 全部 epsilon 值（測到 100）硬規則違反一律 **0**，包括「技術崗位整池當週
   不能服侍」的資源緊絀情境——容差不會令系統走回「硬派一個違規者」的老路。

### ⚠️ 階段 C：電郵實際內容覆核（新增 `docs/電郵範本樣本.md`）

**問題**：系統已經模擬寄出過幾十封信（2027T1 步驟 4 有 60 個收件人），
但**從來冇人真正讀過收件人會收到嘅內容**——DRY_RUN 只會在 Logger 記一行

新增 `docs/電郵範本樣本.md`：用虛構資料把每一種收件人實際會收到的信
完整渲染出來（主旨＋內文＋附件說明），共 7 個樣本。渲染邏輯**重用正式碼**的

#### ⚠️ 發現的真實問題 1：堂委收到一封寫俾個人、內容壞咗的信

步驟 4「正式發出」同時寄俾兩種收件人：每一位有服侍的義工（PERSON），
以及 `EmailRecipients` 中 `Stage` 欄含 `OFFICIAL` 的名單（LIST，例如堂委、
教會辦公室）。**2027T1 實測嗰次就是「LIST 2 + PERSON 58」**。

修正前兩種收件人**共用同一個 `TPL_OFFICIAL_TC`**，於是那 2 位 LIST 收件人
收到的是：

- 稱呼一份**名單**做「XXX 弟兄／姊妹」；
- 「閣下本季的服侍安排如下：」後面**完全空白**——LIST 收件人冇 `PersonID`，
  `buildAssignmentSummary_()` 回傳空字串，而 `deliverOne_()` 那句
  「本季您暫時沒有任何服侍安排」替代文字**只對 PERSON 收件人生效**；
- 聲稱「個人版職事表已作為附件」，但 `generateMailAttachment_()` 對
  `PERSONAL_PDF` ＋ 非 PERSON 收件人一律回傳 `null`，**實際上冇附件**。

**修正**：新增 `TPL_OFFICIAL_LIST_TC`，沿用步驟 5 已經驗證過的同一套做法
（`TPL_RESEND_LIST_TC` 一直都是這樣做）——LIST 收件人用自己的範本、附完整版
PDF。`sendStage()` 依收件人類型揀範本（`resolveStageTemplates_()`）。
**向後相容**：工作表未加這一行之前會自動退回用舊範本，不會因為缺一行而寄唔到信。

順帶一提：`EMAIL_TEMPLATE_SEEDS` 原本只有 5 個範本，補完之後正好是 **6 個**
——本輪任務描述講的「全部 6 個範本」，缺的正是這一個。

#### ⚠️ 發現的真實問題 2：日期格式有月日歧義

個人信裡「1月4日 主席」那一行的日期格式，由 `dd/MM` 改為 `M月d日`
（`DEFAULTS.MAIL_SUMMARY_DATE_FORMAT`）。`dd/MM` 寫出來是「03/04」，
對習慣 `MM/dd` 的讀者來說究竟是 3 月 4 日還是 4 月 3 日分唔到。義工就是靠
這一行去記自己邊個禮拜要返，記錯日期的代價好實際（當日冇人到位）。

#### 覆核過冇問題的項目

未替換的變數（7 個樣本全部零殘留）、零派工者的替代文字、無電郵者的處理、
OFFICIAL 個人信有交代「未能出席要點做」、全部樣本冇台灣式書面語用詞。

### 階段 D：上線切換嚮導（新增 `src/GoLiveWizard.gs`，**本輪絕對冇執行**）

之前只有 `buildLaunchSequenceNotes_()`——一份「建議你照這個次序改」的唯讀
清單，實際改值仍然要幹事自己去 Config 逐格打字。上線是整個系統風險最高的
一次操作（改錯就是全體義工收到唔應該收的信），靠人手逐格改而冇任何檢查同
確認，唔合理。

新增三個選單項：

| 選單項 | 性質 |
|---|---|
| 維護 ▸ ⚠️⚠️ 上線切換嚮導（會令系統真正寄信） | 會改 Config |
| 維護 ▸ ⚠️ 回退到測試模式 | 會改 Config |
| 查看 ▸ 上線狀態（唯讀） | 純檢視 |

**「中途取消唔會留低半套狀態」點做到**：Apps Script 冇真正的交易，清空前綴
同改 `DRY_RUN` 是兩次獨立寫入，技術上一定可能留低「改咗一半」。所以唔假裝
做到原子性，改為做兩件事：(1) 每一段獨立確認、獨立生效，撳取消即刻停；
(2) **「完成到邊一段」是即場由 Config 真實值計出來，唔靠任何記低的進度旗標**
（`assessGoLiveState_()`，四種組合各對應一個明確 phase）。進度旗標本身可能
同真實狀態脫節（例如幹事自己手動改咗其中一格），直接讀 Config 就一定是真相。
所以「改咗一半」永遠是**睇得到、講得出、可以接住做落去**的。

**段落次序是刻意的**：上線先清前綴、最後先改 `DRY_RUN=FALSE`（風險最高那步
排最後，前面任何一步取消都唔會有信寄出）；回退先改 `DRY_RUN=TRUE` 止血、
之後先還原前綴（止血唔可以等）。這兩個次序都有測試鎖住。

**其他防護**：前置跑一次全面體檢，有「必須處理」就拒絕繼續（把關排在第一次
改 Config 之前）；`DRY_RUN=FALSE` 要逐字輸入「確認上線」；
`setConfigValue_()` **搵唔到 Key 就拋錯、絕不自動新增行**；改完即刻清 Config
快取；每次改值都寫 AuditLog（含改動前後的值）。測試另外用靜態原始碼檢查
確認嚮導**冇順手做任何其他事**（冇寄信、冇改 Stage、冇生成版本、冇建 trigger，
全檔只會改動 `DRY_RUN` 同 `MAIL_SUBJECT_PREFIX` 兩個 Key）。

### 階段 C：epsilon 試算工具嘅可用性

**問題**：上一輪加咗「試算不同 epsilon 的效果（唯讀）」，但輸出係每個 epsilon

**C1／C2 修正**：判斷邏輯搬入程式（`recommendEpsilon_()`），輸出改為
**每個 epsilon 一行**（總偏差、幾多份唔同嘅表、硬規則違反數），
最後一段明確寫「建議值：X」＋ 完整理由 ＋ 「要改嘅話去邊度改」。

判斷準則刻意對齊 `generateBest()` 實際做緊嘅嘢（跑 N 次揀最好嗰份），
所以主要指標係 `deviation.min`（最好嗰份嘅總偏差）：

1. 硬規則違反必須係 0——有違反嘅一律出局，冇得商量（會出警告）。
2. 準硬規則唔可以比 `epsilon=0` 差。
3. 冇多樣性（只排到 1 種表）＝ 冇生效，唔算數。
4. 喺剩低嘅之中揀 `deviation.min` 最細嗰個。
5. 要贏 `epsilon=0` 至少 5%，贏得太少就唔值得改設定，維持 0 更保守。
6. 同分揀較細嗰個 epsilon（容差越細，優勝者偏離最佳分數嘅上界越細）。
7. 建議值 ≥ `SCORE_PREFERENCE_BONUS` 一半時額外出提醒——容差太大會蓋過
   軟規則偏好，令次數分佈被拉平。

**C3 效能實測**（89 人／13 週／18 個崗位欄）：每份職事表約 **18 毫秒**（Node），
Apps Script 保守估 15–25 倍即每份 0.27–0.45 秒。預設 5 個 epsilon × 10 seed
＝ 50 份，約 **13–22 秒**，離 6 分鐘上限好遠。但幹事可以自己輸入 epsilon 清單
