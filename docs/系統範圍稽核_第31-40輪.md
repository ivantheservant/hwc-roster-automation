## 實測（2027T4 全季流程演練報告）

```
ICS 附件 | 查不到 | 認不出這個時間值：
「Sat Dec 30 1899 10:45:00 GMT+1130 (New Zealand Daylight Time)」
```

## 根因：中間還有一層

第二十三輪加了一個 `[object Date]` 分支處理「Config 值是 Date 物件」。
但 `Config.gs` 的 `convertConfigValue_()` 對 `STR` 型別會做
`String(rawValue).trim()`——Date 物件在到達 `normalizeTimeOfDay_()` **之前**
已經變成文字，那個 `[object Date]` 檢查**永遠不會中**。

⚠️ 而第二十三輪的測試「證明」了修正有效，是因為它**直接餵一個 Date 物件
給純函式**，沒有經過 `getConfig()` → `convertConfigValue_()` 這一層。
更糟的是那份測試裡有一條斷言明文要求
「`String(Date)` 出來的英文長格式 ⇒ 拋錯」——
**它把「修正沒有生效」寫成了預期行為。** 本輪已經改掉並註明原因。

## A2　修法

`normalizeTimeOfDay_()` 多認一種輸入：已經被 `String()` 化的 Date。

判斷**刻意收得很窄**：一定要有 `時:分:秒` 這個形狀（`String(Date)` 的特徵）
才嘗試 `new Date()`。實測 V8 的行為：

| 輸入 | `new Date()` 結果 | 不收窄的話會變成 |
|---|---|---|
| `'2027'` | 2027-01-01 | `00:00` |
| `'1045'` | 1045-01-01 | `00:00` |
| `'10:75'` | 1974-12-31 | 一個亂數時間 |

三個都是「認不出被當成一個有意義的值」那個 bug class，
而後果是義工在錯的鐘數返到教會。加了秒之後三個都會落去拋錯。

順序也重要：`HH:mm` 的正則要走在新分支**之前**，
免得一個正常輸入被拉去一條完全不需要的路。

## A3　重新掃一次「值可能被 Sheets 正規化」的 Config Key

第二十三輪的掃描只列了「哪些 Key 的值可能被 Sheets 正規化」，
但沒有把 `convertConfigValue_()` 那一層算進去。這次逐型別問：
**「如果那一格被 Sheets 正規化成 Date／Number，經過 `convertConfigValue_()`
之後會變成什麼？下游收到那個值會怎樣？」**

`convertConfigValue_()` 對每一型的處理：

```
INT / DEC  → String(raw).trim() → Number(str)
BOOL       → String(raw).trim().toUpperCase() === 'TRUE'
LIST       → String(raw).trim().split(',')
其餘（STR / ENUM / EMAIL）→ String(raw).trim()
```

**每一型都先 `String()`。所以下游永遠收不到 Date 物件——一個都收不到。**

| 型別 | 數量 | 被 Sheets 正規化之後會變成 | 風險 |
|---|---|---|---|
| `STR`（29） | 29 | `Sat Dec 30 1899 10:45:00 GMT+1130 (…)` 這種長字串 | 🔴 **就是這次那個** |
| `INT`（22） | 22 | `Number('Sat Dec 30 1899 …')` ⇒ `NaN` | 🟠 見下 |
| `DEC`（6） | 6 | 同上 ⇒ `NaN` | 🟠 見下 |
| `BOOL`（9） | 9 | 長字串 `.toUpperCase() !== 'TRUE'` ⇒ `false` | 🟠 見下 |
| `LIST`（5） | 5 | 長字串被逗號拆開 ⇒ 一堆垃圾項目 | 🟢 低（值都是欄名／前綴，不會被當成時間） |
| `ENUM`（3）／`EMAIL`（3） | 6 | 長字串 | 🟢 低（值不會被當成時間或數字） |

### 🔴 `STR` 裡真正有風險的四個

只有「值本身長得像時間／日期／數字」的格才會被 Google 自動轉：

| Key | 值長什麼樣 | 會不會被轉 | 現況 |
|---|---|---|---|
| `ICS_SERVICE_START_TIME` | `10:45` | **會** | 本輪已治本；Ivan 亦已把那一格改成純文字 |
| `ICS_SERVICE_END_TIME` | `12:00` | **會** | 同上 |
| `SYS_TIMESTAMP_FORMAT` | `yyyy-MM-dd HH:mm:ss` | 不會（有字母） | 安全 |
| `MAIL_SUMMARY_DATE_FORMAT`／`PUBLIC_ROSTER_DATE_FORMAT` | `M月d日` 這類 | 不會 | 安全 |

其餘 25 個 `STR` 的值都是名稱／ID／顏色碼／樣板字串，不會被當成時間。

### 🟠 `INT`／`DEC`／`BOOL` 的「靜靜變成一個能用的值」

這三型不會拋錯，會**靜靜得出一個看起來正常的值**：

- `INT`／`DEC` ⇒ `Number(長字串)` ＝ `NaN`。
  下游多數寫成 `Number(x) || DEFAULT`，所以會**退回預設值**——
  即是「你在 Config 改的那個數字完全沒有生效，而且沒有任何訊號」。
- `BOOL` ⇒ `false`。`DRY_RUN` 落在這一型：
  萬一那一格被轉成非文字，`DRY_RUN` 會靜靜變成 `false` ＝ **真的寄信**。

⚠️ 但**這幾型的值都是純數字或 `TRUE`／`FALSE`**，
Google 對純數字格的處理是存成 Number，`String(3)` ⇒ `'3'`，
`Number('3')` ⇒ `3`——來回是對的。`TRUE`／`FALSE` 也不會被轉成日期。
所以現實風險低，但**機制上沒有防線**：這幾型一旦收到認不出的值，
一律靜靜退回預設，不像 `normalizeTimeOfDay_()` 會嘈。

**這是一個已知的、沒有修的缺口**，本輪沒有動——
要修的話等於給每一個 `INT`／`BOOL` 都加一層「認不出就拋錯」，
是一次橫跨 37 個 Key 的行為改動，應該單獨一輪做。記在這裡。

## 第三十二輪批次

### 階段 A：Config 型別防線

`convertConfigValue_()` 對 `INT`／`DEC`／`BOOL`／`LIST` 認唔出就拋錯。

舊行為：`INT`／`DEC` 認唔出 ⇒ `NaN` ⇒ 下游多數寫 `Number(x) || DEFAULT`
⇒ **靜靜退回預設值**，即係「你喺 Config 改嗰個數字完全冇生效」。
`BOOL` 認唔出 ⇒ 靜靜變 `false`——而 **`DRY_RUN` 就係 `BOOL`**，
嗰格一旦被試算表轉成非文字，`DRY_RUN` 變 `false` ＝ 真係寄信俾全體義工。

#### A3 揀咗「記低後補拋」，唔揀「轉型延後」

兩種都可以，揀咗前者。

`readConfig()` 逐個 key `try/catch`，失敗時把一個 marker 寫入 `config[key]`，
等 `getConfig(嗰個 key)` 真係被叫嗰陣先拋。

| 為什麼不揀「轉型延後」 | |
| --- | --- |
| 快取層 | `readConfig()` 快取嘅係**已轉型**嘅結果（`JSON.stringify` 落 `CacheService`）。轉型延後就要連快取層一齊改——快取要改成存原值 ＋ 型別，而每一個讀 `readConfig()` 直接攞欄位嘅地方（`describeConfigValue_()`、`readCacheTtlSeconds_()`、各種報告）都要跟住改。 |
| 收益一樣 | 兩種做法對外行為完全相同：壞格只喺被讀嗰陣拋，其餘 key 照讀得到。 |
| 風險 | 改動面大好多，而呢一輪冇任何測試覆蓋緊快取層嘅轉型時機。 |

marker 特登做成**普通物件**（`{__configTypeError__: true, message}`）：
`readConfig()` 會 `JSON.stringify` 佢落快取，用 `Error` 物件或者 `Symbol`
會喺嗰一轉靜靜變成 `{}`，然後壞格變成一個睇落正常嘅物件。有測試守住。

#### 刻意冇做

`STR`／`ENUM`／`EMAIL` 一律唔改。`ICS_SERVICE_START_TIME` 呢類靠下游
`normalizeTimeOfDay_()` 處理（第三十一輪階段 A 嘅治本），
喺呢一層攔住會令嗰個修正永遠用唔著。有測試守住。

### 階段 A：Mailer 兩個真 bug（補電郵之後永遠寄不出）

#### 成因

**兩個都係同一個根：`deliverOne_()` 用自己一套更粗嘅邏輯重新判斷「要唔要寄」，
蓋過咗上游已經做好嘅決定。** 本專案嘅「兩個真相來源」bug class。

`computeResendDiff_()`（`ResendFlow.gs` 第 54 行）已經算好
`firstNotifyDueToEmail`（`!hashChanged && lastStatus === SKIPPED_NO_EMAIL && nowHasEmail`），
但 `deliverOne_()`（`Mailer.gs`）嘅過濾**只比 hash**，完全唔理呢個旗標：

| 症狀 | 後果 |
| --- | --- |
| 問題 1 | 一個人喺 OFFICIAL 因為查無電郵被 `SKIPPED_NO_EMAIL`，幹事之後補上電郵、派工一格都冇改 ⇒ 上游正確咁列佢入「要通知」，但走到 `deliverOne_()` 因為 hash 冇變即刻被判 `SKIPPED_UNCHANGED`。**第一封信永遠冇真正發出，而且冇任何錯誤訊息。** |
| 問題 2 | `SKIPPED_UNCHANGED` 唔喺基準名單 ⇒ 下一輪基準仍然係更舊嗰筆 `SKIPPED_NO_EMAIL` ⇒ 同一個人再被列入名單、再被同一個關卡擋住。**死循環。** |

### 階段 C：Diagnostics 修剪不可以留半截報告

演練第 1 段嘅完成對話框話報告「共 255 行」，但表上嗰份只剩 241 行。

**半截報告比冇報告更差**——讀嘅人唔知自己睇緊嘅係殘缺版，而報告開頭通常
就係最重要嗰段摘要。呢個係「缺失被當成正常值」嘅變體：一份被斬過嘅報告，
睇落同一份完整報告一模一樣。

| 項 | 內容 |
| --- | --- |
| C1 | 修剪抽成純函式 `planDiagnosticsTrim_()`（可以離線測）。由最舊嗰份開始**整份**丟，丟到夠位就停。**上限算唔到（`null`／`''`／`'abc'`）就唔修剪**，唔會靜靜當成上限 0 而清空成張表。 |
| C2 | 單一報告自己就超過上限 ⇒ 丟晒其餘，**佢自己一行都唔斬**，並喺頂部插一行明講。另外，「單一報告上限」嘅截斷通知由最尾**搬咗上頂部**——擺喺最尾嘅問題係：一份被斬過嘅報告，正正就係一份可能連最尾都讀唔到嘅報告。 |
| C3 | 新增 `buildDiagnosticsTrimRow_()`：`本表保留 N 份報告，本次清走 M 份最舊的（總行數上限 380）`，連清走咗邊幾份都列出。**冇清走都要寫**「本次沒有清走任何報告」——只喺有清走時先寫，等於要讀嘅人靠「有冇呢一行」推論，而佢根本唔知應唔應該有。 |

但 `validateRequest_()` 回嘅係 `post`（成個崗位物件），**根本冇 `postId` 呢個欄位**。
所以個 filter 永遠一項都唔中 ⇒ `overlaps` 永遠係空陣列 ⇒
畫面永遠唔會話俾幹事聽「你親手改嗰格會蓋過一筆申報」。

**之前偵測唔到，係因為根本冇套用過申報（甲2）——兩個 bug 互相遮住對方。**

而家兩邊都修好：偵測改用 `r.post.postId`，執行階段把嗰啲列號傳落
`applyRequests_()` 記成 REJECTED 並寫明「同一格你已經在職事表上親手改過，
以你改的為準，這一筆沒有套用」。⚠️ **一定要記低**——義工提交咗嘢，
唔可以無聲無息消失。

#### 甲3 判斷：`NEEDS_INPUT` **唔算**「未處理」

現場：掣 3 嘅閘門擋住未處理申報，但撳掣 1 永遠處理唔完
——現場係靠人手去 `Requests` 刪走嗰兩行先行得返。

成因：`readPendingRequests_()` 用 `RequestID` 空白判斷「未處理」，
而 `NEEDS_INPUT` 類申報**刻意永遠唔會攞到 `RequestID`**
（`writeRequestOutcomes_()` 嘅既有設計，噉樣先可以喺底層資料修正之後
重新驗證一次）。兩件事夾埋 ⇒ 死鎖。

**判斷：閘門只應該擋「會改動職事表但仲未套用」嘅嘢。**

一筆 `NEEDS_INPUT` 申報系統根本睇唔明，佢**永遠唔會**自動改動職事表，
所以佢唔構成「正式發出之後職事表會唔啱」嘅風險——擋住佢冇保護到任何嘢，
只係令幹事無路可走。而一筆 `APPLY`／`CONFIRM` 未套用就係真風險，繼續擋。

實作喺 `readDashboardUnsavedState_()`：`pendingRequestCount` 只數
`APPLY`／`CONFIRM`，`needsInputCount` 獨立一個數，而且**唔計入 `hasAny`**。

⚠️ 但 `NEEDS_INPUT` **一定要繼續顯示**（掣 1 嘅文字會講「另有 N 筆申報
系統看不懂……它們不會擋住『正式發出』」）——變成靜靜消失就會係另一個
「缺失被當成正常值」。

#### 甲4：失敗文案分兩種

實測核實甲1 嗰種失敗**一個字都冇寫入**（`RosterVersions` 冇 v2、
`AuditLog` 零新紀錄、`Requests` 未動），但訊息講「第 2 版可能只寫入了一部分…
去核對／或者回退」。**把乾淨失敗講成需要人手善後，會令幹事去做一次
完全不必要嘅回退——而回退本身係一個會建立新版本嘅動作。**
即係一句嚇人嘅文案製造咗一個真正多餘嘅版本。

抽咗做 `buildSaveConfirmFailureResult_()`，靠**去睇實際狀態**分
（`RosterVersions` 有冇登記／grid 工作表在唔在），唔係靠估。
⚠️ 連查都失敗嗰陣一律當成「可能寫咗一半」——呢個方向嘅錯比較安全。

#### 甲5：`ruleFlags` 被寫死空陣列

現場：`2027T3 v2` 嘅完整版 PDF 圖例把 **79 格**報成「系統未能安排」，
正確答案係「待確認 39／— 40／未能安排 **0**」。

算術直接指出成因：273 總行 − 194 有派人 = **79**，同「未能安排」一模一樣；
2026T4 係 273 − 192 = **81**，同樣吻合。即係**冇做分類**，
而係把所有冇派人嘅格整批倒入最後一個桶。

成因：`StateSource.gs` 第 202 行 `ruleFlags: []`。
`classifyGridCell_()`（`Generator.gs`）要靠 `ruleFlags` 先分得出
「待確認／—／特殊主日／未能安排」。冇原因 ⇒ 分唔出 ⇒ 全部當成「排唔到」。
呢個係 bug class 第 2 條（缺失被當成正常值）＋ 第 5 條（冇分開
「系統要排」同「不自動排」）。

⚠️ **呢份 PDF 係寄俾每一位義工嘅附件。** 上線之後全體會收到一份寫住
「系統有 79 格排唔到」嘅職事表，而事實係零格排唔到。

修法：`ruleFlags: s.isManual ? [] : ((originalRow.ruleFlags || []).slice())`。
規則同 `applyRequests_()` 一致——**冇被人手改動嘅格原因原封不動保留**
（唔理佢有冇人）；被人手改動嘅格清空（舊原因描述緊舊嗰個佔用者）。

`RosterAssignments` 資料層完全正常（每個版本 273 行、`SKIPPED` 嘅格連原因都在）

### 乙組：「不能服侍的日期」畫面三項

#### 乙1：成因唔喺 JS，喺 CSS

`postBox.hidden = true` 一直都有寫。但 `.prop-opts { display: flex }`
（class 選擇器）**蓋過咗**瀏覽器 UA stylesheet 嘅 `[hidden] { display: none }`

⚠️ 用 `callServerMutating()` 唔用 `callServer()`——取消會改動資料，
區一嘅狀態卡同四粒掣都要跟住重新整理（有測試守住呢條規則）。

#### 乙3：兩層對「生效」有兩套理解

`WebAppUnavailable.gs` 讀整張表，**完全冇睇 `Status`**，只按日期分兩組。

兩邊都叫佢。列表改成三組（生效中／已取消／已過去），**唔刪走**。
`'CANCELLED'` 亦都由寫死字串改成 `UNAVAILABLE_VALUES.STATUS_CANCELLED`。

而且加咗「總數守恆」（生效 ＋ 已取消 ＋ 已過去 ＝ 工作表總行數）。

## 第三十五輪批次

Prompt P 推上去之後再跑現場，四項。第一項係上線 blocker。

### A 組：講員／翻譯／獻花令「儲存並確認」永遠鎖死（上線 blocker）

#### 現場

`2027T3` 嘅 `2027-07-04` 講員一格，早前用「填講員／翻譯／獻花」填咗一位
**外請講員**（AuditLog：`FILL_PREACHER_TRANSLATION`）。
grid 截圖同 connector 都確認嗰格真係有字。

之後撳「儲存並確認」（grid 一格未改、只有一筆申報），彈出
「有 1 格的文字，系統認不出是誰……`2027-07-04　PREACHER#1　你打了：「(空白)」`」。

核實：**冇建立新版本、`Requests` 未動**——乾淨拒絕本身係啱嘅（第三十四輪甲4 生效）。
但**判斷係錯嘅**。

#### 成因（定位到行）

`FineTune.gs` 嘅 `buildGridOverlayState_()` 第 235 行附近：

```js
const resolvedId = normalizedGrid === '' ? '' : (resolvePersonId(normalizedGrid) || '');
...
if (normalizedGrid !== '' && !resolvedId) { unresolved.push(...) }
```

外請講員**唔喺 `NameMapping`**（亦都唔應該喺），所以嗰格喺
`RosterAssignments` 只有 `PersonNameSnapshot`、冇 `PersonID`，解析返嚟係空。
偵測器見到「grid 有字、解析出空」就當成一格認唔出嘅人手改動 ⇒ 整批拒絕。

**佢冇一條規則去豁免嗰三個本來就唔自動排嘅崗位。**

#### 後果

**任何一季只要幹事填過講員，就永遠撳唔到「儲存並確認」。**
而填講員係開季前必做嘅事——即係呢條路喺真實使用上一定會踩到。

#### 修法

`AutoGenerate = FALSE` 嘅崗位**整格略過**人手改動偵測：唔解析人名、
唔算改動、唔會入 `unresolved`。嗰啲格嘅唯一寫入途徑係
「填講員／翻譯／獻花」（`PreacherTranslationFill.gs`），**唔係 grid 人手改動**。

⚠️ 判斷由 `Posts` 嘅 `AutoGenerate` 讀出嚟，**唔用崗位 ID 白名單**
——崗位會增減，寫死 ID 會喺下一次加崗位嗰陣再爆一次。

實作放咗喺 `buildGridRenderContext_()`（`RosterWriter.gs`）多加一個
`autoGenerateByPostId`——嗰個 context 本身就係「人手改動偵測要用嘅逐崗位資料」
（已經有 `emptyDisplayByPostId`），多一個欄位唔使多讀一次表。

⚠️ **`autoGenerateByPostId` 設成必要欄位，冇傳就拋錯。**
「冇就當全部崗位都係自動排」＝ 把「我唔知道」靜靜當成「係」，
而後果就係本輪呢個 bug 原封不動翻生。唔可以喺修佢嘅時候順手種返一個。

#### A 組第 3 點：同一條路上有冇其他地方有同樣假設

逐個 `resolvePersonId()` 呼叫點查過：

| 位置 | 有冇同樣假設 | 結論 |
| --- | --- | --- |
| `FineTune.gs:235`（人手改動偵測） | ✅ 有 | **就係呢個**，已修 |
| `PreacherTranslationFill.gs:186` | ❌ 冇 | `resolvePersonId(name) \|\| ''` ——解析唔到就存自由文字，**呢個正正係設計本身**，唔係 bug |
| `RequestsApply.gs:150／206／263` | ❌ 冇 | 申報嘅人名本來就一定要喺 `NameMapping`（解析唔到會報 NEEDS_INPUT，係正確行為） |
| `SelfTest.gs:179／236` | ❌ 冇 | 別名解析嘅自我測試，同 grid 無關 |

另外 `readGridPersonIds_()`（`FineTune.gs:82`）**刻意唔解析人名**
（佢自己嘅註解已經寫明理由：逐格重新解析會令未改動嘅格喺版本之間漂移）。

所以**只有一處**，而嗰處嘅下游（`readDashboardUnsavedState_()` 嘅
`unresolvedCount`、`listPendingBackfillCells_()`、`analyseManualState_()`）
全部經同一個 `buildGridOverlayState_()`，一次修好全部。

### B 組：對話框把兩個值講反

同一個對話框寫 `你打了：「(空白)」`，但 grid 上實際有字。

#### 成因：唔係「調轉」，係**欄位名寫錯，永遠 fallback 到空字串**

`WebAppSaveConfirm.gs` 原本寫 `rawText: u.manualText || u.rawText || ''`，
但 `buildGridOverlayState_()` 推入 `unresolved` 嗰陣用嘅欄位名係 **`text`**
——`manualText` 同 `rawText` **兩個都唔存在**。所以永遠 `''`，
而畫面就印成「你打了：「(空白)」」。

（後端嘅文字版 `buildUnresolvedGuidanceText_()` 一直都係啱嘅，
佢兩個值都印。錯嘅只係送去前端嗰份。）

#### 修法

**兩個值都送、兩個值都印**：`gridText`（格內而家有咩）＋
`expectedText`（本來應該係咩）。只印一個就永遠分唔出係邊一邊出事

畫面改成：

```

```

（只有 `buildMailContext_()` 先有）。`WebAppSaveConfirm.gs` 有**三處**寫
`context.postNames ? (context.postNames[x] || x) : x`，三處都永遠 fallback
到 postId ⇒ 幹事見到 `PREACHER#1` 呢種機器鍵，唔係「講員」。

### C 組：主席兼報告「上限」算出 100%，而且被當成目標值

#### 現場

```

#### 100% 喺數學上冇錯，錯喺被攞嚟當目標

`computeChairAnnounceUpperBound_()` 嘅 `bound = Math.min(weeksBothPosts, sumCap)`。
雙重合資格嘅人一多，`sumCap` 就遠大於 `weeksBothPosts` ⇒ `bound` 永遠等於
`weeksBothPosts` ⇒ 比例永遠 100%。

**函式自己嘅假設清單已經明寫「呢個上限偏鬆（實際通常達唔到）」。
一個偏鬆嘅上界唔係目標值。**

攞佢加 ± 5% 去判「偏離」，等於把 23.1% 同一個構造上達唔到嘅數字比

### A 組：非自動崗位嘅值喺新版本消失

真正嘅成因係**污染會被忠實地繼承**：

--- 由污糟基準建立嘅新版本 ---  桶: {"ASSIGNED":12,"MANUAL_PENDING":0,"GENUINE_GAP":4}
```

### A 組：非自動崗位帶自由文字嘅格

#### 現場範圍已經鎖到一格

由 v0 還原建立 v4（圖例 `194／39／40／0／0`，正確）⇒
「填講員／翻譯／獻花」喺 `2027-07-04` 講員填咗一位客席講員 ⇒
撳「儲存並確認」建立 v5 ⇒ 嗰一格變成 `⚠ 未能安排`，
圖例變成 `194／38／40／0／1`。**只有填過嗰一格出事。**

#### ⚠️ 用當下嘅碼重現之後，發現成因同 Prompt S 假設嘅唔同

Prompt S 推斷係「複製到新版本嗰陣遺失」。但即場跑一次：

```
--- 生成之後 (v0) 桶:{"ASSIGNED":9,"MANUAL_PENDING":4,"GENUINE_GAP":0}
    講員格: id="" name="" src="SKIPPED" flags="HARD_NO_AUTO_PREACHER"
--- ★ 用真入口填咗講員之後（同一版 v0，一格都未複製） 桶:{"ASSIGNED":9,"MANUAL_PENDING":3,"GENUINE_GAP":1}
    講員格: id="" name="客席講員某某" src="MANUAL" flags="HARD_NO_AUTO_PREACHER"
```

**corruption 喺「填」嗰一刻已經發生，一格都未複製過。**
`MANUAL_PENDING 4 → 3`、`GENUINE_GAP 0 → 1`——同現場嘅 `39 → 38`、`0 → 1` 一模一樣。

#### 成因（定位到行）

`apiSavePreacherTranslationEntry()`（PreacherTranslationFill.gs）寫入嗰一格：

```
personId    = ''                      （外請講員唔喺 NameMapping）
personName  = '（客席講員嘅名）'
assignSource = MANUAL                  ← 佢咁寫
ruleFlags   = 'HARD_NO_AUTO_PREACHER'  ← 冇被掂過
```

而 `classifyGridCell_()`（Generator.gs）：

```js
if (assignment.personId) return ASSIGNED;          // '' ⇒ 唔中
… STRUCTURAL_NA / SPECIAL_SKIP …                   // 唔中
if (assignSource === SKIPPED && flags has NO_AUTO_GENERATE)
  return MANUAL_PENDING;                           // src 係 MANUAL ⇒ 唔中
return GENUINE_GAP;                                // ← 跌落呢度
```

⚠️ 呢個係本專案 bug class 第 2 條最直接嗰個形態：
**把「我解析唔到佢係邊個」當成「呢度冇人」。**
一格幹事親手填咗人名嘅格，被系統報成「搵唔到合資格而當日又有空嘅人」。

而且**只有 `ASSIGNED` 會渲染人名**（`resolveGridCellText_()` 第 195 行，
其餘四類一律出固定標籤）——所以判錯類 ＝ **個名喺 grid 同 PDF 上消失**。

#### 修法

`classifyGridCell_()`：有 `personId` **或者**有非空 `personName` ⇒ 呢一格有人。

⚠️ **同 Prompt S 講嘅預期數字有出入，要記低。**
Prompt S 寫「複製到新版本之後斷言 39 格待確認、0 格未能安排」。
實際正確結果係 **`38 待確認 ＋ 1 有人 ＋ 0 未能安排`**（總數不變）。
點解唔係 39 待確認：嗰一格而家**真係有人**（幹事親手填咗），
而「待確認」嘅意思係「仲未有人」。而且只有 `ASSIGNED` 會渲染人名，
判成「待確認」就等於個名唔會出現喺表上。
**「0 未能安排」呢個關鍵要求完全滿足。**

#### 第二處（靠加闊咗嘅斷言先揪到）

修好分類之後，共用斷言即刻報：

```
2027-07-04|PREACH|1　assignSource：「MANUAL」 → 「SKIPPED」
```

`materialiseManualEdits_()`（StateSource.gs）寫
`assignSource: s.personId ? … : ASSIGN_SOURCE.SKIPPED`
——自由文字格冇 `personId`，所以佢原本嘅 `MANUAL` 被覆寫成 `SKIPPED`。
**又一次「解析唔到人 ⇒ 當冇嘢」。** 已改成「冇被人手改動嘅格，來源原封不動搬」。

（`LOG-...164818`）。回到第 0 版而把一個之後才填的名字清走，
**是正確的**——第 0 版本來就沒有那個講員。

所以這一行不是「rollback 弄丟了資料」的證據。

### D 組：路 5（`applyDecisions()`）端到端覆蓋

#### 之前是怎樣的

前三輪這一條路都只是**讀原始碼用 regex 檢查**，從來沒有真正執行過。
C 組的 `finetune-clear-touched` 整壞了仍然綠燈，就是這件事的直接證明。

#### 現在走的是完整真入口鏈

```
apiGenerateDraftExecute()            生成底本
apiSavePreacherTranslationEntry()    填一格講員（自由文字，沒有 PersonID）
在 grid 打字                          造一格違反硬規則的人手改動
apiDetectChanges()                   真入口，把提案寫進 FineTuneProposals
在 FineTuneProposals 填 Decision      幹事的輸入
applyDecisions(batchId)              真入口，建立新版本
```

#### 第一次跑就抓到一個真 bug

```
FAIL  [applyDecisions] 冇被改動嘅格，五個欄位逐字相同
      got=["2027-07-04|PREACH|1　assignSource：「MANUAL」 → 「SKIPPED」"]
FAIL  assignSource 仍然係 MANUAL
      got="SKIPPED"  expected="MANUAL"
```

`applyDecisions()` 寫的是 `personId ? source : ASSIGN_SOURCE.SKIPPED`。
後果：一格填了自由文字的講員（有 `PersonNameSnapshot`、`AssignSource = MANUAL`、
**沒有 PersonID**，因為外請講員不在 NameMapping），一按「套用決定」
就被壓成 `SKIPPED`。

**這跟第三十七輪在 `materialiseManualEdits_()` 修好的那個一模一樣**，
只是當時沒有一併改這一條路——因為第五條路一直沒有端到端測過。

修法跟那邊一致：不是這次改動的格，來源原封不動搬。

#### 另外加了路 5b

一個「決定落在**沒有人在 grid 改過**的格」的情境（把讀經的資格全部關掉，
令每一格讀經都違反 HARD_ELIGIBILITY 而且找不到替補）。

順帶確認了一件值得鎖住的行為：**決定永遠不會把一格洗成空白。**
找不到替補時 `ACCEPT_SUGGESTED` 會跌落 `else`（保留現況），
`REVERT_ORIGINAL` 有 `revertBlocked` 擋住同一件事。

這是對的——找不到替補是「排不到」，不是「不用人做」。
靜靜洗成空白會令一格服侍沒有人知道就沒有了。

### E 組：`classifyGridCell_` 八個呼叫點逐個驗

#### 呼叫點清單

`src/` 一共 6 個（加上兩個 helpers 就是 Prompt T 說的 8 個）：

| 檔案 | 幾多個 | 是什麼 |
|---|---|---|
| `DraftReviewReport.gs` | 1 | 初稿檢視報告的圖例計數 |
| `Generator.gs` | 1 | 生成完成畫面的統計 |
| `RosterWriter.gs` | 3 | grid 文字、grid 底色、`renderExpectedGridText_()` |
| `WebApp.gs` | 1 | 網頁版 grid |

6 個裡面有 5 個收一個變數，所以真正要驗的是**砌那個變數的地方**有沒有
把 `PersonNameSnapshot` 帶下去。逐個查過，**全部都有**。

`tests/classify_call_sites.test.js` 把這份清單鎖住：多了一個呼叫點而沒有
更新清單就會紅（本輪 G 組加了 `VersionCellAudit.gs` 那個新呼叫點，
這條測試立刻就抓到了）。

#### 但驗邊界的時候查出一個真 bug

給分類函式餵一格「`AssignSource = MANUAL`、名字是空白、`RuleFlags` 仍有
`NO_AUTO_GENERATE`」，它答 **`GENUINE_GAP`（未能安排）**，而不是
`MANUAL_PENDING`（待確認）。

成因：那條分支寫的是

```js
if (assignment.assignSource === ASSIGN_SOURCE.SKIPPED
  && flags.indexOf(RULE_IDS.NO_AUTO_GENERATE) !== -1) { ... }
```

一格講員一旦被寫成 `MANUAL`（幹事用側邊欄填過），之後名字因為任何原因
變回空白，它就**不再符合這個條件**，跌落「未能安排」。

**「未能安排」的意思是「系統要排，但排不到」。** 一格帶著
`NO_AUTO_GENERATE` 的格，系統從頭到尾都沒有打算排它，講它「未能安排」
是講錯話——而且 PDF 圖例上會多出紅字。

#### 這正好解釋了現場 v7 那個數字

現場圖例：`有派人 194／待確認 37／— 40／特殊主日 0／未能安排 2`，
而 `37 + 2 = 39` ＝ 13 個主日 × 3 個非自動崗位。

即是說：**那兩格「未能安排」，本來就不應該由系統排。**
它們是填過講員之後名字掉了（舊碼造成的）、而 `AssignSource` 停留在
`MANUAL` 的格。

修法：那條分支改為只看 `RuleFlags`，不看來源。只影響**空白**的格——
有 PersonID 或有自由文字的在上面已經早走了（ASSIGNED），
所以放寬這個條件不會把有人的格算錯。

⚠️ 這個修正**不會**把名字變回來（名字是舊碼弄丟的，已經不在任何地方）。
它只會令那兩格由「未能安排」變回「待確認」——正確的說法。
名字要幹事自己補，見 `docs/污染版本處理指引.md`。

### F 組：「grid 贏」推廣到步驟 3

#### 查到的

規格 1.4（同一格幹事已經親手改了 ⇒ 以幹事改的為準，那筆申報不套用但要記低）
在第三十四輪實作了。但實作方式是**由呼叫端傳一個列號清單進
`applyRequests_()`**，而全系統有三條路會叫它：

| 路 | 入口 | 有沒有傳 |
|---|---|---|
| 掣 1「儲存並確認」 | `apiSaveAndConfirmExecute()` | ✅ |
| 步驟 3「套用修改申報」 | `executeStep3Apply_()` | ❌ |
| 步驟 5「改動後重發」 | `executeStep5Send_()` 那條 | ❌ |

沒有傳的那兩條路，那個 set 是空的 ⇒ **整段「grid 贏」的邏輯直接跳過** ⇒
申報照樣蓋過幹事親手改的格，而且沒有任何提示。

這跟第十九輪那個 bug 是同一件事的下半截：那時修好了「看哪裡」
（讀 grid 不讀長表），但「誰贏」只在一條路上實作了。

#### 修法

沒有傳那個參數的時候**不是當作沒有 overlap**，而是由 `plan` 自己算回來。
`plan.assignByKey` 每一格都帶著 `isManual`（`planApplyRequests_()` 由 grid
疊加算出來），所以那段跟掣 1 那邊的 `overlaps` 是同一個判斷來源。

有傳就以呼叫端為準（掣 1 那條路行為完全不變）。

#### 順帶修好一個 fixture 的陷阱

寫這一份測試的時候被 `appendRows()` 咬了一次：它是**由第 1 欄開始逐個位
寫下去**，不是按欄名對號入座。keys 中間漏了一個鍵，整行資料就靜靜向左
移一格——`QuarterID` 寫進了 `RequestID` 欄，然後測試報「找不到待處理申報」，
而真正的成因在 fixture，跟被測的程式一點關係都沒有。

已經加了對齊檢查：keys 跟工作表第 2 行的機器鍵對不上就直接拋錯，
把成因寫在錯誤訊息裡。這種錯要即刻大聲講出來，不可以由得它變成一個
查半天的假 bug。

### G 組：現有污染版本的處理工具

#### `src/VersionCellAudit.gs`（唯讀）

選單 ▸ 測試工具 ▸ **清點格子分類（唯讀）**。掃描所有季度所有版本，
把五個桶的數字寫進 `VersionCellAudit` 工作表，有問題的行有底色。

**只看，不改。** 不會動任何一格派工、不會建立版本、不會刪任何東西。
唯一會寫的是它自己那張報告表。

分類一律經 `classifyGridCell_()`——全系統唯一的分類來源。不可以自己再寫
一套，否則這個工具會跟 grid／PDF 講不同的話。

#### 兩個指紋

**指紋一：`未能安排 ＝ 總格數 − 有派人`。**
現場 2026-08-20 見到的是 `273 − 194 = 79`。這條等式成立代表所有沒有人的
格都被算成「系統排不出」，即是「這一週不設」「特殊主日」「待確認」
三種原因整批不見了。

**指紋二：上一版有名字、這一版變成空白。**

⚠️ 這一項**光看桶是看不出來的**——掉了名字的格跟從來沒填過的格在五個桶
裡面長得一模一樣（都是「待確認」）。要分得出，唯一辦法是比較上一版。

而且這樣一併給出補救的路：上一版還留著那個名字，抄回來就是了。
報告會直接寫出是哪一天、哪個崗位、掉了的是哪個名字。

（本來寫了另一個指紋——「未能安排的格全部是非自動崗位」。E 組的修正
之後那個狀態不再落入 `GENUINE_GAP`，即是那個指紋永遠不會觸發。
已經拆走，換成上面這個真正搆得到的。）

#### 刻意沒有寫自動修復

Prompt T 明確要求，理由也站得住：

1. **那個名字系統根本不知道。** 外請講員不在 NameMapping，只有幹事知道
   那個主日請的是誰。系統能做的最多是「把上一版還留著的抄過來」——
   但上一版也可能已經是壞的，一鍵抄過去只會把錯誤散得更廣。
2. **多一個會自動改舊版本的工具，就是多一條沒有經過任何檢查就寫進資料
   的路。** 第三十四到三十八輪一連五輪修的都是同一類毛病：建立版本的
   時候有欄位沒有帶過去。教訓正正是「寫入的路愈多，愈難保證每一條都對」。

怎麼補寫在 `docs/污染版本處理指引.md`（寫給幹事，不是寫給工程師）。

### A 組：主流程六步

幹事的真實工作流程就是這六件事，順序固定：

| 步 | 內容 | 落到最後叫的是 |
|---|---|---|
| 1 | 生成下一季職事表 | `openGenerateDraft()`（原有） |
| 2 | 查看／修改職事表 ＋ 儲存我的修改 | `openSaveAndConfirm()`（原有） |
| 3 | 在職事表加入名單選單 | `apiApplyGridNameDropdowns()`（新） |
| 4 | 維護各崗位的事奉人員名單 | `apiOpenEligibilitySheet()` ／ `apiApplyEligibilitySheet()`（新） |
| 5 | 寄出 | `openReview()`／`openOfficial()`／`openResend()`（原有） |
| 6 | 要印紙本的人 | `apiGeneratePaperPack()` ／ `apiEmailPaperPackToSelf()`（新） |

**第 1、2、5 步完全沒有新的業務邏輯**——只是把入口搬到最頂、
把「要不要自己判斷」那部分拿走。第 3、4、6 步是新的。

#### 第 1 步：不要他揀季度

掣上面直接寫「生成 2099 年 4-6 月職事表」。判斷規則一句話：
**他現在看著的那一季如果還沒有生成過，就是它；否則就是下一季。**

已經開始、甚至已經過去的季度——**准許，但先彈警告**。擋住他不是我們的
位置：補一個漏掉的舊季度是真實會發生的事。

而且「已經開始」同「已經過去」用兩句不同的話，不合成一句「日期不對」
——合成一句就等於什麼都沒有講。

⚠️ 目標季度如果不是他現在看著那一季，會**先把頂部的季度選單切過去**。
不切的話，生成完之後畫面其餘部分仍然在講另一季，而他會以為生成失敗了。

#### 那條永久連結

生成之後畫面直接顯示，有一粒「複製連結」，旁邊一句人話：

> 這是唯一一條連結。它永遠指向你最近一次「儲存我的修改」的版本。
> 內容改了之後不用換連結，收到的人重新開就見到新版。

⚠️ `navigator.clipboard` 在 Apps Script 的 iframe 裡面**不一定用得到**。
所以有退路（`execCommand`），而且兩條路都會明確講結果——
複製失敗**不可以扮成功**，否則他會以為複製好了，貼出來卻是舊東西。

#### 第 3 步：下拉選單不可以變成限制

每個「系統會排」的崗位那一欄，設上該崗位的合資格名單選單，
一律 `setAllowInvalid(true)`——**有選單，但照樣可以打任何字**。

外請講員、新人、借調本來就不在任何名單上，而且是真實會發生的事。
一個「只准揀名單上的」選單會把這幾種情況直接堵死。

講員／翻譯／獻花那幾欄**刻意不設選單**：它們的值本來就是自由文字，
給個選單只會令幹事以為「不在選單上就是不可以」。

⚠️ 略過了的欄**一定要講出來**，而且要講原因。不講的話，幹事會以為
那一欄壞了，或者更差——以為那一欄不用填。

#### 第 3 步：一切正常就不要彈窗

改一格、撳「儲存我的修改」，如果規則檢查全部通過、沒有申報、
沒有認不出的名字——**直接儲存，講一句「已儲存」**。

彈一個沒有東西要他決定的窗，只會訓練他不看內容就撳確定；
而下一次真的有東西要看的時候，他一樣不會看。

⚠️「完全沒有問題」的定義刻意寫得**嚴**：任何一項有東西就照舊彈窗。
判斷錯的代價不對稱——多彈一個窗只是麻煩，少彈一個就是靜靜改了東西。

有東西要他決定的時候，兩粒掣改成〔照樣儲存〕〔返回修改〕——
「取消」在這裡不是對的講法，他不是放棄，是回去表上改那幾格。

#### 確認清單要講人話

原本一行是 `2027-07-11　主席#1　陳大文　HARD_ELIGIBILITY`。
對幹事來講 `HARD_ELIGIBILITY` 跟一串亂碼沒有分別。改成：

> 7 月 11 日　主席　陳大文——他未做過這個崗位

⚠️ 對不上的規則代號**照樣印出來**，不可以靜靜變成空白——
印一個代號最少查得回；印空白就等於說「這一格沒有問題」。

#### 第 4 步：用工作表維護名單，不是彈窗

現有的「崗位資格」畫面是一格一格改的。要一次過重排一個崗位的十幾個人，
在彈窗裡面點十幾次，比在試算表裡面複製貼上慢很多倍。

所以開一張 `崗位名單` 工作表，**一個崗位一欄**。改完回來撳
「儲存並套用名單」，先看預覽（新增了誰、移除了誰），確定才寫。

⚠️ 這一步**沒有取代**區三那個畫面，兩個都保留。
逐格微調用舊那個，整批重排用這一個。

⚠️ **認不出的名字不可以靜靜略過。** 這是本專案最反覆出現的一類 bug。
在這裡的形態是：幹事打錯一個字 ⇒ 系統認不出 ⇒ 靜靜當那一格是空的 ⇒
那個人被移出名單，而畫面上什麼都沒有講。下一季他就不會被排到，
而沒有人知道為什麼。所以**有認不出的名字就整批拒絕套用**。

⚠️ 移走是**停用，不是刪除**——跟區三那個畫面同一個做法。
而且被移走的人如果已經排在現有職事表上，要特別標出來：
移走名單不會把他從已排好的格子拿走。

### B 組：字大、載入回饋睇得見

Ivan 明講兩件事：**字太細他讀不到**，**載入回饋太細看不出在做什麼**。

- 內文基準由 15px 升到 16px，行高 1.65 → 1.75，主流程用一個明顯大一級的尺度
- **不用 `zoom`**——它會連邊框同陰影一起放大，而且沒得逐個元件微調。
  改用一個一致的字級尺度（`--fs-xs` 到 `--fs-2xl`），逐個元件講明用哪一級
- 載入回饋改成畫面中央一塊牌，講明**在做什麼**（不是一個轉圈），
  需時長的動作報得出進度，完成講「已完成」而且**停留 1.1 秒**才收
- 失敗有自己的樣（紅），跟成功分得出
- 加了 `@media (max-width: 700px)`——幹事有機會用平板或手機開

⚠️ 收牌一定要在刷新之後。在之前收就會出現「講了已完成、但畫面還是舊數字」
那個空窗。

⚠️ 新樣式一條 `display: ... !important` 都沒有加。這個檔案已經因為
`[hidden]` 被覆蓋而出過三次事（`.zone-body`、`.modal-backdrop`、`.prop-opts`），
現在的總閘是 `[hidden] { display: none !important; }`——
只要沒有人再寫第二條 `display: ... !important`，它就贏。
`main_flow_ui_shape.test.js` 數住這一點。

### C 組：一粒「寄出」，一個彈窗

幹事本來要在三粒掣之間自己揀（審閱／正式／重發），而那個判斷其實完全是
機械的——由這一季走到哪一步決定，沒有任何空間讓他選擇。

現在：**由系統判斷，用一句人話講出來，他看得見但不用自己想。**

- 「這一次是寄給堂委審閱（這一季還未正式發出過）」
- 「這一次是正式發出給全體」
- 「這一次是改動後重發（只寄給安排有改動的 N 位）」

在 `REQUESTS_APPLIED` 那一步，審閱同正式**兩粒都是著的**。這時候一律揀
行得最前那一個（正式發出），而「再寄一次審閱本」仍然做得到，
由彈窗另外給一條路，不會消失。

⚠️ **底層的 Stage 機器完全不變**——版本紀錄、SendLog、稽核、重發比對
全部靠它。撳落去之後走的仍然是 `openReview()`／`openOfficial()`／
`openResend()` 那三條已經在真實環境跑過的路。沒有另起爐灶，
是因為那條路上每一道閘（三層防重複、未儲存改動、公開連結、
附件資料夾、DRY_RUN）都是前面幾十輪逐個補回來的。

#### 未儲存改動要先問

〔繼續寄出〕〔先去儲存〕。這一問不可以省：幹事剛改完表、未撳儲存就撳寄出，
系統寄的是**上一次儲存確認那一版**——即是他剛改的那些不在裡面，
而他完全不會察覺。

#### 「寄什麼」是講事實，不是給他揀

Prompt U 要求「寄什麼」做成可以複選的勾選格（只寄連結／寄 PDF／
個人 highlight／`.ics`）。**這一項沒有做**，原因見下面「沒有做的部分」。

改為由真正會用到的範本推出來，照實講會寄什麼。畫一堆撳落去沒有作用的
勾選格，比不畫更差。

⚠️ 那條永久連結**一律要在信裡面**（Prompt U 的硬要求）。
系統檢查範本內文有沒有 `{PublicRosterUrl}`，**沒有就在彈窗上講出來**——
靜靜寄一封沒有連結的信，收信的人就沒有辦法自己去看最新版。

### D 組：沒有電郵的人要印紙本

一粒掣，列出是誰，兩個出口。

預設**把沒有電郵那批全部勾好**——他們一定要印，不應該要幹事逐個勾。
同時可以搜尋並加入有電郵但也想要紙本的人（有些長者兩樣都要）。

#### 為什麼不是 zip

`Utilities.zip()` 做得到，但**幹事拿不到那個檔案**：Web App 沒有辦法
直接把一個 blob 交給瀏覽器下載。唯一的路是先存去 Drive 再給連結——
而那樣跟直接給那個**已經放著全部個人 PDF 的資料夾連結**比較，
只是多了一個會過期、會累積、要清理的中間檔。

所以「下載」做成：**產生齊 PDF，然後給資料夾連結**。
Google Drive 本身的「下載資料夾」就會打包成 zip，那是幹事本來就熟悉的操作。
逐個人的連結亦一併給出，只想印其中一兩位的時候用。

#### 「寄到自己信箱」同 DRY_RUN

收件人**永遠**是現在操作的那個人自己（`Session.getActiveUser().getEmail()`），
不接受任何參數。這不是為了方便——是為了令這一條路**結構上不可能**
被用來寄給義工。

所以就算系統仍然在模擬模式，這一封都會真的寄出：DRY_RUN 要守住的是
「不會有義工收到一封他不預期的信」，而寄給自己不違反這一點。
這件事在確認畫面明明白白講一次。

附件按大小同數量自動分批（15MB／20 個），不分批的話人數一多就會撞
Gmail 上限，而那個英文錯誤訊息對幹事完全沒有意義。

### 收回上一輪一個決定

上一輪 C 組「寄什麼」停低了，理由是要把 options 物件由 `sendStage()` 一路

所以這一輪做了，但**收成三個決定**——功能覆蓋原本六個選項而少很多出錯機會。

### A 組：寄出彈窗三個決定

| 決定 | 選項 | 各階段預設 |
|---|---|---|
| 寄給誰 | `ALL` ／ `CHANGED_ONLY` ／ `PICK` | REVIEW、OFFICIAL ⇒ `ALL`；RESEND ⇒ `CHANGED_ONLY` |
| 附件 | `NONE` ／ `PERSONAL_PDF` ／ `FULL_PDF` | 該階段範本 `AttachType` 那一欄的值 |
| 日曆檔 | 附／不附 | `buildIcsAttachmentForPerson_()` 本來的自動判斷 |

#### ⚠️ 第一條規矩：幹事什麼都不揀，行為要同今日一模一樣

這是整組最重要的一條。`sendOptions` 缺席、或者其中一個欄位缺席，
一律退回今日的行為。`tests/send_options.test.js` 有一整節釘住：
五個階段 × 三種「什麼都沒有傳」的寫法（`undefined`／`null`／`{}`），
逐項對住今日的預設值比。

而且**分得出「他沒有揀」同「他揀了一個剛好一樣的值」**——
`overridden` 三個布林。AuditLog 要記得出這個分別，否則日後查
「為什麼那一次是這樣」的時候答不出。

#### ⚠️ 第二條規矩：`deliverOne_()` 不可以自己再判斷一次

這條路上第三十三、三十八輪連續修過兩個同一類的 bug：
`deliverOne_()` 用自己一套更粗的邏輯重新判斷「要不要寄」，蓋過上游決定。

所以：**`resolveSendOptions_()` 一次過把三個決定解析成結論**，
放進 `context.sendDecision`。落到 `deliverOne_()` 那一層，
`attachType` 已經是一個確定的值、`includeIcs` 已經是一個確定的布林值
——沒有任何東西要它再想。

收件範圍同樣在上游做：`sendStage()` 那條路在 `listRecipients_()` 之後
用 `filterRecipientsByScope_()` 篩一次；RESEND 那條路在
`sendResendStage_()` 裡面調整 `changedPersonIds`——**都在
`deliverOne_()` 被叫之前**。`tests/send_options.test.js` 比對兩者的位置。

#### 幾個具體判斷

- **「自己揀」但一個都沒有揀 ⇒ 拋錯**，不可以靜靜當成寄全部。
  靜靜寄全部是最壞的結果：他以為只寄給三個人，實際上整班人收到。
- **`PICK` 的鍵不可以只用 `PersonID`**。REVIEW 階段**只有 LIST 收件人**
  （堂委名單），他們沒有 PersonID。只用 PersonID 的話，在 REVIEW 揀
  「自己揀」會一個人都揀不到，而彈窗看起來完全正常。
  所以 LIST 收件人的鍵是 `LIST:` 加小寫電郵。
- **選了「全部人」而那個人內容沒有改** ⇒ 要在上游給他一個
  `notifyReason`。不給的話 `deliverOne_()` 那個 hash 保險絲會把他擋走，
  而幹事明明揀了「全部人」。這跟 `RESEND_ONLY_CHANGED=FALSE` 同一個意思。
- **`includeIcs` 一定要是布林才當作「他揀過」**。`'係'` 這個字串是
  truthy，直接當 true 就會靜靜開了一樣他沒有揀的東西。
- **今次用了什麼選項一定要記低**。`SendLog` 加了 `SendOptions` 欄，
  但現有的工作表沒有那一欄——`writeSendLogRows_()` 是按表頭逐欄寫
  （`headers.map(...)`），所以會靜靜略過。所以那裡見到沒有那一欄會寫
  一句 WARN，而且**同一份紀錄一定會寫入 AuditLog**（自由文字，一定寫得入）。

### B 組：永久連結一律注入信末

實測核對過七個範本的 `Placeholders` 欄：**一個都沒有用 `{PublicRosterUrl}`**。
有幾個用 `{SpreadsheetUrl}`，但那是幹事用的試算表連結，不是給義工看的公開
連結，兩樣不可以混淆。

即是說「範本會放連結」這個假設，由頭到尾都不成立。而上一輪彈窗那句
「範本裡面沒有放那條永久連結，要加的話去 EmailTemplates⋯⋯」會封封信都出，
而幹事什麼都做不到——他不會去改範本。

**所以改成系統自己加，不依賴範本。** 三種情況：

| 情況 | 做法 |
|---|---|
| 範本已經有 `{PublicRosterUrl}` | **不加**（避免同一條連結出現兩次） |
| 範本沒有 | 加在信末 |
| 這一季沒有公開連結 | **整段略過** |

第三種最重要：加一段「固定連結：」後面卻是空白、或者 `undefined`，
比不加更差——收信的人會以為系統壞了，而且會去撳一條不存在的連結。

`BodyHtml` 同 `BodyPlain` 兩邊都加。只做一邊的話，用純文字看信那些人
（很多長者的郵件程式）就沒有連結。

⚠️ 傳給 `appendPermanentLinkFooter_()` 的是**原始範本內文**，不是套用完的。
套用完之後 `{PublicRosterUrl}` 已經沒有了，就永遠偵測不到「範本本來有放」，
結果同一條連結出現兩次。

⚠️ **這個不做成選項。** 做成選項就有機會被關掉，而那一批人手上就只剩
一份會過期的附件。`tests/permanent_link_footer.test.js` 有一條斷言
釘住「三個寄出選項裡面沒有它」。

### C 組：未儲存就撳寄出 ⇒ 先問

第三十九輪已經有這一問，這一輪補的是**話講得夠不夠清楚**：

- 要講出**改了幾多格**（「你在表上改了 3 格」）
- 要講出**寄的是第幾版**（「寄出的會是第 8 版」）

只講「你有未儲存的修改」，幹事分不清是不是自己剛才那幾格，
也不知道寄出去那一份是什麼內容——結果他只會撳「繼續」算數。

〔先去儲存〕直接帶去第 2 步的「儲存我的修改」，不是只關窗
（關了窗他要自己再找一次）。沒有未儲存改動就**不彈這個窗**。

### D 組：「認不出的名字」加〔立即加入這個人〕

#### 拍板：維持硬擋，不加〔照樣儲存〕

Ivan 問過為什麼不給〔照樣儲存〕。**這個拍板要寫低，日後一定會再有人問。**

一個系統認不出的名字**沒有 `PersonID`**。所以那一格：

- 他收不到電郵（收件名單是按 PersonID 砌的）
- 沒有個人 PDF（檔名同內容都靠 PersonID）
- 不會被計入服侍次數（統計、平衡、上限全部按 PersonID）
- 不會被任何規則檢查覆蓋（資格、連續兩週、身分限制全部按 PersonID）

即是說：儲存了之後，那一格對那個人**完全沒有作用，而且沒有任何錯誤**。
職事表上看得見他的名字，系統裡面他不存在。

這正正是這幾輪一直在殺的那一個 bug class——**缺失被當成正常值**。
加一粒〔照樣儲存〕等於在系統裡面開一道門，讓那一類狀態合法地產生。

這句理由同時寫進了對話框本身——不寫的話，幹事只會覺得系統無理取鬧。

#### 但補一個出口

借調、外請、新人未入名單都會發生。叫他「去試算表新增」等於中斷手上的
工作再走一轉，而且回來之後要重新再撳一次儲存。

所以每一個認不出的名字旁邊一粒〔立即加入這個人〕：

1. 小表單：中文名（已填好——他剛才打過一次）、英文名、電郵（都可留空）
2. 順帶一問「同時讓他可以做〈該崗位名〉嗎？」，**預設勾選**
   （他既然被排在那一格，多數就是要做那個崗位）
3. 加完**自動重新檢查**——不自動的話他要自己記得再撳一次，
   而他多數會以為加完就搞掂
4. 撞名**只提示不阻擋**（真的有兩個同名的人是正常事），但一定要講出來，
   否則他會以為加到原本那一個上面

⚠️ 沒有電郵是合法的（現時就有幾位），但要提一句「他收不到信，
要用第 6 步印紙本」。不提的話他會以為加完就萬事俱備。

⚠️ `apiAddPersonForUnresolvedName()` **沒有自己一套新增邏輯**——
它叫 `apiAddPerson()` 同 `apiSaveEligibilityBatch()`，即是區三那兩個
畫面用的同一條路。另起爐灶就會變成「同一件事有兩個做法」，
而其中一個一定會落後。

### E 組：第 1 步要看生成日期

實測撞到：今日是 2026-08-21，那粒掣寫住「生成 2027 年 1-3 月職事表」，
而 `2027T1` 的 `GenerateOn` 是 **2026-11-27**——還有三個多月。
那一季是留來真正上線那一季，今日撳落去會把它用掉。

原本的規則只看「有沒有生成過」，完全沒有看「到了生成日期沒有」。

所以加了第三種警告 `TOO_EARLY`（另外兩種是 `PAST`／`STARTED`，維持不變），
而且掣旁邊直接寫住生成日期同還有幾多天。

⚠️ 這**仍然是警告，不是阻擋**。提早生成不會出錯，只是之後義工的情況
可能會變、到時要重新生成。擋住他不是我們的位置。

⚠️ 判斷次序：「已經過去」同「已經開始」行先。一季既已經開始、
又未到生成日期，是資料本身矛盾（`GenerateOn` 填錯了），
這時候講「已經開始」對幹事有用得多——那才是他看得見的事實。

⚠️ 沒有填 `GenerateOn` 就照講「沒有填」，**不可以當成 0**：
0 的意思是「今日就是生成日」，那是一個肯定句，而我們根本不知道。

#### F4 抓到的真 bug

生成完成畫面那段統計本來寫 `if (a.personId) return;`——即是只認

但 `ASSIGNED` 有**兩種**（第三十七輪 A 組加的）：有 PersonID、

然後去追一個不存在的問題。這跟第三十八輪 E 組是同一類的東西。

#### F5：那個工具本來跑過等於沒有跑過

實測：Ivan 跑過「清點格子分類（唯讀）」，但

- 讀不到報告（它只寫自己那一張 `VersionCellAudit`，他不知道要去哪裡看）
- `AuditLog` 一行紀錄都沒有（它根本沒有寫）

一個「做完之後查不到自己做過什麼」的診斷工具，比沒有更差——
下一次出事的時候，沒有人答得出「上一次清點是什麼時候、看到什麼」。

現在三個地方都寫：`Diagnostics`（摘要）、`AuditLog`（一行結論）、
