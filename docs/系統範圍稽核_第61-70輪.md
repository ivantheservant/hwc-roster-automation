## 第六十一輪批次

**範圍：只改亂行機的效率，不改它驗什麼。**

### 現場

2028T3 上面跑得動、零失敗，但**一批 4.5 分鐘只跑得 2 步**。
照這個速度，50 步要撳 25 次、超過一個鐘。

已跑兩步都成功：第 1 步「儲存並確認」造出 v1（`cellCount: 2`）；
第 2 步「寄給堂委審閱（模擬）」`dryRun: 3`。Stage 現為 `REVIEW_SENT`。

### ⚠️ A 組的前提不成立——先寫這一段

原本的判斷是：`MonkeyState` 顯示「已抽次數 10、已跑步數 2」，
所以亂行機是「先抽再問合法、不合法就重抽」，抽 10 次只中 2 次。

**這兩件事都不是這樣。**

**一、「已抽次數」不是「試了幾多次」。**
它是 `rnd.drawnCount()`——這一支亂數用掉了多少個數。
而 `makeMonkeyRandom_(seed, skip)` 續跑時的**快轉迴圈也會加**：

```js
for (let i = 0; i < (Number(skip) || 0); i++) next();   // next() 內 drawn++
```

所以「10」＝「之前幾批用掉 8 ＋ 這一批用掉 2」。
它存在的理由只有一個：續跑時要快轉到同一點，否則「繼續亂行」
會由同一個 seed 的第一抽再走一次同一條路。

**二、亂行機從第一天就是先篩後抽。**
`git show ccd6cc2:src/MonkeyRun.gs`（`MonkeyRun.gs` 的第一個版本）
第 270–278 行：

```js
const legal = actions.filter(function (a) {
  try { return a.legal(facts); } catch (err) { return false; }
});
if (legal.length === 0) { … break; }
const picked = legal[Math.floor(rnd() * legal.length)];
```

`git log -S"actions[Math.floor" -- src/MonkeyRun.gs` 沒有任何 commit。
**「抽完先問合法、不合法就重抽」那一段從來沒有存在過。**

所以 A 組那個改法沒有東西可以改——真正的樽頸在 B 組（見下）。

### A 組：仍然做了的那一項

A 的 ⚠️ 那一條是真的缺口。舊寫法：

```js
if (legal.length === 0) {
  stepLog.push({ step: i, action: '（沒有合法動作）', outcome: '停手', invariant: '' });
  break;
}
```

**沒有記成失敗、沒有印路徑。** 於是報告會寫
「跑了 1 / 20 步，0 項失敗」，而沒有人知道為什麼只有 1 步。

現在：記成一項失敗、帶完整重現路徑，報告最頂印

```
⛔ 這個狀態下沒有任何合法動作，已乾淨停手。
　 停在第 1 步，狀態 DRAFT|-1|0（Stage｜最新版本號｜認不出的格數）
　 這一批可以撳的動作有 9 個，沒有一個在這個狀態下合法。
　 完整重現路徑：…
　 用同一個種子（7）重跑會走同一條路。
```

⚠️ 跟第六十輪 A3 防打轉閘同一個道理：
**一份「跑了幾步、零失敗」的報告看上去好像沒事**——那個才是最危險的輸出。

### B 組：抽驗 ＋ 定期全驗（**真正的樽頸**）

舊寫法每一步都 `runAllInvariants_(quarterId)`——沒有傳 set 就是 `ALL`。
`Invariants.gs` 自己的註解已經寫明哪幾條貴：

> 貴那幾條（I04 全表 10,920 行、I08 每條要行一次完整 plan）
> 留到全部情境跑完之後才一次過跑

自測機第五十輪就已經分了 `PER_SCENARIO` / `FINAL`，**而亂行機沒有跟上**。

現在：

| | |
|---|---|
| 每一步 | `INVARIANT_SET.PER_SCENARIO`（I01／I05／I09／I10） |
| 每 10 步 | `INVARIANT_SET.ALL` |
| 最後一步 | `ALL` |
| 收尾 | 如果最後一步不是全套那一步，**補跑一次** |

⚠️ 收尾那一次不可以省。迴圈會因為時間到、原地打轉、沒有合法動作、
`DRY_RUN` 變了而中途 `break`——省了的話，最尾那段改動一次全套都沒有驗過。

報告分開講，而且失敗行標明是哪一次驗到的：

```
不變量：逐步跑快的那批（I01／I05／I09／I10）；全套跑了 2 次（每 10 步一次，另加收尾補跑第 12 步）。
🔴 第 10 步　不變量 I04（全套那一次驗到；可能是前面幾步之內壞的）
```

⚠️ 最後那一句是必要的：一條只在全套才驗到的不變量紅了，
代表它是在前面某幾步之內壞的，**不一定是這一步**。

⚠️ 快那批的 id 是從**真正跑過那一次**的結果取回來的，
不是在亂行機裡另寫一份清單。另寫一份的話，
`INVARIANT_SET.PER_SCENARIO` 日後加減一條，報告就會講一個不存在的事實。

### C 組：`MONKEY_SKIP_SLOW_ACTIONS`

⚠️ **「產生個人 PDF」不是亂行機的一個動作。** 亂行機的十個動作裡面
沒有這一個，`generatePersonalPdfBatch_()`（`PdfBatch.gs`）
由頭到尾沒有任何一個動作叫得到。

亂行機裡面真正慢的那一個是**「正式發出給全體（模擬）」**：
`apiStep4Confirm()` → `executeStep4Send_()` 要逐個收件人（全體 ≈ 58 位）
解析、砌信、查那個人的個人 PDF。就算 `DRY_RUN` 不真寄，上面幾樣一樣要做足。
（它**讀**個人 PDF，查不到就記 `errorPdfMissing`；它不產生。）

所以開關按你的規格做齊，而標了 `slow` 的是這一個：

```

「測試工具 ▸ ⚠️ 亂行機（沙盒季度，DRY_RUN）」是否跳過產生個人 PDF 這一類很慢的動作。
TRUE（預設）＝跳過。那條路自測機 S08（產生個人 PDF）和 S09（正式發出，DRY_RUN）
已完整驗過，不會漏測。想它也一起亂行，就改 FALSE。
```

⚠️ 只是**篩走**，動作仍然留在清單裡面。刪走的話，
兩個月之後沒有人記得亂行機本來走過那條路。

報告開頭固定印：

```
已跳過的慢動作：正式發出給全體（模擬）（MONKEY_SKIP_SLOW_ACTIONS=TRUE）
　 ・正式發出給全體（模擬）：要逐個收件人（≈58 位）砌信同查個人 PDF；自測機 S08 ＋ S09 已完整驗過同一條路
　 ⚠️ 連帶：Stage 上不到「已正式發出」，所以「改動後重發（只算，不寄）」這一步也不會被抽到。
　 想它也一起亂行，把 MONKEY_SKIP_SLOW_ACTIONS 改成 FALSE。
```

⚠️ 那一行「連帶」是這一輪加的，因為跳過它的代價比表面大：
Stage 上不到 `OFFICIAL_SENT` ⇒「改動後重發」的掣永遠不亮 ⇒
十個動作實際只剩八個會被抽到。這不是 bug，是開關的代價，
但不講明的話，下次會以為那一步壞了。

## B 組：亂行機的步數計錯，永遠撳不到 50/50

### 現場（Claude 直接由試算表讀到）

| 時間 | 已抽次數 | 已跑步數 |
|---|---|---|
| 早前 | 10 | 2 |
| 之後 | 32 | 4 |
| 現在 | 70 | **3** |

已抽次數一路加（證明隨機序列真的接住走），但「已跑步數」由 4 跌到 3。

成因：`writeMonkeyState_()` 寫進表的是 `report.ranSteps`——
**當前這一批**跑了多少步——而 `readMonkeyState_()` 由頭到尾沒有讀回它。
報告第一句「跑了 N / 50 步」用的就是這個會歸零的數。

> ⚠️ 底層一直有進展：最新一批三步是「寄堂委審閱（模擬，dryRun:3）
> → 改 grid 1 格 → 儲存並確認造出 v7」，跟上一批完全不同，
> 季度已走到 v7，全程零不變量失敗。
>
> **不是機器不動，是計數器騙人。**
> 而一個會歸零的進度計數器比沒有計數器更差——
> 它會令人以為機器在打轉，然後放棄。

### B1：`totalSteps`

- `runMonkey_(steps, seed, skipDraws, priorSteps)` 多收一個累計步數
- 迴圈裡 `i` 仍然是**這一批**的第幾步（時間閘、`DRY_RUN` 複查、
  全套不變量的節奏都靠它），另外算一個 `absStep = priorStepCount + i`
  用來寫報告、`MonkeyLog`、失敗紀錄
- `MonkeyState` 第三欄由「已跑步數」改成「累計步數」，寫 `totalSteps`

第七十三輪回歸 K1（2028T3 已正式發出）：用〔填講員／翻譯／獻花〕把一格獻花改成一位會友，之後〔儲存及寄出〕回「沒有偵測到任何改動」。讀碼：`apiSavePreacherTranslationEntry()` 找最新版本，**直接改那一版的 `RosterAssignments` 和 grid**，不理那一版是不是已經寄出——①已寄出的內容被改寫、和寄出紀錄對不上；②「只寄給安排有改動的人」拿最新版和「上次寄出的版本」比較，兩者是同一版，填獻花的那位會友永遠收不到通知。Ivan 已批准修改 `src/` 實作（BC 組）。

### 改動

- **判斷「已通知過人」**：`isVersionNoticeSent_(quarterId, versionNo)`（`SheetReader.gs`）＝`SendLog` 有**這一版**的 `OFFICIAL` 或 `RESEND` 紀錄，而且 Status 屬「已收到」（`isNoticeReceivedRecord_()`＝SENT／DRY_RUN／SKIPPED_UNCHANGED／EXTERNAL，補寄工具同一個共用判斷）。按版本判斷：已正式發出之後存成新一版（未寄）就恢復照舊直接填；寄失敗（FAILED）不算；`SendLog` 工作表不存在＝從來沒寄過。
- **填格工具**（`PreacherTranslationFill.gs` `apiSavePreacherTranslationEntry_locked_()`）：最新一版已通知過人 ⇒ **不寫 `RosterAssignments`，只寫最新那張職事表工作表的那一格**（保護中的工作表照舊「暫時解除→寫入→重新保護」）；工作表找不到那一格就拋錯，不當成功；回傳多一個 `sheetOnly`；AuditLog 備註寫明只寫了工作表。未通知過人的版本（初稿、只寄過審閱本）**完全照舊**。
- **彈窗資料**（`apiListPreacherTranslationPending()`）：多回 `writesToSheetOnly`；已通知過人的版本，工作表上已有人名的格仍然列出，帶 `currentName`、`sheetOnly`（第 4 點：讀工作表上的值，幹事改完再開彈窗見到的是新值）。
- **畫面**（`ui/ScriptZone2.html`）：`writesToSheetOnly` 時最上面出提示「這一季已經正式發出。你在這裡改的格會先寫在職事表上；要撳第 2 步〔儲存及寄出〕才會成為新一版，之後用「改動後重發」通知受影響的人。」（取代較籠統的舊提示）；儲存後狀態寫「已寫在職事表，未儲存成新版本」，不寫「已儲存 ✓」。
- **「開季前準備」未填計數**（第 5 點）：原本只讀 `RosterAssignments`；已通知過人的版本改為「`RosterAssignments`＋工作表上已填的格」合併（`WebAppPreQuarter.gs` `buildPreQuarterChecklistInputs_()`），否則填完仍顯示未填。未通知過人的版本照舊。
- **〔儲存及寄出〕要偵測得到這一格（Opus 原 prompt 沒有發現的缺口）**：`buildGridOverlayState_()`（`FineTune.gs`）自第三十五輪起對 `AutoGenerate=FALSE` 的崗位「整格略過」（因為當時它們的唯一寫入途徑是填格工具，同時寫長表和 grid）。所以工作表上那一格改動**偵測不到**，〔儲存及寄出〕仍會回「沒有偵測到任何改動」。改為：**只有已通知過人的版本**才偵測這類崗位的 grid 改動（`buildFineTuneContext_()` 讀 `SendLog` 算好 `context.noticeSent`，純運算函式不讀工作表）；未通知過人的版本維持整格略過（不改變現有行為）。外請的自由文字名（不在 NameMapping）不算「認不出的名」（`unresolved`），並由 `materialiseManualEdits_()`（`StateSource.gs`）把 grid 文字帶進新一版（名字不蒸發、來源 MANUAL）。
