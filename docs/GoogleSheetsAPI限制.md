# Google 試算表 API 結構性限制

**讀者**：本專案嘅開發者（包括另一個對話嘅 Claude）。呢份文件記錄
`SpreadsheetApp`／`Sheet`／`Range` 呢幾個 Google Apps Script 類別
**唔直覺、容易寫錯**嘅結構性行為，全部都係本專案實測撞到過先寫落嚟嘅，
唔係憑空列舉 API 文件。

**背景**：第十二輪批次（版面轉置）38 個測試檔全部 PASS，但真實試算表
連續兩次發佈都拋錯，之後再發現三個顯示問題。原因係之前嘅測試全部係
「靜態原始碼字串檢查」，完全冇一個測試真正**執行**過會寫試算表嘅函式，
所以完全捉唔到呢份文件列嘅呢類限制。第十三輪批次修正咗全部問題，
並且用 `tests/helpers/sheet_mock.js` 補回真正嘅行為測試（見
`tests/public_roster_write.test.js`）。

## 1. 合併儲存格不可以跨越凍結／非凍結分界線

**限制內容**：如果一張工作表已經（或即將）凍結咗某幾行／某幾欄，
唔可以有任何合併儲存格嘅範圍**一半喺凍結範圍入面、一半喺出面**——
列同欄兩個方向都適用。

**實際錯誤訊息**（Google 原文，本專案實測撞到過）：

- 列方向：`You can't merge frozen and non-frozen rows.`
- 欄方向：`Sorry, you can't freeze columns which contain only part of a merged cell.`

**本專案喺邊度撞到**：`PublicRoster.gs` 嘅 `writePublicRosterContent_()`
第十二輪批次版本，第 1 行（標題）用咗 `getRange(1, 1, 1, colCount).merge()`
橫跨全部欄，但只凍結第 1 欄（`setFrozenColumns(1)`）——呢個標題合併格
必然一半喺凍結欄（第 1 欄）入面、一半出面（第 2 欄起），結構性違反呢個
限制。

**點解會有時得、有時唔得**：第一次喺一張全新（冇任何凍結狀態）嘅工作表
執行合併，因為當其時仲未凍結任何嘢，`merge()` 唔會撞到呢個限制，
會成功。**凍結（`setFrozenColumns()`）要到之後先執行**，於是第一次睇落
「冇事」。但第二次執行（重新發佈）嗰陣，上一次遺留低嘅凍結狀態（見
下面第 2 條）依然存在，呢一次嘅合併就會喺凍結狀態已經存在嘅情況下嘗試
跨界，即刻拋錯——呢個就係「頭一次冇事、第二次先至爆」嘅根源，唔係
隨機、唔係環境問題，係結構性必然。

**本專案點樣避開**：

1. 需要橫跨成行嘅標題唔再用合併——改為單一儲存格（例如 `A1`）裝長
   文字，靠 Google 試算表對「長文字、右邊儲存格冇內容」嘅預設溢出顯示
   行為，視覺效果一樣但完全冇合併／凍結衝突可能。
2. 其餘全部合併（月份標題橫跨日期欄、崗位名稱直向合併多個 slot）刻意
   設計成**完全落喺預定嘅凍結範圍之內、或者完全喺出面**，唔會跨界：
   月份合併全部喺欄 2 起（凍結範圍只係欄 1），崗位名稱合併全部喺欄 1
   之內（凍結範圍剛好係欄 1）。
3. **合併一定排喺凍結之前**（見下面「建議嘅安全次序」）。

## 2. `Range.clear()`／`Sheet.clear()` 唔會解除合併，唔會歸零凍結列／欄

**限制內容**：`clear()`（或者只清內容嘅 `clearContent()`）淨係清值同
格式，**唔會**：

- 解除任何已經存在嘅合併儲存格；
- 將 `setFrozenRows()`／`setFrozenColumns()` 設定嘅凍結範圍歸零。

呢個唔係直覺行為——「clear 咗」聽落應該係「乾淨返」，但合併同凍結兩樣
嘢會完整保留到下一次寫入。

**本專案喺邊度撞到**：`writePublicRosterContent_()` 每次發佈都會
`sheet.clear()` 之後重新寫入，但因為 clear() 唔會解除舊有合併／凍結，
第二次執行嗰陣，上一次遺留低嘅合併／凍結狀態同呢一次即將設定嘅新
合併／凍結產生衝突——呢個就係第 1 條限制「頭一次冇事、第二次先至爆」
嘅直接原因。

另一個相關但唔同嘅問題：`clear()` 亦唔會刪除多餘嘅欄／列。如果新版面
只需要 14 欄，但工作表上一次寫過 24 欄嘅版面，`clear()` 之後嗰 10 欄
會保持存在（雖然冇內容，但欄闊、欄本身仍然喺度）——實測發現右邊確實
殘留咗上一版嘅內容同格式。

**本專案點樣避開**：新增共用 helper `resetSheetToBlankSlate_()`
（`Utils.gs`），重寫任何一張已經寫過嘅工作表之前**一定要**先呼叫：

```
1. setFrozenRows(0)／setFrozenColumns(0)——凍結一定要行喺解除合併之前，
   凍結範圍仲存在嘅話，部分合併格可能解除唔到。
2. 對成張表嘅範圍呼叫一次 breakApart()——解除全部合併儲存格（唔使逐個
   合併群組分開搵，對一個涵蓋全表嘅 Range 呼叫一次就夠）。
3. clear()／clearNotes()／clearConditionalFormatRules()／
   clearDataValidations()——清晒內容、格式、備註、條件格式、資料驗證。
4. deleteColumns()／deleteRows()縮到得返 1 欄 1 行——等寫入端自己用
   ensureSheetDimensions_() 擴到啱好嘅尺寸，唔會有舊版面殘留嘅多餘
   欄／列。
```

**唔可以假設**「呢張工作表係第一次寫」，亦唔可以假設「上一次執行完全
成功、留低嘅係一個乾淨、完整、符合預期嘅狀態」——如果上一次執行寫到
一半就拋錯，留低嘅可能係一個介乎新舊版面之間嘅混合狀態。`resetSheetToBlankSlate_()`
唔去推斷上一次停喺邊一步，一律強制清到底，令重寫邏輯唔使理會歷史狀態。

## 3. 合併儲存格之間不可以部分重疊

**限制內容**：兩個合併範圍如果部分重疊（唔係完全一致、都唔係完全冇
交集），`merge()` 會拋錯。完全一致嘅範圍（即係對同一個範圍再 merge
多一次）係安全嘅，等同無操作。

**本專案有冇實際撞到**：冇直接撞到呢一個（本專案嘅合併範圍設計上唔會
互相重疊），但 `sheet_mock.js` 有實作呢個限制嘅模擬，因為「重寫已經有
殘留合併嘅工作表」（見第 2 條）本質上就係新舊合併範圍好大機會部分重疊
嘅情況——如果冇第 2 條嘅 `resetSheetToBlankSlate_()` 先解除晒舊合併，
呢一條限制隨時都會撞到。

## 4. 儲存格內容嘅自動型別判斷（純數字字串會被當做數字）

**限制內容**：`setValues()`／`setValue()` 收到一個「睇落似數字」嘅
字串（例如 `"3"`、`"10"`）時，Google 試算表**唔會**當佢係純文字保留，
而係自動判斷成數字型別儲存格，之後套用嘅預設（或者繼承自舊格式嘅）
數字格式可能帶小數位，顯示變成 `"3.0"`。

呢個唔係本專案獨有嘅發現——`Utils.gs` 嘅 `applyTimestampFormat_()`
（好耐之前已經寫嘅函式）檔頭已經有類似嘅註解：「即使我們寫入的是字串，
Google Sheets 仍會把『像日期』的字串自動轉成日期值」，講嘅係同一類
行為，只係對象係日期唔係數字。

**本專案喺邊度撞到**：`RosterWriter.gs` 嘅 `formatShortDateLabel_()`
第十二輪批次版本，回傳純數字字串（例如 `"3"`）做日期標籤，寫入公開
試算表之後顯示變成 `"3.0"`。

**本專案點樣避開**：`formatShortDateLabel_()` 改用帶中文字嘅可配置
樣板（預設 `{M}月{d}日`，例如「1月3日」），保證輸出一定帶非數字字元，
試算表無論如何都唔會將佢判斷做數字。`tests/public_roster.test.js` 有
一個永久回歸測試，直接斷言預設樣板嘅輸出**唔可以**符合 `/^\d+$/`
（純數字）呢個 pattern。

**類似情況要留意**：任何寫入試算表嘅字串，如果原始資料本身係數字或者
日期（例如版本號、金額、日期），都要考慮清楚會唔會被自動判斷型別，
需要嘅話用文字樣板包裝，或者明確 `setNumberFormat()`／喺數字前加
`'`（強制文字）。

## 5. 建議嘅安全次序（寫入一張會設定版面嘅工作表時）

綜合以上幾點，本專案總結出嘅標準次序（`writePublicRosterContent_()`
係目前唯一嘅實作範例）：

```
1. resetSheetToBlankSlate_(sheet)  —— 完全還原（見第 2 條）
2. ensureSheetDimensions_(sheet, 需要嘅行數, 需要嘅欄數)  —— 擴到啱好嘅尺寸
3. 寫內容（setValue／setValues／setBackground(s)／setFontWeight 等）
   —— 呢一步完全未合併、未凍結，寫入次序可以自由調整
4. 合併（merge()）—— 一定要等內容寫晒、位置穩定之後先做；設計合併範圍
   時要確保唔會跨越即將設定嘅凍結分界線（見第 1 條）
5. 欄闊／列高（setColumnWidth／setRowHeight）—— 獨立於合併／凍結，
   邊個位都得，但建議跟返內容一齊做收尾
6. 凍結（setFrozenRows／setFrozenColumns）—— 一定要排喺最後，呢個時候
   全部合併已經到位，凍結範圍可以一次過對照埋去，唔會切開任何合併格
```

**任何一步拋錯都應該令函式整體失敗**（唔應該用 try/catch 吞咗令後面
嘅步驟喺一個唔一致嘅中途狀態下繼續跑）——`writePublicRosterContent_()`
冇喺任何一步加 try/catch，靠呼叫端（`runPublishPublicRoster_()`）嘅
頂層 try/catch 統一處理錯誤，符合本專案一貫「錯誤要清楚俾使用者睇到，
唔靜靜吞咗」嘅原則。

## 6. mock 層做得到幾多（`tests/helpers/sheet_mock.js`）

第十三輪批次新增咗一個輕量版試算表 mock，等會寫試算表嘅函式可以喺
Node 環境真正執行一次，唔再淨係測「原始碼有冇出現某個函式名」。
`MockSheet`／`MockRange` 有實作：

- ✅ 上面第 1、2、3 條限制（合併跨凍結分界線、`clear()` 唔解除合併／
  凍結、合併部分重疊）；
- ✅ `_seedResidualState()`：可以由測試直接種入「上一次執行留低嘅
  殘留狀態」（凍結、合併、尺寸、內容），模擬重寫已經被寫過嘅工作表；
- ✅ 儲存格值／背景色／字型粗細／換行／對齊／數字格式；
- ✅ 欄闊／列高記錄（可以喺測試斷言實際套用咗嘅數值）。

**做唔到／簡化咗嘅部分**：

- `deleteColumns()`／`deleteRows()` 淨係縮細 `_maxCols`／`_maxRows`，
  **唔會**將右邊／下面嘅資料實際向左／向上移。喺本專案實際嘅呼叫序
  （一定先 `clear()` 晒所有值先至刪欄／刪列）之下呢個簡化唔影響任何
  測試結果，但如果將來有第二個呼叫點喺仲有資料嗰陣就刪欄／刪列，
  呢個 mock 唔會如實反映。
- 完全冇實作第 4 條（純數字字串自動判斷型別）——呢個限制係 Google
  試算表**顯示層**嘅行為（型別判斷 + 數字格式渲染），mock 唔會實際
  渲染畫面，呢一條改為喺純函式層面測試（`formatShortDateLabel_()`
  嘅輸出斷言，見上面第 4 條）。
- 冇實作 `setDataValidation()`（本專案公開/個人頁面寫入路徑目前完全
  唔用資料驗證，`clearDataValidations()` 做咗 no-op）。
- 冇實作篩選器（`createFilter()` 等）——本專案目前冇任何寫入點會建立
  篩選器。
- 唔驗證儲存格內容嘅實際渲染／型別轉換（第 4 條淨係喺純函式層測）。

如果將來新增嘅功能會用到以上未實作嘅方法，呢個 mock 需要相應擴充，
唔應該假設佢已經涵蓋晒全部 Sheets API 行為。
