## 第五十一輪批次

**測試揀「對系統影響最小」的做法，可能正好觸發系統最嚴厲的一道閘。**

S03 想驗「未儲存格數數得對」，於是揀了一個系統一定認不出的字，
以為這樣最乾淨。結果 `unresolvedCount` 變成 3，
而系統的規矩是「有認不出的名字就什麼都不准做」——
後面七條情境連環倒，主流程一步都沒有跑過。

系統在那九條紅裡面一次都沒有做錯。錯的是測試對系統的理解。

### A 組：S03 寫的字系統認不出

**修正前**（`src/SelfTestRunner.gs`）：

```js
// ⚠️ 寫一個**一定唔會解析成真人**嘅字。…
selfTestWriteGridCell_(…, '自測改動' + (i + 1));
```

那個判斷本身講得通——S03 只想驗「未儲存格數數得對」，
而寫一個真名就會變成「換了另一個人」，是另一種情境。
而它確實驗到了：`gridChangeCount === 3`，S03 是綠的。

**但同一個動作順手令 `unresolvedCount` 變成 3。**

**修正後：**

| | |
|---|---|
| **A1** | 現場由 `NameMapping` ＋ `Eligibility` 揀一個**認得出**的人。⚠️ **不寫死人名**——寫死的話，日後有人離開名單，自測機就會無聲無息地壞掉，而那正正是這部機器要擋的事 |
| | 挑選規則：必須在 `NameMapping` 找得到／必須跟該格現時的人不同／**優先**揀該崗位合資格的人。揀不到合資格的，退而求其次，但**要在報告講明**——不講的話，S05 那條規則提示會變成一個查極查不到來源的雜訊 |
| **A2** | S03 同時驗兩個數：`gridChangeCount === 3` **同** `unresolvedCount === 0`。⚠️ 第二條是關鍵。沒有它，同一個坑下次還會踩 |
| **A3** | 新增 `S16　認不出的名字：整批拒絕，而且講得出是哪幾格`，**排在最後**，而且**自己收拾**（把那一格改回原本的文字，並斷言 `unresolvedCount` 回到 0） |
| **A4** | S10 同樣揀真名，而且**開始之前先驗前置狀態**——不乾淨就報「上一個情境留下了未清理的格」並停下，不再往下跑 |

⚠️ A4 那一條的理由：一個在污染狀態下硬跑的情境，它的紅和綠都沒有意思。

### B 組：S04 斷言的是一個故意的短路

`buildUnsavedSendPreview_()` 在 `canSendUnsaved=false` 時回傳空預覽
——**這是對的**，因為那個畫面根本不會出現。
S04 斷言「拿得到 3 格明細」在那個前提下本來就不可能成立。

**修正後**：先斷言 `canSendUnsaved === true`；是 false 就報
「前置條件不成立，下面那一條不驗」並 return。

⚠️ 一個根因報成兩條紅，會令報告看起來比實際嚴重。

### C 組：S14 叫了重新生成，但版本號沒有變

**C1 查證結果：是 (b)。**

`apiGenerateDraftExecute()` 在已經有版本的季度上回傳：

            現在的情況：沒有生成任何東西，職事表完全沒有改動。…' }

`findLatestVersionNo() >= 0` 就直接 return 那個物件。）

### D 組：連環倒要報成「被擋住」

**D1**　情境宣告 `dependsOn`。依賴的情境是紅／ERROR／BLOCKED ⇒
這一個標 `BLOCKED`（**不是紅**），註記寫「被 SXX 擋住，沒有跑」。

⚠️ 續跑時，**上一次的結論也算數**（`byId` 由 `state` 起頭）——
否則一個「上一次紅、今次跳過」的上游就擋不到下游。

⚠️ 有一條測試守住「沒有一個情境依賴一個排在它後面的情境」——
那種依賴永遠不會生效，而它看起來好像有防護。

**D2**　報告摘要獨立數出「被擋住」，並且分節印：

```
自測機：16 個情境　6 綠　1 紅　2 被擋住　0 跳過　0 未跑
（情境按執行次序排，不按編號。）

🔴 真正失敗（1 條）
　S05 …

🚧 被上游擋住（2 條，修好上游之後會重跑）
　S06　S07
```

⚠️ `BLOCKED` **不等於通過**。只數綠同紅的話，一份「6 綠 1 紅」的報告
看起來像情況不錯，而實際上有兩條根本沒有跑過。

**D3**　「只重跑紅色情境」一併清走 `BLOCKED`——
不清的話，修好上游之後被擋住那幾條仍然不會跑，而那幾條才是重點。

### E 組：兩個小的

**E1**　「用了 4 分 60 秒」。

成因：先 `Math.floor` 取分鐘、再 `Math.round` 取秒。
299.6 秒 ⇒ 分鐘 `= floor(4.99) = 4`、秒 `= round(59.6) = 60`。

修正：**先把總秒數 round 一次**，再拆分鐘同秒。修正後 299.6 秒 ⇒「5 分 0 秒」。

**E2**　S11 的「實際」同「證據」是同一段長文字，印了兩次。
修正：`c.evidence === c.actual` 就只印一次。
證據欄應該講**這個值從哪裡來**，不是把值再抄一次。

### A 組：造了版本，公開連結沒有更新

公開連結那個畫面自己寫住：

> 這是唯一一條連結。它永遠指向你最近一次「儲存我的修改」的版本。
> 內容改了之後不用換連結，收到的人重新開就見到新版。

**A1 逐個入口查過：**

| 入口 | 實作 | 之前 | 判斷 |
|---|---|---|---|
| 步驟 1 生成初稿（幹事介面主流程） | `WebAppGenerate.gs` | ✅ 有發佈 | 本來就對 |
| 進階功能 ▸ 重新生成初稿 | `WebApp.gs` `apiGenerateRoster()` | ❌ | **應該發佈**——它造出新版本取代原本那一版 |
| 試算表選單 ▸ 生成 | `Menu.gs` `runGenerateRoster_()` | ❌ | **應該發佈**——舊入口仍然撳得到，造出來的版本一模一樣 |
| 四階段流程 ▸ 步驟 1 | `FourStageFlow.gs` `runFourStageStep1_()` | ❌ | **應該發佈**——另一條舊路，同上 |

現場是自測機 S14 的 I09：

```
⚠️ 不變量：I09｜預期 v1｜實際 v0
　 PublicLinks.LastPublishedVersion=0；findLatestVersionNo()=1
```

幹事重新生成一次，然後同堂委講「連結已經更新」，
而堂委開連結見到的仍然是舊那一版——**中間沒有任何一個畫面提示過**。

**A2**　三個入口補上發佈，全部用**同一支** `tryPublishPublicRoster_()`。
⚠️ 這一組 bug 的成因就是「同一件事四個地方做，其中三個漏了」；
再各自補一次，只會把四個分岔變成四個新分岔。

**A3**　發佈失敗**不可以只寫 log**——寫 log 等於沒有人知。

⚠️ 職事表已經生成第 1 版，但公開連結沒有更新成功——

只講「發佈失敗」，幹事不知道嚴不嚴重。

### B 組：一個既有的不變量失敗，令 13 條情境跑不到

不變量是**整個季度的性質**，不是某一個情境的產物。舊寫法卻是：

```
情境跑完 → 跑快那批不變量 → 有一條紅 ⇒ 這個情境算紅
```

於是一條在開跑之前就已經紅的不變量，會令**之後每一個情境**都紅；
而每一個紅的情境又經 `dependsOn` 把下游標成 `BLOCKED`。

**一個根因　⇒　13 條情境一條都跑不到**，
而報告看起來好像有 13 個地方壞了。

**修正：歸咎。**

| 之前 | 之後 | 判斷 |
|---|---|---|
| 綠 | 紅 | 這個情境弄的 ⇒ **算它頭上** |
| 紅 | 紅 | 開跑之前就已經這樣 ⇒ **不算它頭上**，但在註記講一句 |
| 紅 | 綠 | 順手修好了 ⇒ 講一句 |

**B1**　新增 `snapshotFailingInvariants_()`——只影相，**不判斷責任**。

**B2**　開跑之前影一次底相。

⚠️ **這是全程唯一一次額外開支。**
每一個情境跑完本來就會影一次，而**上一個情境的事後相，
就是下一個情境的事前相**——所以逐個情境的歸咎一毫都不用多付。
第五十輪那個時間預算問題不可以走回頭路
（有一條突變 `inv-snap-twice` 守住這一點）。

**B3**　`caused.length > 0` 才把情境判紅。
⚠️ 這一條不可以連著一起放鬆——放鬆了就等於沒有了不變量。
一個情境**弄紅了**一條本來綠的，仍然算它頭上。

**B4**　報告開頭獨立一節：

```
⚠️ 開跑的時候已經存在的不變量失敗（1 條）
　 這幾條不是下面任何一個情境弄出來的，所以不算在它們頭上。
　 但它們是先決條件：不清乾淨，下面每一條的綠和紅都要打個折扣。
　 ⚠️ I09｜預期 v1｜實際 v0｜…
```

⚠️ 排在最頂，因為它是**先決條件**。

⚠️ 影不到底相 ⇒ **不可以當成「什麼都沒有紅」**。
當成沒紅的話，一條既有的失敗會被算在第一個情境頭上——
即是這一組要修的那件事。所以影不到就在報告講明「後面的歸咎可能不準」。

**測試**：`tests/selftest_invariant_attribution.test.js`（新）。
一樣**不驗字串**——真正叫落 `runSelfTestMachine_()`，
把 `runAllInvariants_()` 換成一個逐次回不同答案的 stub，
然後看**機器真正判出來的狀態**：X1 綠、X2 沒有被擋住、一個 `BLOCKED` 都沒有。

### C 組：亂行機叫完真實入口，沒有看回傳值

`MonkeyRun.gs` 的「生成初稿」叫 `apiGenerateDraftExecute()`，
然後把回傳值 `JSON.stringify` 落 `MonkeyLog` 就算數——**沒有人看**。

**它不拋錯**。所以亂行機會照樣行落去，行足 50 步，
然後交一份「沒有發現任何問題」的報告。

⚠️ **一個真實入口靜靜地沒做事，而測試照樣往下走**
——這正正是這個專案由第一輪殺到現在的那種病。

**C1**　動作清單加 `expect(result, before, after)`。

**C2**　主迴圈跑完 `run()` 之後再讀一次 facts，叫 `monkeyCheckOutcome_()`。
兩層：

1. **共通規則**——`legal()` 說做得到，而回傳 `ok: false` ⇒ 系統拒絕了。
   ⚠️ 這個跟「一個合法動作拋錯」同一級：都是「畫面說得，而系統說不得」。
2. **逐個動作的 `expect`**——狀態有沒有真的動過。

⚠️ 查證本身爆了要**報**。靜靜地當它過，就是這一組要修的那件事。

**C3　其餘八個動作逐個查過：**

| 動作 | 查什麼 |
|---|---|
| 生成初稿 | `versionCreated !== false`，而且版本號真的加了 |
| 改 grid 幾格 | `changedCells > 0`——一格都寫不到，這一步實際上什麼都沒做 |

### A1：S07 讀錯欄位

**修正前錯誤原文：**

```
label「系統看得到剛才那幾筆申報」
expected「≥ 3 筆」　actual「0 筆」
evidence「apiStep3Plan().results」
```

**成因**：`results` 是內部那個 `planApplyRequests_()` 的欄位。
`mapPendingPlanForClient_()`（`WebAppFlow.gs`）把它**拆成三個陣列**
才交出來：`applyList`／`confirmList`／`needsInputList`。

**修正後**——兩條，次序有意思：

1. `mode === 'HAS_PENDING'`。不是這個 mode 的話，那三個陣列
   **根本不會出現在回傳裡面**，下面驗多少都是在數一個 `undefined`。
2. `applyList.length >= want`。

**⚠️ 為什麼驗 `applyList` 而不是「三個陣列加起來」：**
S07 已經特意揀了套用得到的格（第五十五輪 B3），所以一筆跌落
`needsInput` 就是一個問題。驗總數的話那一筆照樣夠數，
問題要等到下面 `appliedCount` 才爆——那時候就分不出是
「寫錯格式」還是「套用邏輯壞了」。

證據行印齊三個數，並且逐筆列出 `needsInputList` 的原因。
