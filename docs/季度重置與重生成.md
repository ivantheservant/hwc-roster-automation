# 季度重置與重新生成

呢份文件講點樣把一個**曾經用嚟做測試**嘅季度清乾淨，然後用最新嘅演算法
重新生成一份乾淨嘅職事表。

寫俾唔熟悉程式嘅人睇——每一步都會講明「撳邊度」「應該見到咩」「點知做啱咗」。

---

## 一、咩情況先需要做

只有以下情況先需要：

- 呢個季度之前被用嚟試系統，累積咗一堆測試版本（v1、v2……v18）、
  測試申報、測試 PDF，而家想由頭嚟過。
- 演算法之後有更新，想用新版本重新排一次，唔想俾舊嘅測試版本混淆。

**唔需要做嘅情況**：

- 只係想改幾格 → 用「步驟 3：套用修改申報」，或者人手改 grid，唔使清晒。
- 想睇下另一種排法 → 用「查看 ▸ 試算不同 epsilon 的效果（唯讀）」，
  嗰個工具完全唔會寫入任何嘢。
- 上一季已經正式發出咗 → **唔好清**。清咗就再對唔返義工實際收到嘅係咩。

> ⚠️ 呢個動作除咗 PDF（會移去垃圾桶，30 日內可以復原）之外，**全部無法復原**。

---

## 二、開始之前

1. **確認你要清嘅係邊一季**。QuarterID 嘅格式係 `2026T4` 咁樣。
   清錯季度冇得返轉頭。
2. **如果嗰一季曾經真正寄過信俾義工**（`SendLog` 有 `Status=SENT` 嘅行），
   停一停諗清楚：清走之後，你就再查唔到當時邊個收過咩。
   建議先用「維護 ▸ 封存舊季度資料（唯讀預覽）」睇下，或者自己另存一份副本。
3. **記低而家嘅 Stage**。用「查看 ▸ 匯出關鍵狀態 → Diagnostics」睇得到。

---

## 三、完整步驟

### 步驟 1：睇清單（唯讀，唔會改任何嘢）

選單：**`維護 ▸ ⚠️⚠️ 重設季度測試資料`**

輸入 QuarterID 之後，會問你「連 v0 一齊清？」：

- **選「否」**（預設）：保留 v0。如果 v0 係當初生成、想留低做對照，就揀呢個。
- **選「是」**：連 v0 都清走，季度回到「完全冇生成過」嘅狀態。
  **想用最新演算法重新生成一份乾淨嘅 v0，就要揀呢個。**

之後會出一個**確認清單**，列明將會清咩：

```
將會清理：
　RosterVersions 登記列：18 個版本（v0、v1、……）
　對應的 grid 工作表：18 張
　RosterAssignments：3,942 行
　SendLog：762 行
　Requests：24 行
　Unavailable（只限 Source=REQUEST）：6 行
　FineTuneProposals（主表）：0 行
　FineTuneProposals_Archive（封存表）：37 行
　RosterPDF：213 個檔案（移到垃圾桶，30 日內可復原）
　Quarters.Stage：重設為 DRAFT
```

**第十四輪批次新增咗 `FineTuneProposals`／`FineTuneProposals_Archive` 兩行**
——步驟 3「套用修改申報」每次執行都會喺呢兩張表留低紀錄（`FineTuneProposals`
係暫存區、通常自然清空；`FineTuneProposals_Archive` 係歷史批次封存表，
之前完全冇被呢個工具檢查過，會不斷累積）。之前嘅版本冇處理呢兩張表，
如果你上一輪執行過「重設季度測試資料」，呢兩張表可能仲有 2026T4 嘅殘留，
下次執行就會一併清走。

**呢一步淨係睇，未清任何嘢。** 唔啱就直接取消。

### 步驟 2：睇「唔會自動清」嗰幾段（最重要）

同一個視窗再落啲，會有兩段特別要留意——呢兩類系統**故意唔幫你清**，
因為程式分辨唔到邊啲係測試資料、邊啲係真嘢：

#### 2a. 落喺呢一季、但唔係申報自動加入嘅 `Unavailable`

```
⚠ 落在這一季、但不是由申報自動加入的 Unavailable（不會清，請自己看一次）：
　P017　2026-11-08 → 2026-11-08　Source=（空白）
　P042　2026-12-20 → 2026-12-27　Source=MANUAL　AppliesTo=ALL
```

- **Source=REQUEST** 嗰啲係系統由「不能服侍」申報自動寫入嘅 → 會自動清走。
- **Source 係空白或者其他值**嗰啲係**人手打入去**嘅 → **唔會清**。

點解要自己睇：測試期間你可能自己打過幾行入去試，嗰啲同真實請假**外表一模一樣**，
程式冇辦法分。如果唔清，重新生成時系統會繼續避開嗰啲人嗰幾日。

**要清就自己去 `Unavailable` 工作表，用上面列出嘅 PersonID 同日期搵返嗰行，
整行刪除。** 唔肯定就留低——留低最多係排表避開咗一個其實得閒嘅人，
刪錯就變成派咗一個真係唔得閒嘅人。

#### 2b. 由「指定服侍」申報自動加入嘅 `Eligibility`

```
⚠ Eligibility 中由「指定服侍」申報自動加入的行（不會清，會影響重新生成）：
　P031　崗位 AUDIO　Active=TRUE　加入於 2026-09-14 10:22:03
```

呢個係**最容易被忽略**嗰一項。

背景：步驟 3 套用「指定服侍」申報嗰陣，如果你指定嘅人**未曾做過嗰個崗位**，
系統會喺 `Eligibility` 新增一行，令佢由此變成合資格。呢行嘅 `Source` 係
`REQUEST`、`HistoricalCount` 係 0。

問題係：**`Eligibility` 唔屬於任何季度**，所以「重設季度」永遠碰唔到佢。
清完之後重新生成，嗰個人**仍然**對嗰個崗位算合資格，會繼續被排到。

點做：

- 如果嗰行係測試時亂試出嚟嘅 → 去 `Eligibility` 把嗰行 `Active` 改做 `FALSE`
  （或者整行刪咗）。
- 如果嗰個人真係學識咗做嗰個崗位 → **保留**，呢個係真實嘅資格變更。

#### 2c. 曾經發佈過嘅公開職事表（第十二輪批次新增，**系統會自動處理，唔使你自己執行**）

如果呢一季之前曾經用「準備工作 ▸ 發佈公開職事表」發佈過（見
[`幹事操作說明.md`](幹事操作說明.md)「新選單項目：⚠️ 發佈公開職事表」），
確認清單會多一段提示：

```
⚠ 這一季曾經發佈過公開職事表（https://docs.google.com/spreadsheets/d/...）：
　連結本身不會改變、檔案不會刪除，但內容會清空並顯示「已重設」提示，
　等下次重新執行「發佈公開職事表」時自然覆寫回正確內容。
```

**呢一項唔需要你做任何事**——同 2a／2b 唔同，公開連結呢部分係系統自動
處理，你打字確認之後會連同其他資料一齊完成，結果畫面會有一行「公開職事表：
已清空內容並顯示「已重設」提示（連結不變）」。

為什麼唔刪除檔案／連結：如果連結變咗，之前如果已經派過俾人試睇，義工再打開
就會 404。所以做法係保留同一條連結、但清空內容，避免義工睇到「已經被重設
但外表仲好似有效」嘅舊資料——等你重新發佈嗰陣自然覆寫返最新內容。

**個人專屬連結 token 完全唔受重設影響**——token 存喺 `NameMapping` 工作表
（跟人綁定，唔跟季度），`NameMapping` 本身喺「重設季度測試資料」嘅
「絕對不碰」名單之內，重設任何季度都唔會改到任何人嘅 token。

### 步驟 3：打字確認

睇完清單、處理完上面兩段之後，系統會要求你**逐字輸入**：

```
確認重設
```

撳 Yes／揀個掣係唔夠嘅——一定要打呢四個字。打錯就當取消。

### 步驟 4：等佢做完，睇結果

做完會出一個結果視窗，逐項報實際清咗幾多：

```
已清理：
　RosterVersions：18 行
　grid 工作表：18 張
　RosterAssignments：3,942 行
　SendLog：762 行
　Requests：24 行
　Unavailable：6 行
　FineTuneProposals（主表）：0 行
　FineTuneProposals_Archive（封存表）：37 行
　PDF：213 個（已移到垃圾桶）
　Stage：已重設為 DRAFT
```

數字應該同步驟 1 嘅清單對得上。差好遠就記低，同 Claude 講。

### 步驟 5：確認真係清乾淨

**唔好淨係信嗰個結果視窗**，自己核一次：

1. 執行 **`查看 ▸ 匯出關鍵狀態 → Diagnostics`**，打開 `Diagnostics` 工作表，睇：
   - `Quarters` 嗰一區：嗰一季嘅 `Stage` 應該係 `DRAFT`，
     「最新版本」應該係「（尚未生成）」（如果連 v0 都清咗）。
   - `SendLog` 嗰一區：唔應該再見到嗰一季嘅批次。
   - `RosterPDF` 嗰一區：唔應該再見到嗰一季嘅檔案。
2. 打開試算表底部嘅工作表清單，確認 `Roster_2026T4_v*` 嗰啲工作表已經冇咗。
3. 如果你有處理步驟 2 嗰兩段，順手再開 `Unavailable` 同 `Eligibility` 望一眼。

### 步驟 6：重新生成

清乾淨之後：

**`四階段流程 ▸ ⚠️ 步驟 1：生成初稿`**

輸入同一個 QuarterID。做完會出一個完成畫面，重點睇：

- **「⚠ 系統應該排但排不出」有幾多格**——理想係 **0**。
  唔係 0 嘅話，嗰幾格會喺表上用**粉紅底 + 「⚠ 未能安排」**標示出嚟，
  要人手處理（搵人頂替，或者接受嗰格留空）。
- **「待人手填寫」有幾多格**——呢個唔係問題。講員、翻譯、獻花三個崗位
  系統設計上就唔會自動排，13 週 × 3 個崗位 ＝ 39 格，屬正常。

生成完，Stage 會係 `DRAFT`。**如果你只係想印出嚟俾堂委睇，到呢一步就夠，
唔好再撳步驟 2。** 撳咗步驟 2 就會寄信。

### 步驟 7（選做）：印出嚟俾堂委睇

1. **`準備工作 ▸ 填寫講員／翻譯／獻花`**——把講員、翻譯、獻花填上去，
   表就唔會有一整欄空白（獻花冧一週冇人認獻可以留空，唔使勉強填）。
2. **`準備工作 ▸ 匯出 PDF`**——匯出完整版。
3. PDF 底部會有**圖例**，逐項解釋每個標示係咩意思，仲會寫住本季實際幾多格，
   例如「⚠ 未能安排：0 格」——呢個數字本身就係最好嘅說明。
4. 想同時俾堂委睇「排得好唔好」嘅數據，用
   **`查看 ▸ 草稿覆核報告（唯讀）`**，出嚟嗰份係寫俾唔熟系統嘅人睇嘅，
   可以直接複製貼上電郵。

## 四、常見問題

### 清完之後，之前嘅測試會唔會影響新排出嚟嘅表？

逐項確認過（呢啲結論有測試鎖住，見 `tests/quarter_reset_plan.test.js`／
`tests/quarter_reset_public_link.test.js`）：

| 殘留 | 會唔會影響重新生成 | 點解 |
|---|---|---|
| `SendLog` 舊紀錄 | **唔會** | 排表演算法完全唔讀 `SendLog` |
| 其他季度嘅舊版本 | **輕微會** | 生成時會讀季初之前幾週嘅安排，用嚟避免跨季連續兩週。呢個係**刻意**嘅設計，唔係污染 |
| 軟規則歷史基準 | **唔會** | 基準係寫死嘅常數（來自 2025T1–2026T3 嘅真實紀錄），唔係即時由 `RosterAssignments` 計，所以測試版本點都影響唔到 |
| `Eligibility` 由申報加入嘅行 | **會** | 見上面 2b。呢個係唯一真正要人手處理嘅殘留 |
| `Requests` 舊申報 | **唔會**（已清走） | 而且步驟 1 生成初稿本來就唔讀 `Requests` |
| 曾經發佈過嘅公開職事表 | **唔會**（系統自動清空內容） | 見上面 2c。連結／檔案保留，內容自動清空並顯示「已重設」提示，唔需要你自己處理 |
| 個人專屬連結 token | **完全唔受影響** | token 存喺 `NameMapping`（跟人唔跟季度），喺「絕對不碰」名單之內 |

### 清錯咗季度點算？

冇得復原，除咗 PDF（喺 Drive 垃圾桶，30 日內可以還原）。

但 `AuditLog` 有記低清之前嘅完整摘要（版本清單、各表行數、原本嘅 Stage），
搵返嗰一行至少知道原本有咩。之後只可以重新生成，
以前嘅人手改動同申報結果就冇咗。

**所以步驟 1 嗰個清單一定要逐行睇清楚先確認。**

### 「連 v0 一齊清」到底揀邊個？

- **想用最新演算法重新生成一份乾淨嘅 v0** → 揀「是」。
- **想保留當初生成嗰版做對照，只清後來嘅測試版本** → 揀「否」。

揀「否」嘅話，重新生成會由 v19 開始（接住舊嘅版本號），
唔會覆蓋 v0。

### 有版本清唔到

清單會講明原因：

- **`Protected=TRUE`**：去 `RosterVersions` 把嗰行嘅 `Protected` 改做 `FALSE`，
  再執行一次。
- **v0 而你揀咗「否」**：重新執行並揀「是」。
