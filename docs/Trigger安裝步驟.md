# Trigger（自動排程）安裝步驟

`dailyAutomationCheck_()` 呢個函式**從未真正被自動觸發過**——一直以嚟
只透過選單「⚠️⚠️ 立即執行自動排程檢查」人手觸發嚟測試。真正安裝
time-based trigger（每日自動執行一次）之後，運作環境同人手執行有幾個
關鍵分別，呢份文件幫你安裝前確認清楚、安裝之後頭幾日點觀察。

---

## 一、自動排程實際上做緊咩（複習）

每日檢查只做兩件事，**淨係通知幹事你自己**，唔會寄畀堂委或義工：

1. **GENERATE**：季度到達生成日期、Stage 仍係 `DRAFT`、仲未有任何版本
   時，自動生成一份初稿。
2. **REMIND**：季度停留在某個 Stage 太耐、或者就快到正式發出日期，
   提醒你去跟進。

**「步驟 4：正式發出」永遠唔會由呢度觸發**——呢個係結構性防護
（`assertOfficialNotFromAutomationTrigger_()`），唔止係「呢度冇寫」，
而係主動攔截，即使日後唔小心加咗一行呼叫都會被擋低。

---

## 二、安裝之前要確認嘅事

1. **`DRY_RUN=TRUE`**——安裝之後起碼觀察一至兩星期先至考慮轉
   `FALSE`。安裝呢一步本身唔會令 `DRY_RUN` 生效唔生效有分別，但你想
   有多啲信心先啟用「真正寄信」嘅話，建議兩件事分開驗證。
2. **`MAIL_ADMIN_NOTIFY`**（Config）要填咗你自己嘅電郵——呢個係
   GENERATE／REMIND 通知寄去邊度嘅唯一設定，留空嘅話通知只會寫入
   Logger，冇人會真正收到，你就完全唔知道自動排程做過啲咩。
3. **執行一次「⚠️⚠️ 自動排程 ▸ 檢查自動排程條件（唯讀）」**——呢個
   工具會話你知「如果今日執行檢查，每一季會發生咩事」，同真正安裝
   trigger 之後嘅行為保證一字不差（兩者共用同一份判斷邏輯）。逐季
   睇一次，確認冇任何一季會喺你意料之外觸發生成或者提醒。
4. **檢查每一季嘅 `StartDate` 係咪真正嘅日期值**——本輪稽核發現：如果
   `StartDate` 係一段完全冇辦法辨識做日期嘅自由文字（例如手快打咗
   「TBD」「待定」呢類字，唔係下拉選單／日期格式揀出嚟嗰種），會令
   計算生成日期嗰一步出錯。**本輪已經修正**：呢種情況而家只會令
   *嗰一季*嘅檢查失敗（記入 AuditLog，`Action=AUTOMATION_QUARTER_JUDGE_ERROR`），
   唔會累到其他季度嘅檢查一齊停擺——但安裝之前，都建議你順手檢查一次
   全部季度嘅 `StartDate` 係咪都係正常日期，減少呢種情況出現嘅機會。
5. **`REMIND_STUCK_DAYS`／`REMIND_DEADLINE_DAYS`／`REMIND_STUCK_MAX_COUNT`
   （Config）用返你想要嘅門檻值**——呢幾個控制幾多日算「停滯」、幾多日
   算「就快到期」、最多提醒幾多次，見 `docs/幹事操作說明.md` 第五節
   「提醒信（REMIND）幾時會寄？」。

---

## 三、安裝步驟

選單 `職事表系統 ▸ ⚠️⚠️ 自動排程 ▸ ⚠️⚠️ 安裝自動排程`，跟指示打字
輸入「確認安裝」。系統會自動先移除舊嘅同名 trigger 先至裝新嘅，唔會
出現重複安裝令一日執行兩次嘅情況。

安裝完成後，可以用「查看自動排程狀態（唯讀）」確認已安裝 1 個 trigger。

---

## 四、安裝之後頭幾日點觀察

1. **每日檢查一次 `AuditLog`**：篩選 `Action` 欄，留意呢幾種值：
   - `TRIGGER_GENERATE`／`TRIGGER_REMIND`——正常執行成功。
   - `TRIGGER_GENERATE_ERROR`／`TRIGGER_REMIND_ERROR`——某一季嘅動作
     本身執行失敗（唔係判斷階段，係真正執行嗰步，例如生成初稿時
     Sheets API 暫時性錯誤），`Notes` 欄會有原始錯誤訊息。下一日
     系統會自動重試，唔需要你人手介入，除非連續好多日都係同一個
     錯誤先要跟進。
   - `AUTOMATION_QUARTER_JUDGE_ERROR`（本輪新增）——某一季連「判斷
     今日要唔要做」都做唔到（通常係資料問題，例如上面提到嘅
     `StartDate` 格式問題），`Notes` 欄有原因。呢個唔會影響其他季度，
     但代表嗰一季嘅資料需要你人手檢查修正。
2. **檢查你嘅電郵**：GENERATE／REMIND 觸發時應該收到通知信
   （`MAIL_ADMIN_NOTIFY` 呢個信箱），確認內容同 `AuditLog` 記錄相符。
3. **執行「🩺 全面體檢（唯讀）」**：留意「自動排程狀態」呢一項，確認
   顯示嘅 trigger 數量同你安裝嗰個相符（應該係 1 個，唔係 0 個或者
   多個）。

---

## 五、已知限制（唔算 bug，但值得留意）

**自動觸發嘅動作，操作者欄可能會顯示空白**：`RosterAssignments` 的
`UpdatedBy`、`RosterVersions` 的 `CreatedBy`、`AuditLog` 的 `Actor`
呢幾欄，一律用 `Session.getActiveUser().getEmail()` 讀取。人手喺選單
或者 Web UI 操作時，呢個一定讀到你自己嘅電郵；但 Apps Script 官方文件
提到，喺某啲情況下（尤其係 time-based trigger 呢類冇人直接互動嘅執行
環境），基於私隱理由呢個 API 可能讀唔到身分、回傳空字串。

**呢個唔會影響任何功能**——生成初稿、寫入 RosterAssignments、記錄
AuditLog 全部照常運作，唔會因為呢個空白而報錯。**唯一嘅影響係稽核
追蹤嘅可讀性**：自動排程生成嘅版本，`CreatedBy` 呢一欄可能會係空白，
而唔係顯示話「呢個係自動排程做嘅」。

呢個係本輪稽核發現、但因為冇辦法喺呢一輪安裝真正 trigger 嚟驗證
（指示禁止安裝 trigger），所以列為**待你安裝之後觀察嘅未知數**，
唔係已經確認嘅 bug：安裝之後留意下自動生成嗰版本嘅 `CreatedBy` 欄係
咪真係空白。如果係，而你介意呢一點，可以話俾 Claude 知，改用
`Session.getEffectiveUser()`（理論上對 installable trigger 更可靠，
但呢一輪未有機會實測驗證，唔想喺未驗證嘅情況下改動咁多處程式碼）。

---

## 六、發現異常即時停止

選單 `職事表系統 ▸ ⚠️⚠️ 自動排程 ▸ ⚠️⚠️ 移除自動排程`——即時生效，
唔需要打字確認（安裝先需要，移除本身風險低，唔會發生任何動作）。
移除之後，你隨時可以再重新安裝一次，唔會影響已經執行過嘅紀錄。

如果懷疑係 `DRY_RUN` 忽然變成 `FALSE` 導致真正寄咗信，處理方式同
`docs/WebUI實測步驟.md` 第五節一致：先去 Config 確認／改返
`DRY_RUN=TRUE`，然後打開 `SendLog` 核對實際寄出咗啲咩。
