## 一、共通規則（全頁適用）

### 1.1 頁面骨架

```
┌─────────────────────────────────────────────┐
│ 粵語堂職事表                                  │
│ 季度：[2026年10-12月 ▾]   狀態：初稿已生成…    │  ← 唯一的季度下拉
│                          [測試模式] [🌙]      │
├─────────────────────────────────────────────┤
│ 這一季現在的情況                              │  ← 狀態卡（一句人話）
├─────────────────────────────────────────────┤
│ 區二　開季前準備            （還有 3 項未做）  │  ← 未做完 >0 時展開，=0 時收摺
├─────────────────────────────────────────────┤
│ 區一　日常四個掣                              │  ← 永遠展開，永遠在最當眼
├─────────────────────────────────────────────┤
│ 區三　名單維護                     （收摺）    │
├─────────────────────────────────────────────┤
│ 區四　進階功能                     （收摺）    │
└─────────────────────────────────────────────┘
```

- 季度下拉只有一個，在最頂。全頁所有動作都作用於它。**任何彈窗都不再問一次季度。**
- 季度下拉的文字寫人話：`2026年10-12月`，後面括號補 `（10月4日開始）`。不寫 `2026T4`。
- 換季度＝整頁重新載入狀態，任何已打開的確認畫面立即關閉。

### 1.2 狀態卡文字（取代 `Stage`）

| 內部 Stage | 有無版本 | 狀態卡顯示 |
|---|---|---|
| `DRAFT` | 無 | 還未生成初稿。系統會在 **11月27日** 自動生成，也可以在「進階功能」手動生成。 |
| `DRAFT` | 有 | 初稿已生成，未寄給堂委。 |
| `REVIEW_SENT` | 有 | 已寄給堂委，等他們的意見。 |
| `REQUESTS_APPLIED` | 有 | 堂委意見已處理，未正式發出給全體。 |
| `OFFICIAL_SENT` | 有 | 已正式發出給全體。 |

狀態卡第二行（細字，排第二位）：`目前第 3 版　12月4日 11:20　套用堂委意見後`

測試模式徽章：`DRY_RUN=TRUE` 時顯示紅色 `測試模式：不會真的寄出任何電郵`。

### 1.3 術語對照（畫面上一律用右欄）

| 不可出現 | 改寫成 |
|---|---|
| Stage / 階段 | 「這一季現在的情況」 |
| RosterAssignments / grid | 「職事表」／「表上」 |
| Version / v2 | 「第 2 版」（永遠連同日期與一句描述） |
| DRY_RUN | 「測試模式」 |
| Requests | 「修改申報」 |
| SendLog | 「寄出記錄」 |
| Eligibility | 「崗位資格」 |
| PersonPostExclusions | 「暫時不做某崗位」 |
| Unavailable | 「不能服侍的日期」 |
| Roles / COMMITTEE / DEACON | 「身分」／「堂委」／「執事」 |
| SpecialSundays | 「特別主日」 |
| hard rule / HARD_ELIGIBILITY | 「一定要遵守的規則」＋人話理由 |
| materialise | 「儲存成新一版」 |

### 1.4 確認畫面規範

1. **一個動作只有一個確認畫面。** 所有輸入在動作開始前已在畫面上填好。
2. 確認畫面必須有數字：會寄幾多封、會改幾多格、會建立第幾版。
3. **只有不可逆動作要打字確認**：正式發出給全體（掣 3）、改動後重發（掣 4）、放行硬規則違反。其餘一律「確定／取消」兩粒掣。
4. 打字確認的字串一律是 **`確認`** 兩個字，不用英文、不用長句。
5. 確認畫面永遠有「取消」，取消＝零改動、零寄出。

### 1.5 錯誤訊息規範

每一個失敗訊息必須有三段，缺一不可：

```
發生了什麼：找不到「陳大汶」這個名字。
現在的情況：職事表沒有任何改動，第 2 版仍然是最新一版。
你可以怎樣做：
  ・如果打錯字，把那一格改回「陳大文」
  ・如果是同一個人的別寫，去「名單維護 ▸ 人員與電郵」加別名
  ・如果是新人，去「名單維護 ▸ 人員與電郵」新增
```

**不可以只寫技術原因。** 不可出現 exception message 原文（原文寫入 `AuditLog`，畫面只給人話 + 一個「複製技術詳情」細掣）。

### 1.6 不可撳的掣

不可撳時 **講「怎樣才撳得到」，不講「為何失敗」**。掣本身變灰、可 hover、下方一行灰字寫條件。

反例：`目前鎖定——現在 Stage 是 DRAFT`
正例：`要先撳「寄給堂委審閱」，收齊意見之後再撳「儲存並確認」，這一粒才會著。`

### 1.7 一條總原則

> **掣 1 是唯一會改動職事表內容的掣。掣 2／3／4 只寄信，永不改內容。**

所以掣 2／3／4 執行前一律先檢查「有沒有未儲存的改動」，有就拒絕並指去掣 1（D5）。

## 二、區一：日常四個掣

### 2.1 自動：生成初稿（沒有掣）

不是掣，只是狀態卡的一句話。條件與行為完全沿用 `Trigger.gs` 現有邏輯，本規格不改。

- 顯示：`系統會在 11月27日 自動生成初稿，生成之後會 email 通知你。`
- 已生成：`初稿已在 11月27日 09:00 自動生成。`
- 手動重跑入口在區四，不在這裡（避免幹事在錯的時機插入新版本）。

### 2.2 四個掣的狀態機

| 掣 | 可撳的條件 | 執行後 Stage |
|---|---|---|
| 1 儲存並確認 | 已有至少一個版本（任何 Stage 都可撳） | `DRAFT`→`DRAFT`；`REVIEW_SENT`→`REQUESTS_APPLIED`；其餘不變 |
| 2 寄給堂委審閱 | 已有版本 **且** Stage ≠ `OFFICIAL_SENT` **且** 沒有未儲存改動 | 一律設為 `REVIEW_SENT` |
| 3 正式發出給全體 | Stage = `REQUESTS_APPLIED` **且** 沒有未儲存改動 **且** 這一季從未正式發出過 | `OFFICIAL_SENT` |
| 4 改動後重發 | Stage = `OFFICIAL_SENT` **且** 沒有未儲存改動 **且** 上次發出之後有人的安排改過 | 不變 |

「未儲存改動」的定義（三者任一成立）：
1. 最新版本的 grid 工作表上有系統認得出的人手改動（`resolveAuthoritativeState_(..., GRID_OVERLAY)` 的 `changes.length > 0`）
2. grid 上有系統認不出的文字（`unresolved.length > 0`）
3. `Requests` 工作表有待處理申報（`readPendingRequests_()` 非空）

### 2.3 每個掣旁邊那句動態文字

每次開頁、每次動作完成之後重新計算一次（一個新 API `apiGetDashboardState(quarterId)` 一次過回傳，不要逐粒掣各自打一次後端）。

#### 掣 1

| 情況 | 文字 |
|---|---|
| 零改動、零申報 | `未偵測到你在表上改過任何格。` |
| 有 grid 改動 | `偵測到你在表上改了 4 格。` |
| 有申報 | `有 3 筆修改申報未處理。` |
| 兩者都有 | `偵測到你在表上改了 4 格，另有 3 筆修改申報未處理。` |
| 有認不出的文字 | `有 2 格的文字系統認不出，撳下去會告訴你是哪幾格。` |
| Stage=`REVIEW_SENT` 且零改動 | `堂委沒有提出改動。撳下去就當作意見已收齊，可以進入正式發出。` |

#### 掣 2

| 情況 | 文字 |
|---|---|
| 可撳 | `把唯讀連結寄給 3 位收件人。` |
| 收件人為 0 | `現時沒有登記任何堂委電郵，寄出去不會有人收到。先去「名單維護」補。` |
| 已寄過 | `上次在 11月28日 14:30 寄過。再撳一次會重新寄給同一批人。` |

### 2.4 掣 1「儲存並確認」——完整內部流程

九步。每一步都可能中止，中止時**必須說清楚職事表現在處於什麼狀態**。

#### 步 1.1　取現況

讀最新版本 N、建立 context（`buildFineTuneContext_`）。

- **失敗：沒有任何版本** → 掣本身已變灰，不會走到這裡。
- **失敗：grid 工作表被刪或改名** → 訊息：
  `找不到「第 2 版」的工作表。職事表資料本身仍然完整（在 RosterAssignments 內），但你看的那張表不見了。可以去「進階功能 ▸ 回到上一個版本」重新建立一張。`

#### 步 1.2　認名

`unresolved.length > 0` → **立即中止，不進入之後任何步驟。**

畫面列出：日期、崗位、你輸入的文字。每一行給三個出路（1.5 節的三段式）。
**不提供「略過這幾格繼續」。** 認不出就是認不出，猜是第十九輪那一類 bug 的溫床。

#### 步 1.3　讀待處理申報

`readPendingRequests_()`（用 `RequestID` 空白判斷，不看 Status）。分三類：

| 類別 | 處理 |
|---|---|
| `APPLY` | 直接列出，會自動套用 |
| `CONFIRM` | 逐筆要幹事勾選才套用（例如要順手加崗位資格） |
| `NEEDS_INPUT` | **不阻擋**。列出並寫明：`這 2 筆系統看不懂，會原封不動留在申報表，你可以之後自己處理。` |

#### 步 1.4　合併，grid 優先

同一格既有 grid 人手改動、又有申報 → **grid 贏**。

確認畫面必須有獨立一節：
`以下 2 格你在表上改過，同時亦有修改申報。系統會以你表上的為準：`
（逐格列：日期／崗位／申報想改成／你表上是）

#### 步 1.5　規則檢查

用 `STATE_SOURCE.GRID_OVERLAY` 跑 `findStateViolations_()`，套第二十一輪的三分類：

| 類別 | 行為 |
|---|---|
| 第 1 類：真違反 | **阻擋**。要打字 `確認` 放行 |
| 第 2 類：規則後加、舊資料追溯不合 | 顯示，不阻擋 |
| 第 3 類：結構性不適用 | 顯示，不阻擋 |
| 準硬規則（連續兩週） | 顯示警告，不阻擋 |

放行畫面文案：
```
以下 1 格違反了一定要遵守的規則：
　11月8日　報告　陳大文
　原因：報告只可以由現任堂委擔任，陳大文目前不在堂委名單。

如果這是正確的（例如名單還未更新），請在下面輸入「確認」放行。
放行之後這一格會照樣儲存，並記入 AuditLog。
[            ]  [放行並繼續]  [取消]
```

#### 步 1.6　三欄對照，逐格接受／拒絕

只有「有違反 **且** 系統找到替代人選」的格才出現建議欄。沿用 `proposeMinimalFix()` ＋ `apiDetectChanges()` 已有的 `original／manual／suggested`。

畫面（每格一行，預設全部選「用我改的」）：

| 日期 | 崗位 | 原本 | 你改成 | 系統建議 | 選擇 |
|---|---|---|---|---|---|
| 11月8日 | 報告 | 李美華 | 陳大文 | 張淑儀 | ⦿用我改的　○用系統建議　○改回原本 |

- **預設一定是「用我改的」。** 幹事的決定是最新真相。
- 「改回原本」在原本是空白時要禁用（`applyDecisions()` 已有這道保護，前端要同步變灰並寫 `原本這一格是空白，不能改回`）。
- 全部格頂部一粒「全部用我改的」快捷。

#### 步 1.7　確認畫面

一頁過，包含：

```
儲存成第 3 版

會做的事：
　・套用你在表上改的 4 格
　・套用 3 筆修改申報（其中 1 筆是你剛才勾選確認的）
　・2 筆申報系統看不懂，會留在申報表不動
　・放行 1 項規則違反（你剛才輸入了確認）
　・儲存成第 3 版。第 2 版原封不動保留，可以對照
　・重新發佈公開連結（連結地址不變）

不會做的事：
　・不會寄出任何電郵
　・不會產生任何 PDF

[確定儲存]  [取消]
```

#### 步 1.8　寫入

次序固定：`AuditLog` 逐格 → `createRosterSheet()` → `writeAssignments()` → `registerVersion()`。

- **失敗：中途出錯（版本已建、派工未齊）** → 這是最危險的一種。訊息必須寫：
  `儲存到一半失敗了。第 3 版可能只寫入了一部分。請去「進階功能 ▸ 檢查各版本派工紀錄」核對，或用「回到上一個版本」退回第 2 版。原因：<人話>`
  並且 **不要前進 Stage、不要發佈公開連結**。

#### 步 1.9　重新發佈公開連結

`publishPublicRoster_(quarterId)`。

- **失敗** → 版本已經寫好，這一步失敗不是全盤失敗。訊息必須分開講：
  `第 3 版已經儲存好了。但公開連結未能更新（原因：<人話>）。堂委現在開連結會看到舊內容。請去「進階功能 ▸ 重新發佈公開連結」再試一次。`

#### 零改動路徑（D4）

| Stage | 行為 |
|---|---|
| `DRAFT` | 不建版本、不動 Stage、不發佈。訊息：`沒有偵測到任何改動，不需要儲存。` |
| `REVIEW_SENT` | 不建版本，**Stage 前進到 `REQUESTS_APPLIED`**，重新發佈公開連結。確認畫面：`堂委沒有提出改動。撳下去就當作意見已收齊，「正式發出給全體」會亮起。職事表內容不會改變。` |
| `REQUESTS_APPLIED` | 同 `DRAFT`，只是文字加一句 `可以撳「正式發出給全體」了。` |
| `OFFICIAL_SENT` | 同 `DRAFT`，文字加 `這一季已經正式發出過了。` |

### 2.5 掣 2「寄給堂委審閱」

- 前置：D5 未儲存改動檢查 → 有就拒絕，訊息 `你在表上改了 4 格未儲存。先撳「儲存並確認」，堂委才會看到最新內容。`
- 確認畫面：收件人數、逐個顯示名 + 電郵、公開連結地址、版本描述、`測試模式：不會真的寄出`（如適用）。
- 收件人 0 → 拒絕執行（不是警告）。訊息指去「名單維護 ▸ 收件人」。
- 已寄過 → 確認畫面加一行 `上次在 11月28日 14:30 寄過，會再寄一次給同一批人。`
- 不需要打字確認（可重複、可逆、對象只有堂委）。
- 執行後 Stage 設 `REVIEW_SENT`（D2）。**不可以由 `OFFICIAL_SENT` 退回**（掣在該 Stage 已變灰）。
- 執行後同時檢查區二未做完項目，若 > 0，完成畫面加一句：
  `提提你：開季前準備還有 3 項未做（講員未填 2 週、獻花未填 5 週、有 1 個合堂日期未確認）。堂委看到的表會有空格。`

### 2.6 掣 3「正式發出給全體」

三層防重複：

| 層 | 檢查 | 不通過的行為 |
|---|---|---|
| 1 | Stage 必須 = `REQUESTS_APPLIED` | 掣變灰 |
| 2 | `SendLog` 內這個季度**不可有任何 `OFFICIAL` 紀錄**（不論版本、不論 `DRY_RUN`） | 掣變灰，文字：`已在 12月4日 11:20 正式發出過。之後有改動請用「改動後重發」。` |
| 3 | D5 未儲存改動檢查 | 拒絕，指去掣 1 |

另加兩項**只警告不阻擋**：

- `alreadySentCount > 0`（同版本同階段已有寄出記錄，代表上次寄到一半中斷）→ 確認畫面顯眼一段：
  `注意：這個版本已經有 12 個人收過信，很可能是上次寄到一半中斷了。如果只想補寄未收到的人，請取消，改用「進階功能 ▸ 補寄未收到的人」。`
- 個人 PDF 缺件（`apiStep4GetMissingPdfWarnings`）→ 保留現有阻擋行為（`step4_missing_pdf_gate` 已有測試覆蓋）。

確認畫面內容：

```
正式發出給全體　（不可逆）

會寄給表上 57 個人中的 50 人
　・每人一封信，附自己那份標示了名字的 PDF
　・附月曆檔（.ics），紐西蘭時間，已計夏令時間
　・附個人專屬連結（永遠顯示最新安排）
　・7 人沒有電郵，會略過（名單：…）

同時寄給堂委 3 人。

寄出之後這一季就定稿了。之後有改動只能用「改動後重發」，
只會寄給有改動的人。

請輸入「確認」： [        ]
[確定發出]  [取消]
```

### 2.7 掣 4「改動後重發」

- 前置：Stage = `OFFICIAL_SENT`、D5 未儲存改動檢查。
- 內容閘：比對「最新版本每人的派工摘要」與「上次 `OFFICIAL`／`RESEND` 寄給該人時記錄的 `AssignmentHash`」。0 人有改動 → 掣變灰，文字 `自上次發出之後沒有人的安排改過，不需要重發。`
- 確認畫面列出**逐個有改動的人**：名、改了哪幾格、原本／現在。這是幹事唯一一次可以人眼看出「係咪真係想改咁多人」的關口，不可以只寫數字。
- PDF：只重新產生這 N 個人的 PDF（不是全部 57 份）。若技術上做不到只產生部分，確認畫面要寫明 `會重新產生全部 57 份 PDF（約需 X 分鐘），但只寄給這 6 個人。`
- 打字 `確認` 才執行。
- 堂委一律連同收到（他們需要知道最終版）。

## 三、區二：開季前準備

本季一次性。標題右邊常駐 `（還有 N 項未做）`，N = 0 時整區收摺並顯示 `全部做好了`。

### 3.1 「未做完 N 項」怎樣算

N = 以下五項之中，`count > 0` 的**項數**（不是格數）。每項各自顯示自己的數字。

| # | 項目 | count 的定義 | 阻不阻擋掣 2 |
|---|---|---|---|
| 1 | 特別主日日期未確認 | `SpecialSundays` 中本季 `Active=TRUE` 且 `isUnconfirmedSpecialSunday_()` 為真的行數（**空白＝已確認**，只有明確 `FALSE` 才算未確認） | 否，只在掣 2 完成畫面提醒 |
| 2 | 合堂未指定跳過崗位 | 本季 `Type` 為合堂類、`SkipPostIDs` 空白的行數 | 否 |
| 3 | 講員未填 | 本季主日之中，講員崗位仍為空白的週數 | 否 |
| 4 | 翻譯未填 | 本季主日之中 `TranslationRequired=TRUE` 而翻譯仍空白的週數 | 否 |
| 5 | 獻花未填 | 本季主日之中獻花仍空白的週數 | 否 |

名單檢查**不計入 N**（它跟人不跟季），改為一個獨立提示條，見 3.4。

### 3.2 畫面一：確認特別主日

一張表，一行一個特別主日：

| 日期 | 類型 | 名稱 | 這一週哪些崗位不用排 | 日期已確認 |
|---|---|---|---|---|
| 2027-03-28 | 浸禮 | 復活節／浸禮 | ☐領詩 ☐司琴 ☐… | ☐ |

- 「哪些崗位不用排」用 checkbox 陣列，不是叫幹事打 `WORSHIP,PIANO`。寫入時轉成 `SkipPostIDs`。
- 「日期已確認」是 checkbox。**未勾 = 寫入 `FALSE`；勾了 = 寫入空白**（配合 `isUnconfirmedSpecialSunday_()` 的方向，不可以反）。
- 可以改日期（`ServiceDate`），改完要即時警告如果新日期不在本季 `ServiceDates` 之內。
- 「新增一個特別主日」掣：日期、類型（下拉：合堂／浸禮／宣教月／堂慶／其他）、名稱、跳過崗位。
- **不提供刪除**，只提供 `Active` 開關（`Active=FALSE` 的行灰底顯示在最底，可以重新開啟）。

年度性動作放在這一頁底部（一年撳一次）：
- `產生下一年度四個季度`
- `產生年度合堂建議`
兩者都是先預覽、確認才寫入，沿用現有 `AnnualQuarters.gs`／`AnnualCombined.gs`。

### 3.3 畫面二：填講員／翻譯／獻花

把現有 `PreacherFillSidebar.html` 原樣搬上 Web，接現有 `apiListPreacherTranslationPending()` / `apiSavePreacherTranslationEntry()`。

- 一行一週：日期、講員、翻譯、獻花，各自一個輸入格＋歷史建議下拉。
- 翻譯欄只在該週 `TranslationRequired=TRUE` 時可輸入，否則灰底寫 `這一週不需要翻譯`。
- 逐格儲存（改完即寫），不需要總確認畫面——這幾個崗位不入排表演算法，改動風險低。
- 寫入路徑沿用 `writeToPossiblyProtectedGridSheet_()`（要處理 v0 受保護的情況）。
- 頁頂一句：`這三個崗位系統不會自動排，一定要人手填。`

### 3.4 畫面三：名單檢查（唯讀提示條）

不是編輯畫面，是四條唯讀提示，每條有「去處理」連去區三對應畫面：

| 提示 | 條件 |
|---|---|
| `表上有 N 個人沒有電郵，正式發出時會略過` | 本季最新版本用到的人之中 `Email` 空白 |
| `表上有 N 個名字不在人員名單` | 版本內 `PersonID` 找不到對應 `NameMapping` 行 |
| `有 N 個人的堂委／執事身分已過期` | `Roles` 中 `EffectiveTo` 早於本季 `StartDate` 而仍被當前排表引用 |
| `有 N 個崗位的合資格人數少於 3 人` | `Eligibility` 逐崗位統計 |

## 四、區三：名單維護

五個畫面，共通規矩：

- **不可刪行（D7）。** 只有 `Active` 開關或 `EffectiveTo`。
- 每次寫入都要寫 `AuditLog`（`action`、`targetSheet`、`targetKey`、`oldValue`、`newValue`、`source='WEBUI'`）。
- `PersonID` 一經建立不可改（畫面上顯示為灰字，不是輸入格）。
- 每個畫面頂部有搜尋格（比對中文名、英文名、`PersonID`）。
- 儲存前一個小確認：`會改動 1 行。[確定]`。批次改動（例如換屆）要列出全部受影響行。

### 4.1 人員與電郵（`NameMapping`）

| 欄位 | 可改 | 驗證 |
|---|---|---|
| `PersonID` | ✗（新增時系統自動編） | — |
| `NameTC` | ✓ | 必填；與現有行重複時警告但不阻擋（陳大文／陳大明的教訓：**不可以自動合併同名**，但真同名要人手確認） |
| `NameEN` | ✓ | — |
| `MemberNo` | ✓ | 5 位數字或空白 |
| `Email` | ✓ | 基本格式檢查；空白時該行顯示 `沒有電郵，正式發出會略過` |
| `EmailSource` / `EmailVerifiedAt` | 系統填 | 手動改 Email 時寫 `手動` ＋今日 |
| `Active` | ✓ | 設 `FALSE` 時警告：`設為停用之後，這個人不會再被自動排入職事表。已經排好的職事表不受影響。` |
| `MaxPerQuarter` | ✓ | 整數或空白 |
| `PersonalLinkToken` | ✗ | 每行一粒「重新產生連結」（外洩時用），接 `reissuePersonalLinkToken_()`，要打字確認 |

畫面附加兩粒掣：
- `從出席系統補電郵` → 現有 `runHwcasSync_()` ＋ `runApplyHwcasDraft_()` 兩步，Web 版要合併成「預覽差異 → 逐行勾選 → 套用」。**不可以整批自動套用**（HWCAS 是唯讀來源，配對錯就寄錯人）。
- `別名` → 開一個小視窗管 `NameAlias`（別名、對應哪個人、`Active`）。同一個人因為異體字或輸入法而寫成兩個不同的名（例如「恒／恆」、「珮／佩」、「敏慧／慧敏」這幾類）都在這裡處理，實際對照名單在試算表的 `NameAlias`，本文不列。

### 4.2 崗位資格（`Eligibility`）

矩陣式：橫軸崗位、直軸人，格內是 checkbox ＋ 歷史次數細字。

- 勾／取消勾 = 寫 `Eligible` ＋ `Active`。**取消勾一律寫 `Active=FALSE`，不刪行**（保留 `HistoricalCount`）。
- 新增資格時 `Source='手動'`、`AddedBy`＝當前帳戶、`AddedAt`＝今日。
- 每一列（人）尾有一個 `合共 N 個崗位`；每一欄（崗位）底有 `合資格 N 人`，少於 3 人時紅字。
- 儲存是批次的：改完一次過確認，確認畫面列出 `會新增 3 項資格、取消 1 項資格`。
- 頁頂一句：`系統只會排曾任該崗位的人。新人一定要在這裡加，系統不會自己擴充。`

### 4.3 身分：堂委／執事（`Roles`）

| 欄位 | 說明 |
|---|---|
| `PersonID` | 下拉揀人（顯示中文名） |
| `RoleCode` | 下拉：堂委 / 執事（寫入 `COMMITTEE` / `DEACON`，畫面永不顯示英文碼） |
| `EffectiveFrom` | 日期 |
| `EffectiveTo` | 日期或空白（空白＝現任） |
| `Active` | 開關 |

**換屆做法（畫面上要明寫）：**

```
換屆時不要刪除舊的行。
撳「換屆」，輸入卸任日期，系統會把所有現任的行填上「生效至」＝卸任日期，
然後你再逐個加入新一屆。

這樣做的原因：舊季度的職事表不會因為今日換屆而被追溯判成違規。
```

`換屆` 是一個批次動作：輸入日期 → 預覽（列出會被填 `EffectiveTo` 的全部行）→ 打字確認 → 執行。

一個人可以有多行（同時是堂委又是執事、或卸任後再連任），畫面按人分組顯示。

畫面底部唯讀提示：接 `buildRoleOverviewRows_()`，顯示 `Posts.RequiredRoles` 有沒有引用到零人持有的身分代號。

### 4.4 不能服侍的日期（`Unavailable`）

| 欄位 | 說明 |
|---|---|
| `PersonID` | 下拉揀人 |
| `DateFrom` / `DateTo` | 日期範圍（單日就兩格填同一日） |
| `AppliesTo` | 下拉：全部崗位 / 指定崗位 |
| `PostIDs` | `AppliesTo=指定崗位` 時才可填，checkbox 陣列 |
| `Reason` | 文字 |
| `Status` | 系統填 |

- **「不能服侍」一律代表整日不在**，畫面上要寫明：`系統沒有「上半場不在」這種概念。`
- 新增時即時警告：`這個日期範圍蓋住本季 3 個主日：11月8日、11月15日、11月22日。`
- 若該人在這些日子已被排入現有版本 → 紅字警告 `他在 11月8日 已被排了「讀經」。加了這一筆之後，要撳「儲存並確認」系統才會重新檢查。`
- 過期的行（`DateTo` 早於今日）自動摺到「已過去」一節，不刪。

### 4.5 個人崗位排除（`PersonPostExclusions`）

| 欄位 | 說明 |
|---|---|
| `PersonID` | 下拉揀人 |
| `PostID` | 下拉揀崗位 |
| `Reason` | 文字，必填（例如「暫時不任主席」） |
| `EffectiveFrom` / `EffectiveTo` | 日期，`EffectiveTo` 空白＝仍然生效 |
| `Active` | 開關 |

- **解除限制＝填 `EffectiveTo`，不是刪行、不是設 `Active=FALSE`。** 畫面上「解除」那粒掣直接彈日期選擇，預設今日。
- 與 4.2 崗位資格的分別要在畫面上寫清楚：
  `崗位資格 = 這個人從來沒做過這個崗位。`
  `暫時不做 = 這個人做得到，但這一段時間不排他。`

### 5.3 「回到上一個版本」完整規格

**做法：讀 v(N-1) 的派工紀錄，寫成新版本 v(N+1)。不刪任何舊版本。**

#### 為什麼不用 Google Sheets 版本記錄

畫面上要有這一句（幹事一定會問）：

```
不要用 Google 試算表本身的「版本記錄」還原。
那個只會還原你看到的那張表，不會還原系統內部的職事表資料、
不會還原這一季的進度、不會還原寄出記錄。
還原之後表面看起來對，實際上系統內部對不上，之後每一步都會出錯。
```

#### 流程

1. **前置檢查一：未儲存改動**
   grid 上有人手改動或有待處理申報 → **拒絕**：
   `你在表上改了 4 格未儲存。回到上一個版本會令這些改動消失。請先撳「儲存並確認」，或者把那幾格改回原樣。`
2. **前置檢查二：目標版本**
   下拉列出這一季全部版本（最新那個標 `（目前）` 並禁選）。
   預設選中 N-1。
3. **預覽**（唯讀，不寫任何嘢）
   逐格比對「目前版本」與「目標版本」，列出：
   - 會改回的格數
   - 逐格：日期／崗位／目前是誰／會變回誰
   - 目標版本的規則檢查結果（把舊版本的違反重新跑一次，因為規則可能自那時起改過）
4. **確認**（打字 `確認`）
   確認畫面必須寫齊：
   ```
   會建立第 4 版，內容與第 2 版相同。
   第 3 版不會被刪除，仍然可以查看和再回去。
   會重新發佈公開連結。
   不會寄出任何電郵、不會改變這一季的進度。
   ```
5. **執行**
   - 讀 `RosterAssignments` 中 `(quarterId, targetVersionNo)` 全部行
   - `createRosterSheet(quarterId, N+1, assignments, [])`
   - `writeAssignments(quarterId, N+1, assignments)`
   - `registerVersion(...)`，`Basis` 寫 `回到第 2 版`，`ParentVersionNo` 寫 **N**（實際的父版本，不是目標版本），`Notes` 寫 `內容取自第 2 版`
   - 逐格寫 `AuditLog`，`action='VERSION_ROLLBACK'`
   - `publishPublicRoster_()`（D6）
6. **失敗處理**：與掣 1 步 1.8／1.9 完全相同的分段訊息。

#### 與 Stage 的互動

**永不改變 Stage。** 逐個 Stage 的效果：

| Stage | 回退之後 |
|---|---|
| `DRAFT` | 沒有副作用 |
| `REVIEW_SENT` | 堂委手上的公開連結會即時變回舊內容。確認畫面要加：`堂委已經收過連結，他們現在開會看到回退後的內容。` |
| `REQUESTS_APPLIED` | 同上 |
| `OFFICIAL_SENT` | **最需要提醒**：`義工已經收過信和 PDF，他們手上那份是舊的。回退之後要撳「改動後重發」，受影響的人才會知道。` 確認畫面必須顯示會有幾多人受影響。 |

#### 與人手改動的互動

已在前置檢查一擋住。**不提供「保留我的改動同時回退」**——這是兩個相反的意圖，混在一起無法用一個確認畫面講清楚。

## 七、實作時必須守的三條

1. **HtmlService 逃逸**：`<?= JSON.stringify(x) ?>` 前端會拿到帶引號的字串。全部注入資料一律用 `<?!= ?>` 或改由 `google.script.run` 取。
2. **falsy 值不可用 `|| ''` 吞掉**：`Active=FALSE`、`Confirmed=FALSE`、`SlotIndex=0` 都是有意義的值。顯示層要分辨「空白」與「FALSE」。
3. **每次改動過 Web UI 之後一定要重新部署**：編輯任一部署 → 新增版本 → 另一個部署改指同一版本號 → 兩者存取權都親眼核對 → Deploy。`clasp push` 本身不會令改動生效。
