## 一、共通規則（全頁適用）

### 1.1 頁面骨架

```
┌─────────────────────────────────────────────┐
│ 粵語堂職事表                                  │
│ 季度：[2026年10-12月 ▾]   狀態：初稿已生成…    │  ← 唯一的季度下拉
│                          [測試模式] [🌙]      │
├─────────────────────────────────────────────┤
│ 這一季現在的情況                              │  ← 狀態卡（一句人話）
├─────────────────────────────────────────────┤
│ 區二　開季前準備            （還有 3 項未做）  │  ← 未做完 >0 時展開，=0 時收摺
├─────────────────────────────────────────────┤
│ 區一　日常四個掣                              │  ← 永遠展開，永遠在最當眼
├─────────────────────────────────────────────┤
│ 區三　名單維護                     （收摺）    │
├─────────────────────────────────────────────┤
│ 區四　進階功能                     （收摺）    │
└─────────────────────────────────────────────┘
```

- 季度下拉只有一個，在最頂。全頁所有動作都作用於它。**任何彈窗都不再問一次季度。**
- 季度下拉的文字寫人話：`2026年10-12月`，後面括號補 `（10月4日開始）`。不寫 `2026T4`。
- 換季度＝整頁重新載入狀態，任何已打開的確認畫面立即關閉。

### 1.2 狀態卡文字（取代 `Stage`）

| 內部 Stage | 有無版本 | 狀態卡顯示 |
|---|---|---|
| `DRAFT` | 無 | 還未生成初稿。建議在 **11月27日** 之後生成，撳下面的「生成初稿」。 |
| `DRAFT` | 有 | 初稿已生成，未寄給堂委。 |
| `REVIEW_SENT` | 有 | 已寄給堂委，等他們的意見。 |
| `REQUESTS_APPLIED` | 有 | 堂委意見已處理，未正式發出給全體。 |
| `OFFICIAL_SENT` | 有 | 已正式發出給全體。 |

狀態卡第二行（細字，排第二位）：`目前第 3 版　12月4日 11:20　套用堂委意見後`

測試模式徽章：`DRY_RUN=TRUE` 時顯示紅色 `測試模式：不會真的寄出任何電郵`。

### 1.3 術語對照（畫面上一律用右欄）

| 不可出現 | 改寫成 |
|---|---|
| Stage / 階段 | 「這一季現在的情況」 |
| RosterAssignments / grid | 「職事表」／「表上」 |
| Version / v2 | 「第 2 版」（永遠連同日期與一句描述） |
| DRY_RUN | 「測試模式」 |
| Requests | 「修改申報」 |
| SendLog | 「寄出記錄」 |
| Eligibility | 「崗位資格」 |
| PersonPostExclusions | 「暫時不做某崗位」 |
| Unavailable | 「不能服侍的日期」 |
| Roles / COMMITTEE / DEACON | 「身分」／「堂委」／「執事」 |
| SpecialSundays | 「特別主日」 |
| hard rule / HARD_ELIGIBILITY | 「一定要遵守的規則」＋人話理由 |
| materialise | 「儲存成新一版」 |

### 1.4 確認畫面規範

1. **一個動作只有一個確認畫面。** 所有輸入在動作開始前已在畫面上填好。
2. 確認畫面必須有數字：會寄幾多封、會改幾多格、會建立第幾版。
3. **只有不可逆動作要打字確認**：正式發出給全體（掣 3）、改動後重發（掣 4）、放行硬規則違反。其餘一律「確定／取消」兩粒掣。
4. 打字確認的字串一律是 **`確認`** 兩個字，不用英文、不用長句。
5. 確認畫面永遠有「取消」，取消＝零改動、零寄出。

### 1.5 錯誤訊息規範

每一個失敗訊息必須有三段，缺一不可：

```
發生了什麼：找不到「陳大汶」這個名字。
現在的情況：職事表沒有任何改動，第 2 版仍然是最新一版。
你可以怎樣做：
  ・如果打錯字，把那一格改回「陳大文」
  ・如果是同一個人的別寫，去「名單維護 ▸ 人員與電郵」加別名
  ・如果是新人，去「名單維護 ▸ 人員與電郵」新增
```

**不可以只寫技術原因。** 不可出現 exception message 原文（原文寫入 `AuditLog`，畫面只給人話 + 一個「複製技術詳情」細掣）。

### 1.6 不可撳的掣

不可撳時 **講「怎樣才撳得到」，不講「為何失敗」**。掣本身變灰、可 hover、下方一行灰字寫條件。

反例：`目前鎖定——現在 Stage 是 DRAFT`
正例：`要先撳「寄給堂委審閱」，收齊意見之後再撳「儲存並確認」，這一粒才會著。`

### 1.7 一條總原則

> **掣 1 是唯一會改動職事表內容的掣。掣 2／3／4 只寄信，永不改內容。**

所以掣 2／3／4 執行前一律先檢查「有沒有未儲存的改動」，有就拒絕並指去掣 1（D5）。

## 二、區一：日常的掣

> **第二十五輪批次改動：生成初稿由「系統自動」改成「幹事撳掣」。**
>
> 原本設計是季初前 5 週由 trigger 自動生成、再 email 通知幹事。
> 決定改掉，理由是：真正操作系統的人不懂電腦，
> **「系統靜靜幫你做了一件事」比「你撳個掣才會發生」難教很多**——
> 幹事開頁見到已經有一份初稿，他沒辦法分辨「是我上次撳的」還是
> 「是系統自己做的」，也不知道應該相信哪一個。
>
> 改完之後，**系統不會自己動任何東西**，全部行動由幹事發起。
> 失去的安全網（幹事放假／病了就沒人做）由提醒信補回：
> `GenerateOn` 到期而這一季仍然沒有任何版本，會**每天**提醒幹事去撳掣，
> 直到生成為止（這一項提醒不設次數上限，見 `Trigger.gs` 維度四）。
>
> 自動生成那條程式碼路徑一行都沒有刪，只是加了一道開關
> （Config `TRIGGER_AUTO_GENERATE`，預設 `FALSE`）。

### 2.1 掣 0：生成初稿

**只在這一季完全沒有版本時出現。** 有版本之後這一粒消失，
四個日常掣才出現——同時見到一粒生得、四粒死，對幹事來說是噪音。

重新生成（覆蓋式）不在這裡，在區四「進階功能」。

#### 動態文字

| 情況 | 文字 |
|---|---|
| 未到 `GenerateOn` | `建議在 2026-11-27 之後生成，那時距離季初大約五個星期。現在就生成也可以。` |
| 就是今天 | `原定 2026-11-27 生成，就是今天。` |
| 已過 `GenerateOn` | `原定 2026-11-27 生成，已經過了 3 天。` |
| 沒有 `GenerateOn` | `隨時可以生成。` |

#### 確認畫面

生成是**可逆**的——不會寄信、不會覆蓋任何東西（沒有版本才撳得到），
所以**不需要打字確認**。打字確認留給真正不可逆的動作（掣 3／掣 4）；
每個動作都要打字，打字就會變成機械動作，到真正危險那一次就失去作用。

```
生成 2027年1-3月 的初稿
・13 個主日、20 個崗位
・系統會試 20 次不同排法，揀最平均那一次
・講員、翻譯、獻花不會自動排，要你之後人手填
・不會寄出任何電郵

可能需要一至數分鐘，過程中不要關掉這個視窗。

[開始生成]  [取消]
```

#### 執行中

全頁按鈕停用，顯示 `正在生成……已經開始，請不要關掉視窗或重新整理。`

#### 成功畫面

```
已生成初稿（第 0 版）
13 個主日、20 個崗位、有 2 格未能安排

[開啟職事表檢查同修改]      ← 大掣，開新分頁

在試算表直接改格子，改完回來撳「儲存並確認」。
另外「開季前準備」還有 3 項未做（講員 13、獻花 13、合堂 1）。
```

「還有 N 項未做」必須真的去叫 `apiGetPreQuarterChecklist()` 拿實數，
不可以寫死。算不到時顯示「暫時查不到」，**不可以顯示 0**。

跑少了次數（`stoppedByTime`）一定要講出來——排表品質下降而幹事完全
不知道，是最差的一種失敗。

#### 失敗處理

三段式。特別要處理「這一季已經有版本」：
`這一季已經有第 1 版，不會重複生成。如果想重新生成，請去「進階功能」。`

### 2.2 四個掣的狀態機

| 掣 | 可撳的條件 | 執行後 Stage |
|---|---|---|
| 1 儲存並確認 | 已有至少一個版本（任何 Stage 都可撳） | `DRAFT`→`DRAFT`；`REVIEW_SENT`→`REQUESTS_APPLIED`；其餘不變 |
| 2 寄給堂委審閱 | 已有版本 **且** Stage ≠ `OFFICIAL_SENT` **且** 沒有未儲存改動 | 一律設為 `REVIEW_SENT` |
| 3 正式發出給全體 | Stage = `REQUESTS_APPLIED` **且** 沒有未儲存改動 **且** 這一季從未正式發出過 | `OFFICIAL_SENT` |
| 4 改動後重發 | Stage = `OFFICIAL_SENT` **且** 沒有未儲存改動 **且** 上次發出之後有人的安排改過 | 不變 |

「未儲存改動」的定義（三者任一成立）：
1. 最新版本的 grid 工作表上有系統認得出的人手改動（`resolveAuthoritativeState_(..., GRID_OVERLAY)` 的 `changes.length > 0`）
2. grid 上有系統認不出的文字（`unresolved.length > 0`）
3. `Requests` 工作表有待處理申報（`readPendingRequests_()` 非空）

### 2.3 每個掣旁邊那句動態文字

每次開頁、每次動作完成之後重新計算一次（一個新 API `apiGetDashboardState(quarterId)` 一次過回傳，不要逐粒掣各自打一次後端）。

#### 掣 1

| 情況 | 文字 |
|---|---|
| 零改動、零申報 | `未偵測到你在表上改過任何格。` |
| 有 grid 改動 | `偵測到你在表上改了 4 格。` |
| 有申報 | `有 3 筆修改申報未處理。` |
| 兩者都有 | `偵測到你在表上改了 4 格，另有 3 筆修改申報未處理。` |
| 有認不出的文字 | `有 2 格的文字系統認不出，撳下去會告訴你是哪幾格。` |
| Stage=`REVIEW_SENT` 且零改動 | `堂委沒有提出改動。撳下去就當作意見已收齊，可以進入正式發出。` |

#### 掣 2

| 情況 | 文字 |
|---|---|
| 可撳 | `把唯讀連結寄給 3 位收件人。` |
| 收件人為 0 | `現時沒有登記任何堂委電郵，寄出去不會有人收到。先去「名單維護」補。` |
| 已寄過 | `上次在 11月28日 14:30 寄過。再撳一次會重新寄給同一批人。` |

#### 掣 3

| 情況 | 文字 |

### 2.4 掣 1「儲存並確認」——完整內部流程

九步。每一步都可能中止，中止時**必須說清楚職事表現在處於什麼狀態**。

#### 步 1.1　取現況

讀最新版本 N、建立 context（`buildFineTuneContext_`）。

- **失敗：沒有任何版本** → 掣本身已變灰，不會走到這裡。
- **失敗：grid 工作表被刪或改名** → 訊息：
  `找不到「第 2 版」的工作表。職事表資料本身仍然完整（在 RosterAssignments 內），但你看的那張表不見了。可以去「進階功能 ▸ 回到上一個版本」重新建立一張。`

#### 步 1.2　認名

`unresolved.length > 0` → **立即中止，不進入之後任何步驟。**

畫面列出：日期、崗位、你輸入的文字。每一行給三個出路（1.5 節的三段式）。
**不提供「略過這幾格繼續」。** 認不出就是認不出，猜是第十九輪那一類 bug 的溫床。

#### 步 1.3　讀待處理申報

`readPendingRequests_()`（用 `RequestID` 空白判斷，不看 Status）。分三類：

| 類別 | 處理 |
|---|---|
| `APPLY` | 直接列出，會自動套用 |
| `CONFIRM` | 逐筆要幹事勾選才套用（例如要順手加崗位資格） |
| `NEEDS_INPUT` | **不阻擋**。列出並寫明：`這 2 筆系統看不懂，會原封不動留在申報表，你可以之後自己處理。` |

#### 步 1.4　合併，grid 優先

同一格既有 grid 人手改動、又有申報 → **grid 贏**。

確認畫面必須有獨立一節：
`以下 2 格你在表上改過，同時亦有修改申報。系統會以你表上的為準：`
（逐格列：日期／崗位／申報想改成／你表上是）

#### 步 1.5　規則檢查

用 `STATE_SOURCE.GRID_OVERLAY` 跑 `findStateViolations_()`，套第二十一輪的三分類：

| 類別 | 行為 |
|---|---|
| 第 1 類：真違反 | **阻擋**。要打字 `確認` 放行 |
| 第 2 類：規則後加、舊資料追溯不合 | 顯示，不阻擋 |
| 第 3 類：結構性不適用 | 顯示，不阻擋 |
| 準硬規則（連續兩週） | 顯示警告，不阻擋 |

放行畫面文案：
```
以下 1 格違反了一定要遵守的規則：
　11月8日　報告　陳大文
　原因：報告只可以由現任堂委擔任，陳大文目前不在堂委名單。

如果這是正確的（例如名單還未更新），請在下面輸入「確認」放行。
放行之後這一格會照樣儲存，並記入 AuditLog。
[            ]  [放行並繼續]  [取消]
```

#### 步 1.6　三欄對照，逐格接受／拒絕

只有「有違反 **且** 系統找到替代人選」的格才出現建議欄。沿用 `proposeMinimalFix()` ＋ `apiDetectChanges()` 已有的 `original／manual／suggested`。

畫面（每格一行，預設全部選「用我改的」）：

| 日期 | 崗位 | 原本 | 你改成 | 系統建議 | 選擇 |
|---|---|---|---|---|---|
| 11月8日 | 報告 | 李美華 | 陳大文 | 張淑儀 | ⦿用我改的　○用系統建議　○改回原本 |

- **預設一定是「用我改的」。** 幹事的決定是最新真相。
- 「改回原本」在原本是空白時要禁用（`applyDecisions()` 已有這道保護，前端要同步變灰並寫 `原本這一格是空白，不能改回`）。
- 全部格頂部一粒「全部用我改的」快捷。

#### 步 1.7　確認畫面

一頁過，包含：

```
儲存成第 3 版

會做的事：
　・套用你在表上改的 4 格
　・套用 3 筆修改申報（其中 1 筆是你剛才勾選確認的）
　・2 筆申報系統看不懂，會留在申報表不動
　・放行 1 項規則違反（你剛才輸入了確認）
　・儲存成第 3 版。第 2 版原封不動保留，可以對照
　・重新發佈公開連結（連結地址不變）

不會做的事：
　・不會寄出任何電郵
　・不會產生任何 PDF

[確定儲存]  [取消]
```

#### 步 1.8　寫入

次序固定：`AuditLog` 逐格 → `createRosterSheet()` → `writeAssignments()` → `registerVersion()`。

- **失敗：中途出錯（版本已建、派工未齊）** → 這是最危險的一種。訊息必須寫：
  `儲存到一半失敗了。第 3 版可能只寫入了一部分。請去「進階功能 ▸ 檢查各版本派工紀錄」核對，或用「回到上一個版本」退回第 2 版。原因：<人話>`
  並且 **不要前進 Stage、不要發佈公開連結**。

## 三、區二：開季前準備

本季一次性。標題右邊常駐 `（還有 N 項未做）`，N = 0 時整區收摺並顯示 `全部做好了`。

### 3.1 「未做完 N 項」怎樣算

N = 以下五項之中，`count > 0` 的**項數**（不是格數）。每項各自顯示自己的數字。

| # | 項目 | count 的定義 | 阻不阻擋掣 2 |
|---|---|---|---|
| 1 | 特別主日日期未確認 | `SpecialSundays` 中本季 `Active=TRUE` 且 `isUnconfirmedSpecialSunday_()` 為真的行數（**空白＝已確認**，只有明確 `FALSE` 才算未確認） | 否，只在掣 2 完成畫面提醒 |
| 2 | 合堂未指定跳過崗位 | 本季 `Type` 為合堂類、`SkipPostIDs` 空白的行數 | 否 |
| 3 | 講員未填 | 本季主日之中，講員崗位仍為空白的週數 | 否 |
| 4 | 翻譯未填 | 本季主日之中 `TranslationRequired=TRUE` 而翻譯仍空白的週數 | 否 |
| 5 | 獻花未填 | 本季主日之中獻花仍空白的週數 | 否 |

名單檢查**不計入 N**（它跟人不跟季），改為一個獨立提示條，見 3.4。

### 3.2 畫面一：確認特別主日

一張表，一行一個特別主日：

| 日期 | 類型 | 名稱 | 這一週哪些崗位不用排 | 日期已確認 |
|---|---|---|---|---|
| 2027-03-28 | 浸禮 | 復活節／浸禮 | ☐領詩 ☐司琴 ☐… | ☐ |

- 「哪些崗位不用排」用 checkbox 陣列，不是叫幹事打 `WORSHIP,PIANO`。寫入時轉成 `SkipPostIDs`。
- 「日期已確認」是 checkbox。**未勾 = 寫入 `FALSE`；勾了 = 寫入空白**（配合 `isUnconfirmedSpecialSunday_()` 的方向，不可以反）。
- 可以改日期（`ServiceDate`），改完要即時警告如果新日期不在本季 `ServiceDates` 之內。
- 「新增一個特別主日」掣：日期、類型（下拉：合堂／浸禮／宣教月／堂慶／其他）、名稱、跳過崗位。

年度性動作放在這一頁底部（一年撳一次）：
- `產生下一年度四個季度`
- `產生年度合堂建議`
兩者都是先預覽、確認才寫入，沿用現有 `AnnualQuarters.gs`／`AnnualCombined.gs`。

### 3.3 畫面二：填講員／翻譯／獻花

把現有 `PreacherFillSidebar.html` 原樣搬上 Web，接現有 `apiListPreacherTranslationPending()` / `apiSavePreacherTranslationEntry()`。

- 一行一週：日期、講員、翻譯、獻花，各自一個自由文字輸入格。
- 翻譯欄只在該週 `TranslationRequired=TRUE` 時可輸入，否則灰底寫 `這一週不需要翻譯`。

> **第二十五輪批次階段 B：拆走了「歷史建議下拉」，改為「儲存之後的回饋」。**
>
> 拆走的理由不是實作有問題，是這個功能本身沒用：講員多數外請或客席、
> 翻譯視乎該週講員的語言需要臨時決定、獻花由會友認獻幾乎每次不同人。
> 用歷史記錄去猜，命中率極低，反而阻住幹事打字。
> 而且實際上根本沒有資料——這三個崗位在 `RosterAssignments` 從來沒填過，
> 所以建議名單一直都是空的。

#### 輸入格必須關掉瀏覽器自動填充

三個輸入格都要 `autocomplete="off"` ＋ 一個 Chrome 認不出的 `name` 值。

沒有這個的話，Chrome 會當它是聯絡人欄位，彈出**使用者自己的通訊錄**。
幹事會以為那些是系統給的建議名單，撳下去就填了一個完全不相干的人。

#### 儲存之後的回饋（取代建議下拉）

`apiSavePreacherTranslationEntry()` 本來就回傳 `linkedToNameMapping`，
但畫面一直沒有顯示。儲存成功之後在該行下面顯示：

| 情況 | 文字 |
|---|---|
| `linkedToNameMapping === true` | `已對上名單上的「XXX」，正式發出時他會收到通知。` |
| `linkedToNameMapping === false` | `名單上沒有這個名字，正式發出時不會寄給他。外請講員屬正常。` |

**為什麼這一句比建議下拉重要得多**：翻譯打錯一個字，那位弟兄姊妹就
**永遠收不到通知**——正式發出時他不在收件名單裡。而畫面上完全看不出：
職事表照樣印住那個名，PDF 照樣有他，一切正常。這一句是唯一會立刻告訴你的位。

⚠️ 對不上**不一定是錯**（外請講員本來就不在名單），所以文案要講清楚
「外請講員屬正常」，不可以寫成錯誤——寫成錯誤幹事會去「修正」一件沒問題的事。

- 逐格儲存（改完即寫），不需要總確認畫面——這幾個崗位不入排表演算法，改動風險低。
- 寫入路徑沿用 `writeToPossiblyProtectedGridSheet_()`（要處理 v0 受保護的情況）。
- 頁頂一句：`這三個崗位系統不會自動排，一定要人手填。`

### 4.2.1 從出席系統（HWCAS）補電郵

> **第二十八輪批次新增**（`src/WebAppHwcas.gs`）。
> 兩個 API：`apiHwcasPreview`／`apiHwcasApplySelected`。
> 入口在「人員與電郵」畫面。

選單版是兩步（產生 `NameMapping_Draft` 初稿 → 整批套用）。
Web 版改成三步：**預覽差異 → 逐行勾選 → 套用**。

**⚠️ 絕對不可以整批自動套用。** HWCAS 是唯讀外部來源，配對靠姓名。
配對錯了的後果是**把甲的電郵寫進乙的資料**——之後乙收到甲的職事表，
甲永遠收不到，而畫面上完全看不出：兩個人都有電郵，職事表照樣印著兩個名。

名單裡真的有幾位姓名只差最後一個同音字的弟兄姊妹。他們是不同的人。

| 規則 | 做法 |
|---|---|
| 預設全部不勾 | 而且**沒有「全選」捷徑**——有了那粒按鈕，「逐個看過」就會變成「撳一下」 |
| 同名多人／認不出 | 連勾都不能勾 |
| 會蓋掉一個不同的現有電郵 | 紅色警告（蓋掉之後，本來收到信的那位就會停止收到，而沒有任何訊號） |
| 風險分級 | 在**後端**做，前端只負責畫紅色。判斷邏輯留在一處 |
| 預覽 | **不寫 `NameMapping_Draft`**——預覽就應該是唯讀 |
| 套用 | 後端只收 `personId` 清單，電郵重新讀一次 HWCAS，並逐行再驗一次 |
| 套用之後 | `EmailSource=HWCAS`、`EmailVerifiedAt=今日`、逐行寫 `AuditLog` |
| Config 未設定 | 回一個獨立旗標，畫面寫：`還沒有設定出席系統的試算表位置。請先在 Config 填 HWCAS_SPREADSHEET_ID。` |

**對 HWCAS 一律唯讀，一個格都不會寫。**

⚠️ 未經瀏覽器驗證，亦未對真實 HWCAS 試算表跑過。

### 4.4 不能服侍的日期（`Unavailable`）

| 欄位 | 說明 |
|---|---|
| `PersonID` | 下拉揀人 |
| `DateFrom` / `DateTo` | 日期範圍（單日就兩格填同一日） |
| `AppliesTo` | 下拉：全部崗位 / 指定崗位 |
| `PostIDs` | `AppliesTo=指定崗位` 時才可填，checkbox 陣列 |
| `Reason` | 文字 |
| `Status` | 系統填 |

- **「不能服侍」一律代表整日不在**，畫面上要寫明：`系統沒有「上半場不在」這種概念。`
- 新增時即時警告：`這個日期範圍蓋住本季 3 個主日：11月8日、11月15日、11月22日。`
- 若該人在這些日子已被排入現有版本 → 紅字警告 `他在 11月8日 已被排了「讀經」。加了這一筆之後，要撳「儲存並確認」系統才會重新檢查。`
- 過期的行（`DateTo` 早於今日）自動摺到「已過去」一節，不刪。

### 4.5 個人崗位排除（`PersonPostExclusions`）

> **第二十八輪批次已實作**（`src/WebAppExclusions.gs` ＋ 區三「暫時不做某崗位」）。
> 四個 API：`apiListExclusions`／`apiSaveExclusion`／`apiAddExclusion`／`apiLiftExclusion`。
>
> `apiLiftExclusion()` 做成**獨立 API** 而不是叫呼叫端用 `apiSaveExclusion()`：
> 獨立入口才**結構上**保證它只寫 `EffectiveTo` 一欄，不會順手改到
> `Active` 或原因，而不是靠呼叫端記得。
>
> 補上的兩條保護：解除日早過生效日會被擋（否則會出現一段負長度的生效期，
> 等於那條限制從來沒有存在過）；打錯 `PostID` 會標示出來
> （崗位表沒有那個代號的話，這條限制根本不會生效，而畫面看起來完全正常）。
>
> ⚠️ 未經瀏覽器驗證。

| 欄位 | 說明 |
|---|---|
| `PersonID` | 下拉揀人 |
| `PostID` | 下拉揀崗位 |
| `Reason` | 文字，必填（例如「暫時不任主席」） |
| `EffectiveFrom` / `EffectiveTo` | 日期，`EffectiveTo` 空白＝仍然生效 |
| `Active` | 開關 |

- **解除限制＝填 `EffectiveTo`，不是刪行、不是設 `Active=FALSE`。** 畫面上「解除」那粒掣直接彈日期選擇，預設今日。
- 與 4.2 崗位資格的分別要在畫面上寫清楚：
  `崗位資格 = 這個人從來沒做過這個崗位。`
  `暫時不做 = 這個人做得到，但這一段時間不排他。`

### 4.6 排表偏好（`PersonPostWeight`）

> **第二十六輪批次新增。** 一個機制搞掂堂委三條「某人多做／少做某崗位幾次」嘅意見。

背景：堂委收到 2026T4 系統初稿之後改咗 23 格，**全部集中喺四個崗位**
（主席、報告、當值堂委、聖餐襄禮），其餘十二個崗位一格都冇改。
三條意見形狀完全一樣：**某人 × 某崗位 → 比平均多／少 N 次**。

#### 同「崗位資格」嘅分別（要喺畫面上講清楚）

```
崗位資格 = 邊個「可以」做。
排表偏好 = 邊個「做幾多次」。
```

⚠️ 兩件事一定要分開改。混埋一齊嘅話，幹事想「少排佢一次」就會去
取消佢嘅資格——而嗰個等於「以後永遠唔會排佢」，一件完全唔同、
而且好難察覺已經做錯咗嘅事。

#### 畫面

同「崗位資格」一樣揀一個崗位，然後逐個人一個下拉。
**只顯示有該崗位資格嘅人**——90 × 16 個空下拉係一幅噪音。

| 顯示 | 存入 `Adjust` |
|---|---|
| 多兩次 | +2 |
| 多一次 | +1 |
| 一般（預設） | 冇呢一行（或者已經填咗 `EffectiveTo`） |
| 少一次 | -1 |
| 少兩次 | -2 |

**下拉用人話，唔俾幹事打數字**——打錯一個負號就完全相反，
而「多一次」同「少一次」睇落只差一個字。

- **揀返「一般」＝填 `EffectiveTo` 為今日，唔刪行**（同 4.5 一致）
- **改動＝解除舊行 ＋ 加新行**，唔就地改個數字——就地改嘅話，
  「上一次係幾多、幾時改、點解改」就冇咗
- 每次改動要填原因，唔填唔俾儲存
- 批次儲存，確認畫面列出 `會新增 3 項偏好、解除 1 項偏好`

#### 頁頂一句

`這裡只影響「誰做多少次」。不會影響誰有資格做，也不會令系統違反任何規則。`

#### 語意

- `Adjust` 係 **soft**，**永遠唔可以壓過任何硬規則或準硬規則**
- `+1` 嘅意思係「呢一季佢喺呢個崗位多做**大約**一次」，唔係「一定多一次」
- 排表品質統計要有一節逐行列出：生效中嘅偏好、目標次數、實際排到幾多次、差幾多。
  **唔可以只改行為而唔顯示結果**

### 5.1 搬上 Web（第二十八輪批次定案：只有七個 ＋ 三個既有入口）

> **⚠️ 這一節在第二十八輪批次被大幅收窄。**
>
> 原本這裡列了十七個工具。實作時重新判斷過：其中大部分是診斷／維護工具，
> **使用者是 Ivan 或者 IT，不是幹事**。搬上來只會令幹事在一堆他一世都不會撳的

**幹事日常真的會用到的七個：**

|---|---|---|
| 重新生成初稿（覆蓋式） | `apiGenerateRoster` | 無；**要打字確認**，並警告會建立新版本、會蓋走未儲存的人手改動 |

**外加三個既有入口**（不是本輪新增，但同樣住在區四）：
回到上一個版本、重新發佈公開連結、規則審閱表匯出／匯入（見 5.4）。

#### 實作上的三條規矩

1. **不可以呼叫任何 `run*_()`。** 那些函式全部會叫 `ui.alert()`，
   在 Web App 環境沒有 Sheets UI，一叫就爆。要叫它們裡面的純運算函式
   ——那些早就為了寫離線測試而拆好了。
2. **版本下拉一律寫人話**：`第 2 版　2026-12-04 11:20　套用修改申報後`。
   原因文字用共用的 `buildVersionBasisText_()`（跟狀態卡同一份翻譯表），
   時間用共用的 `normalizeSentAt_()`。兩邊各有一套就會有一天對不上。
3. **「列出待補格子」不收版本號。** 它問的是「現在還有哪幾格未填」，
   而「現在」永遠是最新版本。叫幹事揀只會令他對著一份跟現況無關的清單去填格。

### 5.2 留在選單，不搬

### 5.3 「回到上一個版本」完整規格

**做法：讀 v(N-1) 的派工紀錄，寫成新版本 v(N+1)。不刪任何舊版本。**

#### 為什麼不用 Google Sheets 版本記錄

畫面上要有這一句（幹事一定會問）：

```
不要用 Google 試算表本身的「版本記錄」還原。
那個只會還原你看到的那張表，不會還原系統內部的職事表資料、
不會還原這一季的進度、不會還原寄出記錄。
還原之後表面看起來對，實際上系統內部對不上，之後每一步都會出錯。
```

#### 流程

1. **前置檢查一：未儲存改動**
   grid 上有人手改動或有待處理申報 → **拒絕**：
   `你在表上改了 4 格未儲存。回到上一個版本會令這些改動消失。請先撳「儲存並確認」，或者把那幾格改回原樣。`
2. **前置檢查二：目標版本**
   下拉列出這一季全部版本（最新那個標 `（目前）` 並禁選）。
   預設選中 N-1。
3. **預覽**（唯讀，不寫任何嘢）
   逐格比對「目前版本」與「目標版本」，列出：
   - 會改回的格數
   - 逐格：日期／崗位／目前是誰／會變回誰
   - 目標版本的規則檢查結果（把舊版本的違反重新跑一次，因為規則可能自那時起改過）
4. **確認**（打字 `確認`）
   確認畫面必須寫齊：
   ```
   會建立第 4 版，內容與第 2 版相同。
   第 3 版不會被刪除，仍然可以查看和再回去。
   會重新發佈公開連結。
   不會寄出任何電郵、不會改變這一季的進度。
   ```
5. **執行**
   - 讀 `RosterAssignments` 中 `(quarterId, targetVersionNo)` 全部行
   - `createRosterSheet(quarterId, N+1, assignments, [])`
   - `writeAssignments(quarterId, N+1, assignments)`
   - `registerVersion(...)`，`Basis` 寫 `回到第 2 版`，`ParentVersionNo` 寫 **N**（實際的父版本，不是目標版本），`Notes` 寫 `內容取自第 2 版`
   - 逐格寫 `AuditLog`，`action='VERSION_ROLLBACK'`
   - `publishPublicRoster_()`（D6）
6. **失敗處理**：與掣 1 步 1.8／1.9 完全相同的分段訊息。

#### 與 Stage 的互動

**永不改變 Stage。** 逐個 Stage 的效果：

| Stage | 回退之後 |
|---|---|
| `DRAFT` | 沒有副作用 |
| `REVIEW_SENT` | 堂委手上的公開連結會即時變回舊內容。確認畫面要加：`堂委已經收過連結，他們現在開會看到回退後的內容。` |
| `REQUESTS_APPLIED` | 同上 |
| `OFFICIAL_SENT` | **最需要提醒**：`義工已經收過信和 PDF，他們手上那份是舊的。回退之後要撳「改動後重發」，受影響的人才會知道。` 確認畫面必須顯示會有幾多人受影響。 |

#### 與人手改動的互動

已在前置檢查一擋住。**不提供「保留我的改動同時回退」**——這是兩個相反的意圖，混在一起無法用一個確認畫面講清楚。

### 5.4 規則「人話版」審閱表（第二十八輪批次新增）

> `RuleSettings` 上面寫著一個 0 到 1 之間的小數。堂委看著那個數字是
> **沒有辦法決定任何事**的——他們不知道單位、不知道調大調小是想怎樣、
> 更不知道調完之後實際會有什麼分別。

**匯出**：在 `ROSTER_DRIVE_FOLDER_ID` 下的 `RuleReview` 子資料夾建立一個新試算表。

| 編號 | 規則（一句話） | 這一條在做什麼 | 現時設定 | 可以改成 | 堂委決定 | 備註／原因 |

- **小數一律換算成「N 個主日之中大約 M 個」。**
  ⚠️ **分母不可以寫死 13**——有些季度是 12 或 14 個主日，整句話的意思
  完全靠那個分母。分母錯了，堂委就會照著一個錯的比例做決定。
  查不到就**不換算**，改寫百分比並明講查不到。
- 分三組：一定要遵守（硬規則，只可揀「同意／要討論」）、盡量遵守（準硬規則）、
  目標值（軟規則，各有 2–5 個人話選項，並標明哪一個是「維持現狀」）。
- 「堂委決定」一欄用資料驗證下拉、黃底。其餘欄由系統產生，不應該改。

**匯入**：只讀「堂委決定」與「備註」兩欄，**其餘一律忽略**——
即使堂委在表上改了規則名或現時設定，都不會進入系統。
然後三欄對照（現時／堂委決定／換算成 `RuleSettings` 的值）給幹事**逐條**
接受或拒絕，跟掣 1 同一個模式，**預設全部不接受**。

**硬規則那一組一律不可以由匯入改動**——就算堂委揀了「要討論」，
系統只會記錄（`AuditLog` 的 `RULE_REVIEW_NOTE_ONLY`），不會改 `Enabled`。

比較「有沒有改動」時**比次數，不比原始小數**：0.63 顯示成「約 8 個」，
而 8 ÷ 13 反推回去是 0.62——比小數的話，揀「維持現狀」反而會靜靜把值改掉。

### 5.5 年度工具（第二十八輪批次搬入區二）

`產生下一年度四個季度`、`產生年度合堂建議` 搬到區二「確認特別主日」畫面底部

## 七、實作時必須守的三條

1. **HtmlService 逃逸**：`<?= JSON.stringify(x) ?>` 前端會拿到帶引號的字串。全部注入資料一律用 `<?!= ?>` 或改由 `google.script.run` 取。
2. **falsy 值不可用 `|| ''` 吞掉**：`Active=FALSE`、`Confirmed=FALSE`、`SlotIndex=0` 都是有意義的值。顯示層要分辨「空白」與「FALSE」。
3. **每次改動過 Web UI 之後一定要重新部署**：編輯任一部署 → 新增版本 → 另一個部署改指同一版本號 → 兩者存取權都親眼核對 → Deploy。`clasp push` 本身不會令改動生效。
